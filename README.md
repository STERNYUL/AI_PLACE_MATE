# AI PLACE MATE

> 조건을 말하면 근거가 붙은 세 곳이 온다 — AI 장소 큐레이션 서비스

제품 문서 저장소입니다. 현재 단계는 **PRD v0.1 → SRS 변환**이며, 이 README는 그 변환의 목표·규격·경계를 규정합니다.

## 1. 작업 목표

`ai-place-prd-v0.1.html` (PRD v0.1 · §1–§9 · 14슬라이드)을 **SRS 형식 문서로 변환**합니다.

### 1.1 무엇을 만드는가

**예시 SRS 문서와 동일한 포맷의 추가 문서를 만든다.**

기준은 SRS 국제 표준안(ISO/IEC/IEEE 29148)의 전체 목차가 아니라 **예시 SRS 문서 그 자체**입니다.
→ [`reference/SRS-example-AD-Core-Platform.md`](reference/SRS-example-AD-Core-Platform.md)

예시 문서의 섹션 구성·표 서식·요구사항 ID 체계·기술 밀도가 곧 변환 규격입니다.

### 1.2 확장 규칙 — 예시 범위를 벗어나는 내용의 처리

기존 PRD에 **예시 SRS의 범위를 벗어나는 내용이 있는 경우에만**, 그 부분에 한해 SRS 표준 포맷의 구성을 따라 확장해 작성합니다.

```
PRD 내용 ─┬─ 예시 SRS에 대응 섹션이 있음  →  예시 포맷 그대로 이관
          └─ 예시 SRS에 대응 섹션이 없음  →  그 부분만 SRS 표준 포맷 구성에 따라 확장
```

확장은 **예외 처리**입니다. 기본값은 언제나 예시 포맷이며, 확장은 옮길 그릇이 없는 내용에만 적용합니다.

### 1.3 비목표 (Non-goals)

| 하지 않는 것 | 이유 |
| --- | --- |
| SRS 표준안 풀버전 문서 작성 | 목표는 예시 포맷 준수. 표준 전체 목차를 채우는 것이 아님 |
| 예시 SRS에 없는 섹션을 표준 목차대로 일괄 신설 | 확장은 PRD에 옮길 내용이 실제로 있을 때만 |
| PRD 내용의 신규 추가·창작 | 변환이지 집필이 아님. 없는 요구사항을 만들지 않음 |
| PRD 원본 수정 | PRD는 상위 문서로 보존. SRS는 별도 산출물 |

## 2. 변환 규격 — 예시 SRS에서 추출

### 2.1 섹션 구성

```
문서 헤더        문서 ID · 개정 버전 · 날짜 · 표준
1. 서론          1.1 목적 / 1.2 범위 / 1.3 정의·약어·축약어
2. 이해관계자     역할 · 이름/부서 · 책임
3. 시스템 맥락 및 인터페이스   클라이언트 / 내부 서비스 / 외부 시스템
4. 구체적 요구사항  4.1 기능 요구사항 / 4.2 비기능 요구사항
5. 추적성 매트릭스  요구사항 ID · 모듈 · 구현 클래스 · 테스트 케이스 ID
6. 부록          6.1 API 엔드포인트 / 6.2 데이터 모델 / 6.3 비즈니스 규칙 / 6.4 DB 스키마
7. 향후 개선 사항
푸터             작성자 · 검토자 · 승인자
```

### 2.2 요구사항 표 규격 — 9열 고정

`ID · 제목 · 출처 · 우선순위 · 유형 · 검증 방식 · 인수 기준 · 상태 · 담당자`

| 항목 | 규격 |
| --- | --- |
| ID | `REQ-FUNC-nnn` (기능) / `REQ-NF-nnn` (비기능) — 3자리 연번, **볼드** |
| 우선순위 | `Must Have` / `Should Have` / `Could Have` |
| 유형 | 기능은 `Functional` / 비기능은 `Performance` `Scalability` `Reliability` `Security` `Maintainability` |
| 검증 방식 | 번호 목록. 기능은 `1) …<br>2) …<br>3) QA 검증` 3단, 비기능은 단문 |
| 인수 기준 | 단일 서술문, 수치 포함, `~해야 한다` 규범형 종결 |
| 상태 | `Proposed` |
| 담당자 | 2. 이해관계자 표의 역할명 중 하나 |

### 2.3 서식 제약

| 항목 | 규격 |
| --- | --- |
| 형식 | 마크다운. 표 중심 |
| 도식 | **없음** — 예시 SRS에 mermaid·이미지가 전혀 없음. PRD의 flowchart 4개·erDiagram 1개는 표·코드·목록으로 치환 |
| 코드 펜스 | 데이터 모델은 `java` enum, DB 스키마는 `sql` 주석 목록 |
| 문체 | 한글. 요구사항은 `~해야 한다`, 서술은 `~한다` |
| 셀 내 줄바꿈 | `<br>` |

## 3. 매핑 계획 — PRD → SRS

### 3.1 이관 (예시 SRS에 그릇이 있음)

| PRD | → 예시 SRS 대응 | 변환 방식 |
| --- | --- | --- |
| §7 In Scope | 1.2 범위 | 불릿 목록으로 정리 |
| PRD 전반 용어 (WEBD · Verification · canonical_key · Top-3 · 폴백 등) | 1.3 정의·약어 | 문서 전역에서 수집해 용어 표 구성 |
| §1 Owner 5팀 | 2. 이해관계자 | 역할·부서·책임 3열로 전개 |
| §7 플랫폼(네이버 지도 탭·모바일 웹) · §6.3 외부 API 3개 | 3. 시스템 맥락 및 인터페이스 | 클라이언트/내부/외부 3분류 |
| §3 AC 24개 + §4 F1–F9 MSCW·근거 | **4.1 기능 요구사항** | AC→인수 기준, MSCW→우선순위, 우선순위 근거→출처 |
| §5 성능·신뢰성·보안·비용 24항 | **4.2 비기능 요구사항** | 항목별 REQ-NF 분해, 유형 어휘 매핑 |
| §5.5 모니터링 7항 | 4.2 검증 방식 열 | 수집 방식·알림 임계를 검증 방식으로 흡수 |
| §6 erDiagram · 필드 규칙 | 6.2 데이터 모델 / 6.4 DB 스키마 | erDiagram → 코드 펜스 + 테이블 목록 |
| §6.3 API 8개 | 6.1 API 엔드포인트 | 서비스·메서드·엔드포인트·설명 4열 |
| §7 Out of Scope + §4 Won't 5항 | 7. 향후 개선 사항 | 버전별 개선 항목으로 재배치 |

### 3.2 확장 (예시 SRS에 그릇이 없음 → §1.2 확장 규칙 적용)

| PRD | 상태 | 확장 방향 |
| --- | --- | --- |
| §1.1 Pain 12개 + 실패 KPI | 예시에 대응 없음 | 4.1 출처 열로 흡수 + 문제 정의 절 신설 |
| §1.2 목표 · §1.3 북극성·보조 KPI 12개 | 예시에 대응 없음 | 이해관계자 요구사항·측정 지표 절로 확장 |
| §2 페르소나 8명 + JTBD | 예시 2절은 내부 역할만 | 사용자 클래스·특성 절로 확장 |
| §2.2 여정 flowchart · 이탈 분기 3개 | 예시에 대응 없음 | 3절에 운영 시나리오로 확장 (도식 → 단계 표) |
| §4.2 의존성 flowchart · 병목 2개 | 예시에 대응 없음 | 요구사항 의존성 절 + 5. 추적성 확장 |
| §7.2 리스크 R1–R7 | 예시에 대응 없음 | 리스크·완화 절 신설 |
| §7 가정 A1–A5 | 예시에 대응 없음 | 가정·제약 절 신설 (표준 항목) |
| §7 ADR-001~004 | 예시에 대응 없음 | 설계 결정 기록 절 신설 |
| §8 실험 E1–E7 · Phase 0→GA 게이트 | 예시 7절은 로드맵 성격만 | 검증 계획·릴리스 게이트 절로 확장 |
| §9 확보 근거 · 측정 체계 | 예시에 대응 없음 | 4.x 검증 방식 흡수 + 부록 배치 |

### 3.3 역방향 공백 — 예시 SRS에 있고 PRD에 없음

| 예시 SRS | PRD 상태 | 처리 |
| --- | --- | --- |
| 5. 추적성 매트릭스 (구현 클래스 · TC ID) | 구현 설계·테스트 케이스 미정 | 모듈·TC ID 골격만 채우고 구현 클래스는 미정 표기 |
| 2. 이해관계자 8역할 | Owner 5팀 단일 | 예시 역할 체계에 맞춰 보강 필요 |
| 문서 헤더 (문서 ID · 승인자) | 없음 | 신규 부여 |
