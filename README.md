# AI PLACE MATE

> 조건을 말하면 근거가 붙은 세 곳이 온다 — AI 장소 큐레이션 서비스

제품 문서 저장소입니다. 현재 단계는 **PRD v0.1 → SRS 변환**이며, 이 README는 그 변환의 목표·규격·경계를 규정합니다.

## 1. 작업 목표

`ai-place-prd-v0.1.html` (PRD v0.1 · §1–§9 · 14슬라이드)을 **SRS 형식 문서로 변환**합니다.

### 1.1 무엇을 만드는가

**예시 SRS 문서와 동일한 포맷의 추가 문서를 만든다.**

기준은 SRS 국제 표준안(ISO/IEC/IEEE 29148)의 전체 목차가 아니라 **예시 SRS 문서 그 자체**입니다.
→ [`reference/SRS-example-AD-Core-Platform.md`](reference/SRS-example-AD-Core-Platform.md)

예시 문서의 섹션 구성·표 서식·요구사항 ID 체계·기술 밀도가 곧 변환 규격입니다.

### 1.2 확장 규칙 — 예시 범위를 벗어나는 내용의 처리

기존 PRD에 **예시 SRS의 범위를 벗어나는 내용이 있는 경우에만**, 그 부분에 한해 SRS 표준 포맷의 구성을 따라 확장해 작성합니다.

```
PRD 내용 ─┬─ 예시 SRS에 대응 섹션이 있음  →  예시 포맷 그대로 이관
          └─ 예시 SRS에 대응 섹션이 없음  →  그 부분만 SRS 표준 포맷 구성에 따라 확장
```

확장은 **예외 처리**입니다. 기본값은 언제나 예시 포맷이며, 확장은 옮길 그릇이 없는 내용에만 적용합니다.

### 1.3 비목표 (Non-goals)

| 하지 않는 것 | 이유 |
| --- | --- |
| SRS 표준안 풀버전 문서 작성 | 목표는 예시 포맷 준수. 표준 전체 목차를 채우는 것이 아님 |
| 예시 SRS에 없는 섹션을 표준 목차대로 일괄 신설 | 확장은 PRD에 옮길 내용이 실제로 있을 때만 |
| PRD 내용의 신규 추가·창작 | 변환이지 집필이 아님. 없는 요구사항을 만들지 않음 |
| PRD 원본 수정 | PRD는 상위 문서로 보존. SRS는 별도 산출물 |

## 2. 변환 규격 — 예시 SRS에서 추출

### 2.1 섹션 구성

```
문서 헤더        문서 ID · 개정 버전 · 날짜 · 표준
1. 서론          1.1 목적 / 1.2 범위 / 1.3 정의·약어·축약어
2. 이해관계자     역할 · 이름/부서 · 책임
3. 시스템 맥락 및 인터페이스   클라이언트 / 내부 서비스 / 외부 시스템
4. 구체적 요구사항  4.1 기능 요구사항 / 4.2 비기능 요구사항
5. 추적성 매트릭스  요구사항 ID · 모듈 · 구현 클래스 · 테스트 케이스 ID
6. 부록          6.1 API 엔드포인트 / 6.2 데이터 모델 / 6.3 비즈니스 규칙 / 6.4 DB 스키마
7. 향후 개선 사항
푸터             작성자 · 검토자 · 승인자
```

### 2.2 요구사항 표 규격 — 9열 고정

`ID · 제목 · 출처 · 우선순위 · 유형 · 검증 방식 · 인수 기준 · 상태 · 담당자`

| 항목 | 규격 |
| --- | --- |
| ID | `REQ-FUNC-nnn` (기능) / `REQ-NF-nnn` (비기능) — 3자리 연번, **볼드** |
| 우선순위 | `Must Have` / `Should Have` / `Could Have` |
| 유형 | 기능은 `Functional` / 비기능은 `Performance` `Scalability` `Reliability` `Security` `Maintainability` |
| 검증 방식 | 번호 목록. 기능은 `1) …<br>2) …<br>3) QA 검증` 3단, 비기능은 단문 |
| 인수 기준 | 단일 서술문, 수치 포함, `~해야 한다` 규범형 종결 |
| 상태 | `Proposed` |
| 담당자 | 2. 이해관계자 표의 역할명 중 하나 |

### 2.3 서식 제약

| 항목 | 규격 |
| --- | --- |
| 형식 | 마크다운. 표 중심 |
| 도식 | 예시 SRS에는 도식이 **전혀 없음**. → **의도적 이탈** — mermaid 6개 추가 (아래 참조) |
| 코드 펜스 | 데이터 모델은 `java` enum, DB 스키마는 `sql` 주석 목록 |
| 문체 | 한글. 요구사항은 `~해야 한다`, 서술은 `~한다` |
| 셀 내 줄바꿈 | `<br>` |

## 3. 매핑 결과 — PRD → SRS

**산출물:** [`SRS-ai-place-v1.0.md`](SRS-ai-place-v1.0.md) — 문서 ID `SRS-AIPLACE-MVP-001` · 개정 1.8 · 요구사항 **59건**(REQ-FUNC 27 · REQ-NF 32)

> 초기 변환은 50건이었습니다. 최종 검토에서 29148 **§5.2.5 Singular**("요구사항은 단일 능력·특성·제약·품질 인자를 진술한다") 위반 7건을 분할해 59건이 되었습니다. 판정 기준은 SRS 4.2에 명문화했습니다 — **이행 수단이 서로 다른 통제는 분리**(2FA/감사로그, 저장/전송 암호화, RTO/RPO, 보관기간/목적제한 등), **하나의 인자를 여러 지표로 측정하는 경우는 유지**(p95/p99, 캐시 히트/미스).

### 3.0.1 확장 절의 표준 근거 — ISO/IEC/IEEE 29148:2018 §9.6

확장 절은 임의로 만들지 않고 **표준 조항에 1:1로 근거**를 두었습니다. §9.6.1이 "절 구성 순서는 프로젝트 정보관리 정책에 따라 선택할 수 있다"고 허용하므로, 사내 양식의 절 구성을 유지한 채 대응 절이 없는 내용만 조항 근거로 확장했습니다. 전체 대응표는 SRS **1.1.1**에 있습니다.

| 확장 절 | 근거 조항 |
| --- | --- |
| 1.4 문제 정의 및 목표 | **§9.6.20 (c)** 소프트웨어가 해결할 문제의 기술 · §9.6.3 (c) 편익·목표 |
| 1.5 가정 및 제약 | **§9.6.8** Assumptions and dependencies · **§9.6.7** Limitations |
| 2.2 이용자 클래스 및 특성 | **§9.6.6** User characteristics |
| 3.2 운영 시나리오 | **§9.6.4.7** Operations · §9.6.5 Product functions |
| 3.1.1~3.1.7 인터페이스 하위 절 | **§9.6.4.1~9.6.4.9** 시스템·이용자·하드웨어·통신·메모리·지역 적응·서비스 인터페이스 |
| 4.3 요구사항 의존성 및 구현 규모 | **§9.6.9** Apportioning of requirements |
| 4.4 표준 및 규제 준수 | **§9.6.17** Standards compliance · §9.6.16 Design constraints |
| 4.5 기능 처리 규격 | **§9.6.12** Functions (유효성·연산 순서·비정상 대응·파라미터·입출력 관계) |
| 8.1.1 인터페이스 상세 | **§9.6.11** External interfaces (목적·범위·단위·타이밍·형식·포함 항목) |
| 8.6 논리 데이터베이스 요구사항 | **§9.6.15 (a)(b)(c)(e)(f)(g)** 정보 유형·빈도·접근 능력·정합성·보안·보존 |
| 5.2 요구사항 → 측정 지표 | **§9.6.9** (교차 참조표 요구) |
| 6. 검증 및 릴리스 | **§9.6.19** Verification |
| 7. 리스크 및 설계 결정 | **§9.6.16** Design constraints · §9.6.20 (b) |
| 8.5 근거 자료 | **§9.6.20 (a)(b)** 사용자 조사 결과·배경 정보 |

**§9.6.1~9.6.20 전 조항을 인용·충족했습니다.** 본문에 대응 내용이 없는 조항(§9.6.4.3 하드웨어 인터페이스 · §9.6.4.6 메모리 제약)은 임의로 채우지 않고 **해당 없음과 그 이유**를 명시했습니다 — 웹 클라이언트라 전용 하드웨어가 없고, 자원 제약이 메모리 용량이 아니라 처리량·단위 비용으로 표현되기 때문입니다.

조항이 부과한 규율 3건도 그대로 따랐습니다.

- **§9.6.6** "구체적 요구사항을 명시하지 말라" → 2.2는 요구사항을 쓰지 않고 대응 REQ ID만 참조
- **§9.6.19** "검증 항목은 §9.6.10~18과 병렬로 제시" → 6절이 4.1·4.2의 검증 방식 열과 병렬 구조
- **§9.6.20** "이 정보 항목이 요구사항의 일부인지 명시하라" → 1.4·8.5를 배경 정보로, 요구사항은 4.1·4.2로 한정한다고 SRS 1.1.1에 명시

도식 6개도 표준 근거가 있습니다 — **§9.6.4**("상위 시스템의 주요 요소·상호연결·외부 인터페이스를 보이는 블록 다이어그램"), **§9.6.5 b)**("기능과 그 관계를 보이는 도해적 방법"). 사내 양식에는 도식이 없으나 표준이 명시적으로 권장합니다.

### 3.0.2 6.1의 실험 설계 → KPI 계측 계획 교체

PRD §8은 A/B 실험 7건(E1~E7)의 표본 크기·성공 임계까지 사전 확정하고 있었습니다. **MVP 개발 관점에서는 시기상조**라 판단해 6.1을 **KPI 계측 계획**으로 교체했습니다 — 기준선이 실측으로 확보되기 전에는 표본 크기와 성공 임계를 산출할 근거가 없고, 미리 정한 설계는 실측 분산이 드러나는 순간 폐기됩니다.

교체 후 6.1의 구성은 이렇습니다.

| 절 | 내용 |
| --- | --- |
| 6.1.1 이벤트 정의 | 이벤트 22종 — 트리거 시점 · 고유 속성 · 계측 지점. 공통 속성 4개(`session_id`·`anon_user_id`·`occurred_at`·`schema_version`) |
| 6.1.2 KPI 산출식 | 북극성 + 보조 11 각각의 **분자(카운트 대상 이벤트) · 분모 · 중복 제거 단위 · 주기** |
| 6.1.3 계측 운영 규칙 | 세션 정의(30분) · 이용자 식별 · 중복 제거 · 봇 제외 · 결측 처리(누락률 5% 초과 시 미공표) · 스키마 버전 · **실험은 실측 분산 확보 후 설계** |
| 6.1.4 기준선 확보 계획 | `산정` 9건과 `0% (신규)` 6건을 실측으로 전환하는 Phase 0 산출물 + 확보 우선순위 ①②③ |

§9.6.19는 검증의 "접근법과 방법"을 요구하는데, 기준선이 없는 단계의 방법은 실험 설계가 아니라 **계측 설계**입니다. E1~E7을 참조하던 9곳(가정 확정 창구 3건 · REQ-NF 검증 방식 2건 · 리스크 완화 1건 · ADR 2건 · 절 주석 1건)도 계측 기준으로 함께 고쳤습니다.

> **표준 PDF는 저장소에 포함하지 않습니다.** `29148-2018-ISOIECIEEE.pdf`는 IEEE 라이선스 제한 문서(Authorized licensed use limited to / Restrictions apply)로, PUBLIC 저장소 배포가 저작권 위반입니다. `.gitignore`로 제외했고 조항 내용은 SRS 본문에 인용 형태로만 반영했습니다.

### 5.2.1 SRS 두 갈래 — 왜 나눴는가

기준 SRS는 **의도적으로 플랫폼을 특정하지 않습니다.** 29148 **§5.2.5 Appropriate**("아키텍처·설계에 불필요한 제약을 두지 말라")와 **§9.6.10**("요구사항에 설계 해법을 넣으면 다른 설계 대안이 배제된다")을 따른 것입니다. 구현 제약을 기준 SRS에 직접 써넣으면 그 제약이 요구사항으로 굳어 대안 검토가 막힙니다.

그래서 `SRS-ai-place-nextjs-v1.0.md`를 **별도 문서**로 두었습니다.

| | 기준 SRS (MVP-001) | 구현 제약 반영본 (NEXT-001) |
| --- | --- | --- |
| 답하는 질문 | 무엇을 만족해야 하는가 | **이 스택에서 어떻게 만족시키는가 · 무엇이 불가능한가** |
| 플랫폼 | 비종속 | Next.js App Router · Vercel · Supabase 확정 |
| ID 체계 | `REQ-FUNC` 27 · `REQ-NF` 32 | `REQ-IMPL` 34 |
| 요구사항 재서술 | — | **하지 않는다.** 출처 열에서 기준 요구사항을 참조하고 실현 방식만 규정 |

**핵심은 4.3 「제약 충돌 분석 및 해소」 11건입니다.** 지정 제약과 기준 요구사항이 충돌하는 지점을 숨기지 않고 해소 방식·잔여 위험과 함께 밝혔습니다. 대표 3건:

| 충돌 | 해소 |
| --- | --- |
| 대화방 180초 마감을 **함수가 대기해서 구현할 수 없다** (상주 프로세스·장시간 함수 부재) | 대기하지 않는다. `expiresAt`을 DB에 기록하고 **읽기 시점 판정**. Cron은 상태 정규화만 담당하므로 Cron이 지연되어도 조회 결과가 정확하다 |
| 제안 도착을 **서버가 푸시할 수 없다** (서버리스는 WebSocket 유지 불가) | 클라이언트가 **Supabase Realtime을 직접 구독**한다. 대가는 RLS 정책이 유일한 방어선이 되는 것 |
| **RPO 5분을 기본 백업으로 달성할 수 없다** | Supabase PITR 애드온을 전제한다. 미승인 상태에서 목표를 충족한다고 **주장하지 않고** 재협상 경로를 명시 |

29148 **§9.6.10**은 요구사항에 설계 해법을 넣으면 "다른 설계 대안이 배제될 위험"이 생긴다고 경고하고, **§5.2.5 Appropriate**는 아키텍처·설계에 불필요한 제약을 두지 말라고 규정합니다. 이 경계에 따라 도식을 나눴습니다 — **같은 도식을 두 문서에 두지 않습니다.**

| | SRS (12개) | SDD (17개) |
| --- | --- | --- |
| 관점 | 블랙박스 — 외부에서 관찰 가능한 것 | 화이트박스 — 내부 구조와 호출 |
| 유스케이스 | 개요 (액터 ↔ 요구사항 군) — 4.1.0 | 수요·공급 분리 + 명세 12건 — 2.1~2.3 |
| 클래스 | 열거형과 소유 엔터티 (데이터 계약) — 8.2 | 도메인 클래스(메서드 포함) · 서비스 계층 — 3.1~3.2 |
| ERD | 논리 — 엔터티와 관계 — 8.2 | 물리 — PK·FK·UK·IDX·파티셔닝 — 3.3 |

**배경지식이 없는 독자를 위해** 각 도식 앞에 "읽는 방법" 주석을 붙였습니다 — 다중도 `1 : 0..*`의 뜻, `<<include>>`와 `<<extend>>`의 차이, 시퀀스의 실선·점선, `PK`·`FK`·`IDX` 표기 등.
