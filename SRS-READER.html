PART 1 · 표 읽는 법

요구사항 한 줄에는 8개의 통제 장치가 들어 있다

§4.1의 표는 열이 8개입니다. 각 열은 장식이 아니라 프로젝트의 서로 다른 리스크를 하나씩 잠그는 장치입니다. 아래는 REQ-FUNC-004 한 줄을 열 단위로 분해한 것입니다.

① ID — REQ-FUNC-004

모든 대화의 좌표. 회의록·티켓·커밋·테스트가 이 번호로 서로를 가리킵니다. 번호가 없으면 "그 기능"이라는 말로 회의를 하게 되고, 그러면 서로 다른 것을 이야기하게 됩니다. FUNC는 기능, NF는 비기능이라는 뜻으로, 번호 안에 분류가 들어 있습니다.

② 제목 — 3단계 폴백 광고 로직

한 줄 이름표. 좋은 제목은 동사 + 목적어로 무엇을 하는 기능인지 드러냅니다.

③ 출처 Source — 설계 문서 5.1

"누가 이걸 요구했나"의 답. 나중에 "이 요구사항 빼도 되나요?"라는 질문이 왔을 때 돌아가서 물어볼 사람을 지정합니다. 이 SRS에서 비기능 요구사항 3건의 출처가 업계 가이드라인인데, 이는 돌아가서 물어볼 사람이 없다는 뜻이므로 약한 출처입니다.

④ 우선순위 — Must Have

일정이 부족할 때 무엇을 먼저 자를지 미리 정해둔 것. 압박이 들어온 뒤에 정하면 정치가 되고, 미리 정해두면 판정이 됩니다.

⑤ 유형 Type — Functional

기능(무엇을 하는가) / 성능·보안·신뢰성 등 비기능(얼마나 잘 하는가). 유형이 다르면 테스트 방법과 담당 조직이 다릅니다. 성능은 QA가 아니라 대개 운영·인프라 쪽에서 봅니다.

⑥ 검증 방식 — 폴백 순서 테스트 / 단계 검증 / QA 검증

어떻게 확인할 것인가. 이 열이 비어 있거나 모호하면 그 요구사항은 사실상 검수가 불가능합니다. "QA 검증"은 검증 방식이 아니라 검증 주체입니다 — 다음 장에서 다시 다룹니다.

⑦ 인수 기준 Acceptance Criteria — PM의 최종 무기

"1단계: 정밀 타게팅 / 2단계: 인구통계만 / 3단계: 컨텍스트·기본 광고". 이 문장을 통과하면 끝난 것이고, 통과 못 하면 끝나지 않은 것입니다. 개발이 "다 됐어요"라고 할 때 PM이 펼치는 유일한 문서가 이 칸입니다.

⑧ 상태 / 담당자 — Proposed / 개발 엔지니어

지금 이 요구사항이 합의된 것인지 제안된 것인지, 그리고 누가 책임지는지. 이 SRS는 13개 조항이 전부 Proposed입니다. 즉 아직 아무것도 승인되지 않았습니다.

문서와 프로세스의 언어

회의에서 이 단어들이 나올 때, 사람들은 절차상의 위치를 이야기하고 있는 것입니다.

요구사항Requirement

시스템이 만족해야 할, 참·거짓을 판정할 수 있는 조건.

핵심 "빠르면 좋겠다"는 요구사항이 아닙니다. "p95 100ms 이하"가 요구사항입니다. 판정할 수 없으면 요구사항이 아니라 희망입니다.

기능 / 비기능 요구사항Functional / Non-functional

무엇을 하는가 / 얼마나 잘 하는가.

이 문서 REQ-FUNC 8건, REQ-NF 5건. 비기능이 프로젝트를 죽이는 경우가 더 많은데, 대개 일정 뒤로 밀립니다.

인수 기준Acceptance Criteria

이 요구사항이 "완료"임을 판정하는 통과선.

이 문서 §4.1·§4.2의 일곱 번째 열. PM이 검수 때 펼치는 유일한 칸입니다.

검증 / 확인Verification / Validation

검증 = "명세대로 만들었나". 확인 = "애초에 옳은 것을 만들었나".

구분 명세대로 완벽히 만들었는데 시장이 원하지 않는 것일 수 있습니다. 검증은 개발팀, 확인은 PM의 책임입니다.

추적성Traceability

요구사항 ↔ 설계 ↔ 코드 ↔ 테스트를 잇는 실.

이 문서 §5 추적성 매트릭스. 실이 끊긴 코드는 "왜 있는지 아무도 모르는 코드"가 되어 아무도 손대지 못합니다.

MoSCoWMust / Should / Could / Won't

우선순위 4등급.

주의 Won't를 적지 않으면 "안 하기로 한 것"이 기록에 남지 않아 나중에 요구로 되살아납니다.

이해관계자Stakeholder

결과에 이해가 걸린 사람 전부.

이 문서 §2에 8개 역할. 광고주와 최종 사용자가 빠져 있습니다 — 돈을 내는 쪽과 광고를 보는 쪽이 없습니다.

범위 / 범위 크리프Scope / Scope Creep

이번에 만들 것의 경계 / 그 경계가 슬금슬금 넓어지는 현상.

방어법 §1.2 범위와 §7 향후 개선을 한 장에 나란히 붙여 두는 것. 요청이 올 때마다 "그건 §7 항목입니다"라고 가리킬 수 있습니다.

MVPMinimum Viable Product

가치를 검증할 수 있는 최소 구성.

이 문서 문서 ID의 MVP. §7이 곧 "의도적으로 자른 것들"의 목록입니다.

MECEMutually Exclusive, Collectively Exhaustive

겹치지 않고, 빠짐없이.

이 문서 인구통계 세분화의 대전제. 14장에서 한 강의를 통째로 씁니다.

SLA / SLO / SLIAgreement / Objective / Indicator

계약상 약속 / 내부 목표 / 실제 측정값.

순서 SLI(측정)가 있어야 SLO(목표)를 세우고, SLO가 있어야 SLA(계약)를 씁니다. 이 SRS는 SLA만 있고 SLI 정의가 없습니다.

DoDDefinition of Done

팀이 합의한 "끝났다"의 정의. 인수 기준의 상위 공통 규칙.

차이 인수 기준은 조항마다 다르고, DoD는 모든 조항에 공통으로 적용됩니다 (예: 코드 리뷰 완료, 테스트 통과, 문서 갱신).

RACIResponsible / Accountable / Consulted / Informed

실행자 / 최종 책임자 / 자문 / 통보 대상.

이 문서 §2와 §4.1의 담당자 열이 R에 해당합니다. A(최종 책임자)가 조항별로 지정돼 있지 않습니다.

스파이크Spike

모르는 것을 추정하지 않고, 시간을 정해두고 조사만 하는 작업.

쓸 곳 "100ms가 가능한지 모르겠다"에는 견적이 아니라 3일짜리 스파이크를 배정하는 것이 정답입니다.

시스템의 뼈대를 말하는 언어

아키텍처란 나중에 바꾸기 어려운 결정들의 집합입니다. 그래서 SRS 단계에서 다루는 것입니다.

모놀리스Monolith

하나의 프로그램 안에 모든 기능이 들어 있는 구조.

장점 단순합니다. 배포 한 번, 데이터베이스 하나, 함수 호출은 공짜. 대부분의 프로젝트는 여기서 시작하는 게 맞습니다.

마이크로서비스 아키텍처MSA

독립적으로 배포·확장할 수 있는 작은 서비스 여럿으로 쪼갠 구조.

이 문서 Audience / Campaign / Ad Serving / Tracking 4개. 20장에서 그 대가를 자세히 다룹니다.

서비스 경계Service Boundary / Bounded Context

서비스를 어디서 자를 것인가 하는 선.

기준 "함께 바뀌는 것은 함께 둔다." 캠페인 설정과 예산은 같이 바뀌므로 한 서비스, 사용자 프로필은 따로 바뀌므로 다른 서비스입니다.

API 게이트웨이API Gateway

모든 외부 요청이 들어오는 정문. 인증·라우팅·속도 제한을 여기서 처리.

이 문서 §5 추적성 매트릭스에서 REQ-NF-001의 모듈로 등장합니다. §3 시스템 맥락에는 없습니다 — 문서 내 불일치입니다.

동기 / 비동기Synchronous / Asynchronous

답이 올 때까지 기다린다 / 던져놓고 다음 일을 한다.

이 문서 광고 요청은 동기(사용자가 기다림), 이벤트 수집은 비동기(사용자는 이미 떠남). 이 구분이 100ms 예산의 열쇠입니다.

배치Batch

한 건씩 보내지 않고 모아서 한 번에 보내는 것.

이 문서 POST /api/v1/tracking/events의 "일괄 수집". 요청 횟수를 100분의 1로 줄이는 대신, 전송 전 유실 위험을 받아들입니다.

결합도 / 응집도Coupling / Cohesion

서로 얼마나 얽혀 있나 / 한 덩어리가 얼마나 한 가지 일에 집중하나.

목표 낮은 결합, 높은 응집. 결합이 높으면 A를 고칠 때 B가 깨집니다 — 일정이 예측 불가능해지는 첫 번째 원인입니다.

상태 비저장Stateless

서버가 이전 요청을 기억하지 않는 것. 요청마다 필요한 정보를 다 들고 옴.

왜 중요 기억하지 않으면 서버를 아무 대나 늘려도 됩니다. 수평 확장(REQ-NF-002)의 전제 조건입니다.

캐시Cache

느리게 얻는 것을 미리 빠른 곳에 복사해두는 것.

대가 원본이 바뀌었는데 사본이 옛것이면 틀린 답을 빠르게 줍니다. 캠페인 예산 소진처럼 즉시 반영돼야 하는 값은 캐시하면 안 됩니다.

메시지 큐 / 브로커Message Queue / Broker

일을 줄 세워두는 대기열. 보내는 쪽과 처리하는 쪽을 떼어놓음.

이 문서 명시되지 않았지만, 초당 1,000건 이벤트를 받으려면 사실상 필수입니다. 설계 검토에서 확인할 항목입니다.

단일 장애점SPOF · Single Point of Failure

그것 하나 죽으면 전체가 멈추는 지점.

이 문서 REQ-NF-003이 요구하는 "서비스 수준 이중화"가 이걸 없애라는 뜻입니다.

타임아웃 / 재시도 / 서킷 브레이커Timeout / Retry / Circuit Breaker

기다림의 상한 / 실패 시 다시 / 반복 실패하면 아예 차단.

3종 세트 남의 서비스가 느려질 때 내 서비스까지 같이 죽는 것을 막는 표준 방어책. 타임아웃 없는 호출은 장애를 전파합니다.

우아한 성능 저하Graceful Degradation

완벽하게 못 하면 아예 멈추는 대신, 덜 좋은 결과라도 내주는 것.

이 문서 3단계 폴백이 바로 이 패턴입니다. 정밀 광고가 없으면 대충이라도 채웁니다.

멱등성Idempotency

같은 요청을 두 번 보내도 결과가 한 번 보낸 것과 같음.

왜 필요 네트워크는 응답을 잃어버립니다. 클라이언트는 실패인 줄 알고 재전송하고, 서버는 클릭을 2번 기록합니다. 광고 정산에서 이건 곧 돈입니다.

§6.1 API 목록을 읽기 위한 언어

API 표는 서비스 간 계약서입니다. 이 표가 확정돼야 팀들이 병렬로 일할 수 있습니다 — 일정 관리의 핵심 문서입니다.

APIApplication Programming Interface

프로그램끼리 정해진 형식으로 주고받기로 한 약속.

비유 식당의 메뉴판. 주방이 어떻게 요리하는지는 몰라도, 메뉴판에 적힌 대로 주문하면 그것이 나옵니다.

엔드포인트Endpoint

그 약속을 실제로 부르는 주소.

이 문서 /api/v1/ads/request 처럼 §6.1에 10개가 정의돼 있습니다.

RESTRepresentational State Transfer

주소는 "자원"을 가리키고, 동사는 HTTP 메서드로 표현하는 API 설계 스타일.

읽는 법 주소에 명사만 있으면 REST답습니다. /campaigns/{id}/targeting은 좋고, /ads/request는 명사가 아니라 동작이라 REST 관례에서 벗어납니다 — 흔한 실용적 타협입니다.

HTTP 메서드GET / POST / PUT / PATCH / DELETE

조회 / 생성 / 통째로 교체 / 일부만 수정 / 삭제.

이 문서 DELETE가 하나도 없습니다. 소프트 삭제 정책(REQ-FUNC-007)과 맞물리는데, 삭제 API 자체가 §6.1에서 빠져 있습니다.

경로 변수 / 쿼리 파라미터Path Variable / Query Parameter

주소 안에 박히는 값 {userId} / 물음표 뒤에 붙는 조건 ?from=2025-06-01.

구분 무엇을 가리키는가는 경로에, 어떻게 걸러 볼 것인가는 쿼리에.

JSONJavaScript Object Notation

데이터를 주고받는 표준 글자 형식. 사람도 읽을 수 있음.

실무 API 문서의 "요청/응답 예시"는 거의 항상 JSON입니다. PM이 읽을 줄만 알아도 스펙 리뷰의 질이 달라집니다.

상태 코드HTTP Status Code

응답에 붙는 세 자리 숫자. 성공·실패의 종류를 말함.

외울 것 2xx 성공 · 4xx 요청한 쪽 잘못 (401 인증 안 됨, 403 권한 없음, 404 없음, 429 너무 잦음) · 5xx 서버 잘못 (500 오류, 503 과부하).

버저닝Versioning

주소에 /v1/을 넣어 기존 사용자를 깨뜨리지 않고 새 버전을 낼 수 있게 하는 것.

이 문서 전 엔드포인트가 /api/v1/. 좋은 설계입니다 — 광고주 연동 코드를 강제로 바꾸게 하지 않겠다는 약속입니다.

인증 / 인가Authentication / Authorization

누구냐 / 그걸 해도 되느냐.

이 문서 REQ-NF-004는 인증만 말하고 인가는 사실상 비어 있습니다. 광고주 A가 광고주 B의 캠페인 성과를 조회할 수 있는지가 정해지지 않았습니다.

속도 제한Rate Limiting

한 클라이언트가 정해진 시간에 부를 수 있는 횟수의 상한.

없으면 클라이언트 하나의 버그가 전체 서비스를 마비시킵니다. 초당 1,000건을 감당해야 하는 시스템에는 필수입니다.

OpenAPI 명세OpenAPI Specification (Swagger)

API를 기계가 읽을 수 있는 형식으로 적어둔 문서.

PM 활용 이게 있으면 개발 전에 가짜 서버를 띄워 프런트엔드와 병렬 작업이 가능합니다. 일정을 앞당기는 가장 확실한 장치입니다.

계약 테스트Contract Test

"약속한 형식대로 주고받는가"만 자동으로 검사하는 테스트.

효과 서비스가 4개면 연결 지점이 여럿입니다. 계약 테스트가 없으면 통합 단계에서야 어긋남이 발견되고, 그때가 가장 비쌉니다.

페이로드 / 헤더Payload / Header

실제 내용물 / 그 내용물에 붙는 꼬리표(인증 토큰, 형식, 요청 ID 등).

실무 인증 토큰과 요청 추적 ID는 헤더에 실립니다. 장애 분석 때 이 요청 ID가 있어야 4개 서비스의 로그를 이어 볼 수 있습니다.

스키마Schema

데이터를 어떤 표에 어떤 칸으로 담을지 정한 설계도.

한 사용자가 AGE_25_34와 AGE_35_44 양쪽에 들어가면, 그 사람의 노출 1회가 리포트에서 2회로 집계됩니다. 세그먼트별 노출 합계가 전체 노출 수를 넘습니다. 광고주에게 보내는 리포트가 산술적으로 틀리는 것이고, 이건 정산 분쟁입니다.

빠지면 무슨 일이 벌어지나

어느 칸에도 안 들어가는 사용자는 1단계·2단계 타게팅에서 전부 탈락해 항상 3단계 기본 광고만 받습니다. Fill Rate는 유지되지만 단가가 바닥이고, 그 사용자로는 영원히 돈을 못 법니다.

엔지니어링 관점 — MECE를 어떻게 강제하는가
  • 타입으로 — enum이면 목록 밖의 값이 애초에 들어갈 수 없습니다 (상호 배타의 절반).
  • 제약으로 — 세 칸 모두 NOT NULL이면 비어 있을 수 없습니다 (전체 포괄의 절반).
  • 키로 — user_profiles에서 사용자 ID가 유일하면 한 사람이 두 세그먼트를 못 갖습니다.
  • 분류 함수로 — 나이·소득·주소를 넣으면 항상 정확히 하나를 돌려주는 함수. 경계값(정확히 25세, 정확히 50,000달러)에서 어느 쪽인지가 코드에 박혀야 합니다.
이 설계의 실제 구멍 — 데이터가 없는 사용자. MECE는 세 값이 항상 알려져 있을 때만 성립합니다. 그런데 현실에서 신규 방문자는 나이도 소득도 모릅니다. §6.2의 enum에는 UNKNOWN 값이 없습니다. 따라서 셋 중 하나라도 모르면 세그먼트를 만들 수 없고, MECE는 그 자리에서 깨집니다. 게다가 소득 4칸 중 IncomeSegment의 단위가 무엇인지(원인지 달러인지)도 문서에 없습니다 — 값은 0~50000으로만 적혀 있습니다.

"가장 높은 입찰가"는 "가장 많은 수익"이 아니다

REQ-FUNC-005의 제목은 수익 최적화인데 인수 기준은 "가장 높은 입찰가를 선택"입니다. 이 두 문장은 같은 뜻이 아닙니다. 이것이 이 SRS에서 가장 값비싼 결함입니다.

숫자로 보는 반례

캠페인과금 방식입찰가예상 CTR노출 1,000회 기대 수익 (eCPM)
ACPC1,000원 / 클릭0.2%1,000 × 0.002 × 1,000 = 2,000원
BCPM3,000원 / 1,000노출—3,000원
입찰가만 비교하면 A(1,000)보다 B(3,000)가 커 보이지만, 단위가 다르므로 이 비교 자체가 성립하지 않습니다. eCPM으로 환산해야 비로소 비교 가능하고, 이 예에서는 B가 실제로 유리합니다. 만약 A의 예상 CTR이 0.5%였다면 A의 eCPM은 5,000원이 되어 결과가 뒤집힙니다. "가장 높은 입찰가"라고 구현하면 CPC와 CPM 캠페인이 섞이는 순간부터 계속 손해를 봅니다.
엔지니어링 — 예상 CTR은 어디서 오나

eCPM을 계산하려면 이 사용자가 이 광고를 클릭할 확률의 추정치가 필요합니다. 정석은 과거 성과 데이터로 예측 모델을 만드는 것이지만, 그건 MVP 범위 밖입니다.

MVP의 현실적 절충안은 과거 실적 기반의 단순 평균입니다 — "이 캠페인 × 이 세그먼트"의 최근 CTR을 쓰고, 데이터가 없으면 캠페인 전체 평균, 그것도 없으면 기본값. 이 계단식 규칙만 정해도 "입찰가 비교"보다 훨씬 낫습니다.

지우지 않고 지운 척하기 — 그 이유와 청구서

REQ-FUNC-007은 어떤 삭제 요청도 실제로 데이터를 지우지 않는다고 규정합니다. deleted_at 칸에 시각을 적을 뿐입니다. 광고 플랫폼에서 이건 거의 표준 관행인데, 이유와 대가가 분명합니다.

왜 이렇게 하는가 — 세 가지 이유
  • 과거 리포트가 깨지지 않게. 캠페인을 지웠다고 지난달 성과 리포트가 빈칸이 되면 안 됩니다. 광고비는 이미 청구됐습니다.
  • 실수 복구. 광고주가 잘못 지운 캠페인을 되살릴 수 있습니다.
  • 감사와 분쟁 대응. "언제 누가 무엇을 지웠는가"가 남습니다. 정산 분쟁에서 이 기록이 증거가 됩니다.
엔지니어링 — 지불해야 하는 청구서
  • 모든 조회에 필터가 붙습니다. WHERE deleted_at IS NULL을 한 군데라도 빠뜨리면 지운 캠페인이 다시 노출됩니다. 소프트 삭제 도입 후 가장 흔한 버그가 정확히 이것입니다.
  • 유일성 제약이 깨집니다. "캠페인 이름은 중복 불가"인데 지운 캠페인이 이름을 계속 점유하면, 같은 이름을 다시 못 씁니다.
  • 표가 계속 커집니다. 지워도 줄지 않으니 색인이 무거워지고 조회가 느려집니다 — 100ms 목표와 정면으로 부딪힙니다.
  • 연쇄 삭제가 애매해집니다. 캠페인을 지우면 그 아래 크리에이티브·타게팅 설정도 같이 지워진 것으로 봐야 합니까?
실무의 정답은 "한 곳에서 강제하기". 필터를 애플리케이션 곳곳에 흩어놓으면 반드시 빠뜨립니다. 데이터 접근 계층 한 곳에서 자동으로 붙이거나, deleted_at IS NULL이 이미 적용된 뷰(view)를 만들어 개발자가 원본 표를 직접 보지 못하게 합니다. 설계 검토에서 "이 필터를 어디서 강제합니까?"가 정확한 질문입니다.

소프트 삭제는 "지우지 않는다"는 정책입니다. 반면 개인정보 보호 법령은 목적 달성 시 지체 없이 파기를 요구하고, 정보 주체는 삭제를 요구할 권리를 갖습니다. 그런데 이 시스템은 user_profiles에 연령·소득·지역·행동 이력을 보관합니다. 소득 구간은 특히 민감하게 다뤄지는 정보입니다.

100밀리초를 일곱 조각으로 나누기

REQ-NF-001은 "p95 100ms 이하"만 말합니다. 그런데 그 100ms를 누가 얼마씩 쓰는지가 정해지지 않으면, 네 팀이 각자 개발한 뒤 통합 단계에서야 초과를 발견합니다. 그때는 되돌릴 시간이 없습니다.

성능 예산 배분표 — 이런 표를 만들어 각 팀에 배정하십시오

클라이언트 ↔ 게이트웨이20ms
인증 · 라우팅5ms
Audience 프로필 조회15ms
Campaign 후보 조회25ms
정렬 · eCPM 계산 · 선택10ms

이 숫자는 예시입니다. 실제 값은 개발팀이 정해야 합니다. 중요한 것은 숫자 자체가 아니라 "각 팀이 자기 몫을 알고 그 안에서 개발한다"는 사실입니다. 그리고 이벤트 기록(Tracking)은 비동기로 빠지므로 이 예산에 포함되지 않습니다 — 그것이 이 설계에서 가장 중요한 최적화입니다.

p95의 진짜 의미

"95% 시나리오에서 100ms 이하"는 100건 중 5건은 100ms를 넘어도 합격이라는 뜻입니다. 평균이 아닙니다. 평균 40ms인 시스템도 p95가 300ms일 수 있습니다 — 소수의 아주 느린 요청이 평균에 묻히기 때문입니다.

그리고 3단계 폴백까지 간 요청은 구조적으로 느립니다. 3단계까지 간 요청이 전체의 5%를 넘으면 p95가 곧바로 위태로워집니다 — 즉 REQ-FUNC-004와 REQ-NF-001은 서로 얽혀 있습니다.

"100ms"라는 숫자의 출처를 물으십시오

출처 열에 "업계 가이드라인"이라고만 적혀 있습니다. 돌아가서 물어볼 사람이 없다는 뜻입니다.

100ms는 실시간 경매(RTB)에서 거래소가 입찰 응답을 기다려주는 관행적 시간에 가깝습니다. 그런데 이 MVP는 RTB가 아닙니다(§7.1이 향후로 미룸). 즉 남의 제약을 근거 없이 가져왔을 가능성이 있습니다. 100ms와 200ms는 필요한 인프라 비용이 크게 다르므로, 이 한 줄이 예산 규모를 바꿉니다.

측정 가능하게 다시 쓰기 — 확정해야 할 5개 항목

  1. 측정 구간 — 게이트웨이 진입부터 응답 최종 바이트 전송까지 (클라이언트 네트워크 포함 여부 명시)
  2. 측정 대상 — POST /api/v1/ads/request만인지, 전체 API 평균인지
  3. 부하 조건 — 몇 RPS에서 측정한 값인지 (10 RPS와 1,000 RPS의 p95는 전혀 다름)
  4. 데이터 조건 — 캠페인 몇 건, 사용자 몇 명이 들어 있는 상태인지
  5. 캐시 상태 — 캐시가 데워진 상태인지 빈 상태인지

얻는 것
  • 독립 배포. 타게팅 기준 수정이 캠페인 관리 화면을 멈추지 않습니다.

치르는 것
  • 모든 화살표가 네트워크입니다. 같은 프로그램 안의 함수 호출은 0.001ms, 네트워크 호출은 1~10ms. 그리고 실패할 수 있습니다.
  • 서비스 간 조인이 불가능합니다. "자동차 태그를 가진 사용자에게 맞는 캠페인"을 한 번의 질의로 못 찾습니다. 두 번 부르고 애플리케이션에서 맞춰야 합니다.

기록이 곧 매출이다 — 이벤트 파이프라인

광고 사업에서 기록되지 않은 노출은 존재하지 않은 노출입니다. 청구할 수 없기 때문입니다. 반대로 두 번 기록된 클릭은 두 번 청구되고, 그건 광고주와의 신뢰 문제가 됩니다.

노출IMPRESSION ─ CTR ─→ 클릭CLICK ─ CVR ─→ 전환CONVERSION → 어트리뷰션공을 누구에게 → 정산청구서
Last-click 어트리뷰션이란

사용자가 A 광고를 보고, B 광고를 클릭하고, 나중에 C 광고를 클릭한 뒤 구매했다면 — C가 전환의 공을 전부 가져갑니다. A와 B는 0입니다.

계산이 단순해서 MVP에 적합하지만, 인지 단계에서 기여한 광고를 전혀 인정하지 않는 편향이 있습니다. §6.3 규칙 6이 "향후 Multi-touch로 확장 가능"이라 적은 이유입니다.

중복과 유실 — 파이프라인의 두 적

중복. 클라이언트가 클릭 이벤트를 보냈는데 응답이 네트워크에서 사라지면, 클라이언트는 실패로 알고 재전송합니다. 서버는 같은 클릭을 두 번 기록합니다. 해법은 이벤트마다 고유 ID를 부여하고 서버가 중복을 버리는 것(멱등성)입니다.

유실. /tracking/events가 "일괄 수집"이라는 것은 보내기 전 잠시 쌓아둔다는 뜻입니다. 그 사이에 브라우저가 닫히면 그 이벤트들은 사라집니다. 정산에 쓰는 노출·클릭은 유실 허용치를 정해야 합니다.

"정보가 없는 사용자는 어떤 세그먼트로 분류합니까? 전체 사용자 중 그 비중은 얼마로 예상합니까?"
중 09

어트리뷰션 윈도우가 정의되지 않았다  §6.3 규칙 6

Last-click을 쓴다고만 하고, 클릭 후 며칠 안의 전환까지 인정하는지가 없습니다. 업계 관행은 7일 또는 30일이며, 이 숫자가 광고주 정산액을 직접 바꿉니다. 계약 전에 확정돼야 합니다.

"어트리뷰션 윈도우는 며칠입니까? 계약서에 명시됩니까?"
중 10

이벤트 중복 제거 규칙이 없다  REQ-FUNC-008

네트워크 재전송으로 같은 클릭이 두 번 기록되면 두 번 청구됩니다. 일괄 수집 방식이라 반대로 유실도 가능합니다. 정산에 쓰는 숫자이므로 두 방향 모두 규칙이 필요합니다.

"이벤트에 고유 ID를 부여해 중복을 제거합니까? 허용 가능한 유실률은 얼마입니까?"
중 11

"실시간"이 두 곳에서 다르게 쓰였다  REQ-FUNC-008 vs §6.3 규칙 8

한쪽은 "실시간 기록", 다른 쪽은 "5분 단위 갱신"입니다. 이벤트 기록과 지표 집계는 다른 일인데 문서가 구분하지 않아, 광고주가 대시보드에서 방금 클릭을 못 찾을 때 설명할 근거가 없습니다.

"대시보드 숫자는 최대 몇 분 전 값입니까? 화면에 그 지연을 표시합니까? 정산 확정 시점은 언제입니까?"
경 12

정의가 빠진 값 3건  REQ-FUNC-006 · 001 · §6.2

① REQ-FUNC-006의 "정의된 슬롯 수"가 문서 어디에도 없습니다. ② 세그먼트 형식이 §1.3(AGE_25_34_MID_URBAN)과 §4.1(AGE_XX_INCOME_XX_GEOGRAPHY_XX)에서 다릅니다. ③ IncomeSegment의 금액 단위(원·달러)가 없습니다.

"설계 단계에서 이 세 값을 채워 문서에 반영해 주십시오."
경 13

광고 운영의 표준 장치 3종이 빠져 있다

페이싱이 없어 예산이 오전에 소진되고, 프리퀀시 캡이 없어 같은 사용자에게 같은 광고가 반복되며, 부정 클릭 필터가 없어 봇 트래픽이 CTR과 정산을 오염시킵니다. MVP에서 제외하는 것은 합리적 선택일 수 있으나, 지금은 제외한다는 기록조차 없습니다.

"이 3건을 §7 향후 개선 목록에 명시적으로 넣고, 광고주 계약서에도 현재 미지원임을 반영합니까?"
이 목록을 쓰는 법. 그대로 회의 안건으로 올리십시오. 각 항목에 담당자와 확정 기한만 붙이면 그것이 곧 착수 전 체크리스트가 됩니다. 13건 전부를 해결하고 시작할 필요는 없습니다 — 치명 5건에 대해 "누가 언제까지 답을 준다"가 정해지는 것이 목표입니다.

SRS를 일정으로 바꾸는 절차

요구사항 13개는 아직 일정이 아닙니다. 작업으로 쪼개고, 의존 관계를 그리고, 가장 긴 경로를 찾아야 일정이 됩니다.

의존 관계 — 이 프로젝트의 실제 순서

enum · 스키마 확정모든 작업의 전제 → API 계약 확정병렬화의 열쇠 → Audience / Campaign병렬 가능 → Ad Serving둘 다 있어야 시작 → Tracking일부 병렬 가능 → 성능 튜닝통합 후에만 가능

붉은 테두리가 크리티컬 패스 — 여기서 하루 늦으면 프로젝트 전체가 하루 늦습니다. Ad Serving Engine은 앞의 두 서비스가 없으면 통합 테스트를 할 수 없습니다. 그래서 Audience와 Campaign의 가짜 응답 서버를 먼저 만드는 것이 일정상 매우 유리합니다 — L2 졸업 과제(API 계약서)가 그대로 여기에 쓰입니다.

마일스톤 초안 — 8주 기준

M00–1주치명 5건 확정 · enum/스키마 · API 계약 서명
M11–3주Audience + Campaign 병렬 · 부하 테스트 환경 구축 병행
M23–5주Ad Serving 3단계 폴백 · eCPM 선택 · 예산 차감
M35–6주Tracking · 집계 · 대시보드 API
M46–8주통합 · 성능 튜닝 · 보안 점검 · 인수 시연

M1에 부하 테스트 환경을 넣은 것이 이 표의 핵심입니다. 성능 문제는 마지막 주에 발견하면 고칠 수 없습니다. M1부터 매주 측정해 추이를 봐야 어느 커밋에서 느려졌는지 알 수 있습니다.

일정을 지키는 세 가지 장치
  • 계약 우선 개발. API 형식을 먼저 확정하고 가짜 서버를 띄우면 네 팀이 진짜로 병렬이 됩니다. 이게 없으면 병렬은 착시입니다.
  • 스파이크. 모르는 것에 견적을 매기지 마십시오. "100ms 가능성 조사, 3일"처럼 시간을 정해두고 조사만 하는 작업을 넣으십시오.
  • 수직 절단. 서비스별로 완성해 마지막에 합치지 말고, 가장 단순한 광고 한 건이 끝까지 흐르는 경로를 2주차에 먼저 관통시키십시오. 통합 위험이 초반에 드러납니다.
견적을 받을 때 던지는 세 질문
  • "이 작업이 늦어지면 무엇이 같이 늦습니까?" — 의존 관계가 드러납니다.
  • "지금 가장 모르는 것이 무엇입니까?" — 스파이크 대상이 나옵니다.
  • "이 견적에 테스트와 문서화가 포함돼 있습니까?" — 대개 빠져 있고, 그만큼이 나중에 초과분이 됩니다.

PART 7 · 실전

"다 됐어요"를 검증하는 절차

완성도 검토의 핵심은 화면을 보는 것이 아니라 숫자와 실패 케이스를 보는 것입니다. 잘 되는 경로는 누구나 시연할 수 있습니다. 검수는 안 되는 경우를 확인하는 자리입니다.

DoD — 모든 조항에 공통 적용하는 완료 정의

  1. 인수 기준의 모든 문장을 재현 가능한 절차로 통과했다
  2. 정상 경로뿐 아니라 예외 경로 테스트가 있고 통과했다
  3. 추적성 매트릭스의 테스트 케이스 ID가 실제 테스트와 연결돼 있다
  4. 소프트 삭제 필터(REQ-FUNC-007)가 새로 만든 모든 조회에 적용됐다
  5. 인증·인가가 적용됐고 타 광고주 데이터 접근이 차단됨을 확인했다
  6. 성능 측정값이 배분된 예산 안에 있다
  7. 로그와 지표가 남아 운영 중 확인이 가능하다
  8. SRS 원문이 구현과 어긋난 부분이 있으면 문서를 갱신했다

8번을 빼면 문서는 3개월 안에 쓸모없어집니다. 문서 갱신을 DoD에 넣는 것이 PM의 방어선입니다.

시연을 요구하는 표준 문장 6개

01"실패하는 경우를 보여주세요."잘 되는 화면 대신 예외 경로. 3단계에서도 후보가 없을 때, 예산이 소진됐을 때, 프로필이 없을 때.
02"숫자를 보여주세요.""빨라졌어요" 대신 p95 몇 ms. "잘 나와요" 대신 CTR 몇 %.
03"제 계정으로 해보겠습니다."개발자 환경에서만 되는 경우가 흔합니다. 다른 사람 손에서 되는지가 진짜 시험입니다.
04"같은 요청을 두 번 보내면요?"멱등성 확인. 클릭 중복 집계는 그대로 정산 오류입니다.
05"데이터베이스를 직접 보여주세요."소프트 삭제가 실제로 행을 남겼는지는 화면으로 확인할 수 없습니다.
06"동시에 100건 보내면요?"예산 초과 집행(치명 02)의 유일한 확인 방법입니다.

이 SRS가 만들려는 것

사용자를 36칸의 인구통계 격자에 정확히 하나씩 넣고, 그 위에 겹쳐도 되는 행동 태그를 붙인다. 광고 요청이 오면 정밀 → 인구통계 → 기본의 세 단계로 내려가며 반드시 채우고, 그중 가장 수익이 큰 것을 고른다. 일어난 일은 전부 기록하되 아무것도 지우지 않는다. 이 전부를 100밀리초 안에, 초당 천 번 한다.

PM으로서 기억할 다섯 문장
  • 불합격을 낼 수 없는 인수 기준은 합격도 낼 수 없다.
  • 비기능 요구사항은 마지막 주에 터진다 — 부하 테스트는 1주차에 시작한다.
  • API 계약이 확정되기 전의 병렬 개발은 착시다.
  • "됐어요"는 실패 케이스와 숫자로만 확인한다.
  • 모르는 것에 견적을 매기지 말고 스파이크를 배정한다.
엔지니어링으로 기억할 다섯 문장
  • MECE는 데이터가 항상 존재할 때만 성립한다.
  • 서비스를 쪼개면 화살표마다 지연과 실패가 생긴다.
  • p95는 평균이 아니다 — 평균은 느린 요청을 숨긴다.
  • 같은 요청이 두 번 오는 것은 버그가 아니라 네트워크의 기본 성질이다.
  • 지우지 않기로 했다면 조회마다 걸러내는 책임이 생긴다.
