## 1. 이 문서에만 있는 최우선 제약 — Phase 2 조건부 착수

일반적인 병합 원칙보다 먼저 짚어야 할 것이 있다.

원문 §5는 **Phase 2를 조건부로 규정**한다. 세 조건(WEBD 60% · 가맹 LOI 30곳 · 매장 제안 참여 의향 실측)이
**모두** 충족될 때만 착수하며, 미충족 시 **`FR-037`~`FR-048` · `FR-074`~`FR-076` · `UX-009`~`UX-011` 총 24건이 v0.2로 이월**된다.

> **따라서 Phase 1 태스크와 Phase 2 태스크를 한 이슈로 묶으면 안 된다.**
> 묶는 순간 그 이슈는 이월도 착수도 불가능한 상태가 된다. **이월 단위가 깨진다.**

이것이 이 문서의 축약에서 **1순위 제약**이다. 아래 모든 병합은 이 선을 넘지 않는다.

## 5. 축약 과정에서 발견한 원문 결함 3건

### 결함 1 — `UX-014`의 Phase 의존성 모순

| 항목 | 값 |
| --- | --- |
| `UX-014` 빈 화면 금지 상태 설계 | **Phase 1** (§5 배분) |
| 선행 태스크 | `UX-003`(Phase 1) · **`UX-009`(Phase 2)** |

**Phase 2가 이월되면 `UX-014`는 Phase 1에서 착수할 수 없다.**
그런데 빈 화면 금지는 폴백 전환(Phase 1 기능)에도 필요하다.

**해소안** — `UX-014`를 두 조각으로 나눈다.
① 폴백 전환 시 빈 화면 방지 → Phase 1 (`UX-B`에 흡수 가능)
② 제안 0건 Top-3 회귀 → Phase 2 (`UX-G`에 흡수)

**본 계획에서는 `UX-F`로 단독 유지**하고 이 결함을 지적만 했다. 분할 여부는 승인 사항이다.

### 결함 2 — `UX-001`에 대응 요구사항이 없음 (원문이 이미 † 로 명시)

원문 각주가 *"착수 전 PM 승인 대상"* 이라 밝혔다. `UX-A`로 병합하면서도 이 사실은 그대로 남는다.
`UX-013`(성능 가이드)은 `REQ-NF-006` 근거가 있으므로, **병합 후 `UX-A`는 근거 있는 태스크가 된다** — 부수 효과로 † 문제가 완화된다.

### 결함 3 — `Evidence` Epic 이름이 두 곳에 중복

원문 Epic 분포를 보면 `Evidence Service`(7건, §3.3)와 `Evidence`(6건, §3.9 Client 내부)가 별개로 존재한다.
후자는 실제로 **Client Epic의 화면 태스크**인데 Epic 열에 `Evidence`로 적혀 집계가 갈린다.
축약 시 `EVD-*`(백엔드)와 `CLI-C`(프론트엔드)로 분리해 해소된다.

| 2 | `MCH-A` = FR-037~040 (4건, H) | **병합** — 전부 Phase 2, 한 덩어리 | FR-037+038 / FR-039+040 분리 | 51건 |
| 3 | `PRV-A` = FR-058·059·062·063 (4건) | **병합** — 전부 서버 측 개인정보 | FR-058+063(수명주기) / FR-059+062(접근통제) | 51건 |
| 4 | `CLI-C` = FR-068~071 (4건, H) | **병합** — 한 화면 파생 UI | FR-068+069 / FR-070+071 분리 | 51건 |

**네 건을 모두 분리하면 54건**으로, 여전히 "50 내외" 범위 안이다.
**1번은 특히 신중할 만하다** — `FR-001`은 후행 12건이 대기하는 최우선 태스크이고, 원칙 4는 단독 유지를 지시한다.
병합을 권하는 이유는 `PriceProfile`·`Attribute.scope`가 **스키마의 일부이지 별개 기능이 아니기** 때문이다.
