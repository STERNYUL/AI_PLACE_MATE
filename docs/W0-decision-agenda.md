**대상 문서:** SRS-ADTECH-MVP-001 v1.0 (`reference/SRS-example-AD-Core-Platform.md`)

## 왜 착수 전인가

이 5건은 답이 없으면 **Acceptance Criteria의 Then 절에 판정 수치를 넣을 수 없는** 항목이다.
그 상태로 이슈를 발행하면 개발은 착수되지만 **완료 판정이 불가능**해지고, 검수 시점에 분쟁이 된다.

또한 SRS §4.1·§4.2의 13개 조항은 현재 상태가 **전부 `Proposed`** 다.
승인 게이트를 통과하지 않은 문서이므로, 이 안건서의 처리는 **승인 회의와 함께 진행**하는 것이 효율적이다.

## D-01 · 광고주 간 데이터 격리 규칙

### 결정이 필요한 질문
1. REQ-NF-004의 **"기본 인증"** 은 구체적으로 무엇인가?
2. 광고주 A가 광고주 B의 `campaignId`를 알아냈을 때, 그 성과를 조회할 수 있는가?

### 지금 문서 상태
> REQ-NF-004 인수 기준 — *"모든 API에 기본 인증이 요구되어야 하며, 비인가 접근은 차단되어야 한다"*

제목에는 **인가**가 있으나 인수 기준은 인증만 규정한다.
"기본 인증"이 HTTP Basic 인증이라는 특정 기술인지, "최소한의 인증"이라는 일반적 표현인지 해석이 갈린다.
그런데 §6.1에는 `GET /api/v1/campaigns/{campaignId}/performance` 처럼 **경로에 식별자가 노출되는 조회 API가 3개** 있다.

### 선택지

| 안 | 내용 | 영향 |
| --- | --- | --- |
| **A** | HTTP Basic 인증 + 자원 소유자 검증 없음 | 구현 최소. **다른 광고주 데이터가 ID 추측으로 노출됨** — 다중 광고주 서비스에서 채택 불가 |
| **B** | 토큰 기반 인증 + 요청 주체의 소유 자원만 접근 허용 | 표준적. 캠페인·성과 조회 시 소유자 대조 1회 추가 (성능 예산 영향 미미) |
| **C** | B + 역할 구분 (광고주 / 내부 운영자 / 시스템 간 호출) | §2의 8개 역할과 정합. 구현량 증가 |

### 권고
**B를 최소선으로, C를 목표로.** §3이 외부 시스템으로 Advertiser Portal을 두고 있어 광고주가 직접 접근하는 구조이며,
§2에 서비스 운영자·CRM 매니저 등 내부 역할이 별도로 존재하므로 결국 C가 필요해진다.
MVP에서 B로 출발하되 **역할 구분을 넣을 자리를 설계에 미리 확보**하는 방식을 권한다.

### 확정 시 문서 반영
- REQ-NF-004 인수 기준에 인가 문장 추가
- §5 추적성 매트릭스에 REQ-NF-004 행 신설 (담당 모듈 · `TC-NF-004`)

## D-02 · 예산 초과 집행 방지

### 결정이 필요한 질문
1. 예산 잔액 확인과 차감을 **원자적으로** 처리하는가?
2. 초과 집행이 발생했을 때 그 비용은 누가 부담하는가?

### 지금 문서 상태
> §6.3 규칙 7 — *"일일 예산 상한을 적용하고, 예산 소진 시 캠페인을 자동 일시중지해야 한다"*
> REQ-FUNC-005 인수 기준 — *"…예산 제약을 준수해야 한다"*

동시성에 대한 언급이 없다. REQ-NF-002가 요구하는 **초당 1,000건** 환경에서,
잔액이 얼마 남지 않은 캠페인에 요청이 몰리면 모든 요청이 "예산 있음"을 읽고 통과한다.
이것은 예외 상황이 아니라 **매일 발생하는 정상 동작의 결과**다.

### 선택지

| 안 | 내용 | 영향 |
| --- | --- | --- |
| **A** | 조회 후 차감 (현행 문서 그대로) | 초과 집행 발생. 초과분은 청구 불가 → 그대로 손실 |
| **B** | 예산 행 비관적 잠금 | 초과 0. 그러나 인기 캠페인의 예산 행이 **병목**이 되어 100ms 목표와 충돌 |
| **C** | 원자적 차감 (조건부 갱신) + 실패 시 다음 후보로 | 초과 0. 잠금 없음. 구현 난도 중간. **가장 일반적인 해법** |
| **D** | C + 예산을 슬롯 단위로 미리 예약 | 초과 0 + 페이싱 기반 확보. 구현량 최대 |

### 권고
**C.** 다만 이 결정은 **허용 오차를 함께 정해야** 실효가 있다.
"일일 상한의 0%를 초과할 수 없음"과 "1% 이내 초과 허용"은 구현 난도가 크게 다르다.
사업 측에서 **허용 초과율**을 숫자로 지정해 주기를 요청한다.

### 함께 확정할 것
- 입찰가 **동점** 시 선택 규칙 (현재 미정 → 구현에 따라 먼저 등록된 캠페인이 항상 승리)
- 일일 예산을 시간대에 걸쳐 배분하는 **페이싱** 도입 여부 (현재 미지원 → 오전 소진 발생)

## D-03 · 캠페인 선택 기준 — 입찰가인가 eCPM인가

### 결정이 필요한 질문
REQ-FUNC-005의 선택 기준을 **"가장 높은 입찰가"** 에서 **"eCPM 환산값이 가장 높은 캠페인"** 으로 변경하는 데 동의하는가?

### 지금 문서 상태
> REQ-FUNC-005 제목 — **수익 최적화** 및 캠페인 선택
> 동 인수 기준 — *"타게팅 조건 내에서 **가장 높은 입찰가**를 선택하고…"*
> §5 구현 클래스 — `YieldOptimizer` (수익 최적화기)

제목과 클래스명은 **수익 최적화**를 가리키는데 인수 기준은 **입찰가 비교**를 규정한다.
그런데 §6.2 `BiddingStrategy`는 CPC · CPM · CPA 세 방식을 정의한다. **세 방식은 단위가 달라 입찰가를 직접 비교할 수 없다.**

### 숫자로 본 반례

| 캠페인 | 과금 | 입찰가 | 예상 CTR | 노출 1,000회 기대 수익 |
| --- | --- | --- | --- | --- |
| A | CPC | 1,000원 / 클릭 | 0.2% | 1,000 × 0.002 × 1,000 = **2,000원** |
| B | CPM | 3,000원 / 1,000노출 | — | **3,000원** |

입찰가만 보면 비교가 성립하지 않는다. eCPM으로 환산하면 이 예에서는 B가 유리하고,
A의 예상 CTR이 0.5%였다면 결과가 뒤집힌다. **현행 문장대로 구현하면 두 과금 방식이 섞이는 순간부터 지속적으로 손실이 발생한다.**

### 선택지

| 안 | 내용 | 영향 |
| --- | --- | --- |
| **A** | 현행 유지 — 최고 입찰가 | 구현 최소. 과금 방식 혼재 시 손실 지속 |
| **B** | MVP에서 과금 방식을 **CPM 하나로 제한** | 입찰가 비교가 성립. `BiddingStrategy` enum의 나머지 두 값은 향후로 이관 |
| **C** | eCPM 환산 비교 + 예상 CTR은 **계단식 규칙** | 정답에 가까움. 예상 CTR 추정 규칙이 추가로 필요 |

### 권고
**C.** 예상 CTR은 예측 모델 없이도 계단식 규칙으로 충분히 처리된다 —
*① 해당 캠페인 × 해당 세그먼트의 최근 실적 CTR → ② 없으면 캠페인 전체 평균 → ③ 없으면 지정된 기본값.*
이 규칙만 정해도 입찰가 비교보다 낫다.

**B도 합리적 선택이다.** MVP 범위를 줄여 확실하게 출시하는 판단이라면 B를 택하고,
§7 향후 개선 사항에 "다중 과금 방식 지원 + eCPM 환산"을 명시적으로 기록하는 편이 낫다.
**어느 쪽이든 지금 문서 상태(제목은 수익 최적화, 기준은 입찰가)를 그대로 두는 것만은 피해야 한다.**

### 확정 시 문서 반영
- REQ-FUNC-005 인수 기준 재작성 + 동점 규칙 명시
- (B 선택 시) §6.2 `BiddingStrategy` 범위 축소 및 §7 이관 기록

## D-04 · 개인정보 수집 근거와 파기 경로

### 결정이 필요한 질문
1. 연령 · **소득 구간** · 지역 데이터는 어디서 수집하며, 이용자 동의 근거는 무엇인가?
2. 이용자가 삭제를 요구하면 어떻게 처리하는가?

### 지금 문서 상태
> §6.2 `IncomeSegment` — LOW / MID / HIGH (금액 구간 정의, **통화 단위 미표기**)
> §6.4 `user_profiles`, `user_behavioral_signals`
> §6.3 규칙 5 — *"물리 삭제를 수행하지 않고 **항상** deleted_at 타임스탬프를 사용해야 한다"*
> §3 외부 시스템 — User Profile Service

시스템은 연령 · 소득 · 지역 · 행동 이력을 보관하지만, **수집 출처와 동의 절차를 규정한 요구사항이 없다.**
소득 구간은 특히 민감하게 취급되는 정보다.

동시에 §6.3 규칙 5는 예외 없이 "항상" 물리 삭제를 금지한다.
**이대로 구현하면 이용자의 삭제 요구에 응할 수 없는 시스템이 된다.**

### 선택지

| 안 | 내용 | 영향 |
| --- | --- | --- |
| **A** | 현행 유지 | 법령 준수 불가. 채택 불가 |
| **B** | 개인정보에 한해 물리 삭제 예외 경로 신설 | 규칙 5에 예외 조항 추가. 과거 리포트에서 해당 사용자 기여분 처리 방식을 함께 정해야 함 |
| **C** | B + 비식별화 — 프로필은 삭제하고 **집계 결과는 유지** | 리포트 무결성과 파기 의무를 동시에 만족. 권고안 |
| **D** | 소득 데이터를 MVP 범위에서 제외 | MECE 격자가 36칸 → 12칸으로 축소. 리스크 최소, 타게팅 정밀도 감소 |

### 권고
**C.** 다만 이 안건은 기술 결정이 아니라 **법무 검토 사항**이다.
사업관리 및 계약 담당자를 통해 법무 확인을 받은 뒤 결정하기를 요청한다.
**D도 진지하게 검토할 만하다** — 소득 데이터의 수집 근거를 확보하지 못한다면 D가 유일한 합법적 경로다.

### 함께 확정할 것
- 소프트 삭제 데이터의 **보존 기간**, 경과 후 물리 삭제 여부
- `IncomeSegment` 금액 구간의 **통화 단위**
- 연령 · 소득 · 지역 중 하나라도 알 수 없는 사용자의 분류 대상 (`UNKNOWN` 값 부재 → MECE 붕괴)

## D-05 · 100ms의 근거와 측정 정의

### 결정이 필요한 질문
1. 이 100ms는 어디서 온 숫자인가?
2. **어디부터 어디까지**, **몇 RPS 부하에서**, **어떤 데이터 상태로** 측정하는가?

### 지금 문서 상태
> REQ-NF-001 인수 기준 — *"모바일/데스크톱 API의 E2E 응답 시간이 차원 조회를 포함하여 95% 시나리오에서 100ms 이하여야 한다"*
> 동 출처 — **"업계 가이드라인"**

"95% 시나리오"는 p95를 뜻하므로 지표 자체는 적절하다. 문제는 두 가지다.

**출처가 "업계 가이드라인"이어서 되물을 대상이 없다.** 100ms는 실시간 경매에서 거래소가 입찰 응답을 기다려주는
관행적 시간에 가까운데, §7.1이 RTB를 향후로 미뤄 **이 MVP는 실시간 경매가 아니다.**
남의 제약을 근거 없이 가져왔을 가능성이 있다.

**측정 조건이 없어 합격 판정이 불가능하다.** 사용자 브라우저부터인지 게이트웨이부터인지에 따라 수십 ms가 달라지고,
10 RPS에서의 p95와 1,000 RPS에서의 p95는 전혀 다른 숫자다.

### 확정해야 하는 5개 항목

| 항목 | 예시 |
| --- | --- |
| 측정 구간 | 게이트웨이 진입 ~ 응답 최종 바이트 전송 (클라이언트 네트워크 제외) |
| 측정 대상 | `POST /api/v1/ads/request` 단독 (전체 API 평균이 아님) |
| 부하 조건 | 1,000 RPS 지속 부하 (REQ-NF-002와 묶어 검증) |
| 데이터 조건 | 캠페인 N건 · 사용자 M명이 적재된 상태 |
| 캐시 상태 | 웜 캐시 / 콜드 캐시 중 어느 쪽 기준인가 |

### 선택지

| 안 | 내용 | 영향 |
| --- | --- | --- |
| **A** | 100ms 유지 + 측정 조건 확정 | 목표 난도 높음. 인프라 비용 증가 |
| **B** | 목표를 완화(예: 200ms) + 측정 조건 확정 | 비용 절감. 근거를 사업 측이 수용해야 함 |
| **C** | 스파이크로 실측 후 결정 | **권고안** |

### 권고
**C.** 지금 A와 B를 표결로 정하는 것은 근거 없는 선택이다.
**3일 타임박스 스파이크**를 배정해 최소 구성으로 프로토타입을 만들고 실측한 뒤,
그 숫자를 근거로 목표를 확정하는 편이 훨씬 안전하다.
이 스파이크는 `NF-003`(부하 테스트 환경)의 착수를 앞당기는 효과도 있다.

### 확정 시 문서 반영
- REQ-NF-001 인수 기준에 측정 5개 항목 명시
- REQ-NF-002 인수 기준에 *"유지해야 할 응답 시간"* 추가 (현재 부재 — 느려도 통과 가능)
- 100ms를 구간별로 배분한 **성능 예산 배분표** 작성 후 각 팀에 배정
