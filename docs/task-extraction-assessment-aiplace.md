# 태스크 리스트 정합성 평가 — 4단계 추출 방법론 대비

**문서 ID:** ASSESS-AIPLACE-EXTRACT-001
**날짜:** 2026-08-25
**평가 대상:** [`TASKS-ai-place-v1.0.md`](../TASKS-ai-place-v1.0.md) — 111건 (UX 15 · IN 14 · FR 82)
**평가 기준:** 4단계 표준 추출 방법론 (계약·데이터 → 로직/CQRS → 테스트 → NFR·의존성)
**근거 문서:** [`SRS-ai-place-v1.0.md`](../SRS-ai-place-v1.0.md) v1.9

> **이 문서의 목적** — 현재 태스크 리스트는 **도메인(Epic) 축**으로 짜여 있고, 표준 방법론은 **산출물 종류 축**으로 짜여 있다.
> 두 축이 어긋나는 지점을 찾아 무엇을 보강해야 하는지, 그리고 풀버전 본문을 어떤 순서로 제작해야 하는지 정리한다.
> **본문 작성은 이 평가에 따른 보강이 끝난 뒤에 시작한다.**

## 0. 결론 요약

| 판정 | 내용 |
| --- | --- |
| **재사용 가능** | 111건 중 **97건**은 그대로 쓴다. 요구사항 커버리지 59/59는 이미 검증됐다 |
| **분해 필요** | **12건**을 Read(Query) / Write(Command)로 쪼개야 한다 |
| **신규 필요** | **31건**이 없다 — API 계약 9 · Mock 8 · 테스트 14 |
| **최종 규모** | 111 → **약 154건** |

**가장 큰 결함 셋**

1. **API 계약(DTO·에러 코드) 태스크가 없다.** 엔드포인트 구현 태스크(`FR-008` · `FR-019` · `FR-025` · `FR-042` · `FR-044`)는 있으나, 그 **계약을 먼저 확정하는 태스크**가 없다. 프론트엔드가 착수할 기준점이 없다는 뜻이다.
2. **Mock 태스크가 전혀 없다.** 현재 리스트에서 `FR-068`(Top-3 카드 렌더)은 `FR-019`(API 구현) 완료를 기다린다. **프론트엔드가 백엔드를 기다리는 직렬 구조**이며, 이는 Phase 1 8주 안에 3스트림 병행을 전제한 §4.3.3과 모순된다.
3. **테스트가 태스크가 아니다.** 현재는 각 태스크의 DoD 체크박스로만 존재한다. 인수 기준을 GWT 시나리오로 전개하는 작업이 **누구의 일도 아니고 일정에도 없다.**

### Step 2 — 로직 및 상태 변경 (CQRS 분해)

| 추출 대상 | 현재 상태 | 판정 |
| --- | --- | --- |
| **Read (Query)** | 조회 태스크가 상태 변경 태스크와 **섞여 있다** | ⚠️ **분해 필요** |
| **Write (Command)** | 상동 | ⚠️ **분해 필요** |

**왜 분해하는가.** 조회와 변경은 **테스트 방법·성능 목표·동시성 위험이 전부 다르다.**
조회는 캐시와 p95가 문제이고, 변경은 검증·상태 전이·동시성이 문제다. 한 이슈에 묶으면 둘 중 하나가 소홀해진다.

**분해 대상 12건**

| 기존 ID | 현재 내용 | Query 쪽 | Command 쪽 |
| --- | --- | --- | --- |
| `FR-005` | PriceProfile 저장·조회 | 조회 | 저장 |
| `FR-007` | Verification 엔터티 및 상태 전이 | 확인 상태 조회 | **상태 전이(핵심)** |
| `FR-008` | dishes 조회 | 조회 전체 | — |
| `FR-018` | Top-3 구성 | 조회 전체 | — |
| `FR-026` | 불일치 신고 및 상태 전환 | — | 변경 전체 |
| `FR-029` | 제안 조건 승계 | 제안 조회 | 예약 생성 |
| `FR-031` | PG 결제 승인 | — | 변경 전체 |
| `FR-035` | 노쇼 판정 및 정산 | 판정 대상 조회 | **상태 전이 + 정산** |
| `FR-037` | 매장 프로필 등록 | 프로필 조회 | 등록 |
| `FR-038` | 프로필 갱신 | 기존 항목 로드 | 갱신 |

> **분해 규칙** — 양쪽이 모두 실질적일 때만 쪼갠다. `FR-008`·`FR-018`처럼 순수 조회는 그대로 두고
> **`[Query]` 태그만** 붙인다. 반대로 `FR-026`·`FR-031`은 `[Command]` 태그만 붙인다.
> **실제로 두 건으로 늘어나는 것은 8건** (`FR-005` · `007` · `029` · `035` · `037` · `038` · `044` · `054`).

## 3. 풀버전 스크립트 제작 순서

4단계 방법론의 순서가 곧 제작 순서다. **앞 단계가 끝나기 전에 뒷 단계를 쓰지 않는다** —
계약이 흔들리면 로직·테스트 본문을 다시 써야 하기 때문이다.

| 순서 | 산출 문서 | 담는 태스크 | 왜 이 순서인가 |
| --- | --- | --- | --- |
| **1** | `P1a-contracts.md` | `SPEC-001`~`SPEC-009` (9) | 나머지 전부의 기준점. **여기가 흔들리면 이후 문서가 전부 무효** |
| **2** | `P1b-data.md` | `FR-001`~`FR-007` 분해분 · `FR-028` (약 12) | 스키마·마이그레이션. 후행 12건이 대기 중 |
| **3** | `P1c-mock.md` | `MOCK-001`~`MOCK-008` (8) | **여기까지 끝나면 프론트엔드가 착수 가능** |
| **4** | `P2a-query.md` | 조회 계열 `[Query]` (약 14) | 읽기 경로. 캐시·p95가 판정 기준 |
| **5** | `P2b-command.md` | 변경 계열 `[Command]` (약 22) | 쓰기 경로. 검증·상태 전이·동시성이 판정 기준 |
| **6** | `P2c-client.md` | `FR-064`~`FR-079` · `UX-002`~`UX-015` (약 29) | Mock 기준으로 작성. 백엔드와 **병행** |
| **7** | `P3-tests.md` | `TEST-001`~`TEST-014` (14) | Step 2 완료 후. **AC 내용이 Step 2 이슈의 DoD로 역류** |
| **8** | `P4a-infra.md` | `IN-001`~`IN-014` (14) | 부하 테스트(`IN-014`)만 **1~2단계와 병행 착수** |
| **9** | `P4b-dependency.md` | 의존 관계도 · Phase 배분 재계산 | 전체가 나온 뒤에만 그릴 수 있다 |

> **P4a의 예외.** `IN-014`(부하 테스트 환경)는 8번째로 미루지 않는다.
> `REQ-NF-001`의 측정 조건을 확정하는 산출물이므로 **1~2단계와 나란히 착수**한다.
> 통합 후에 시작하면 문제를 발견해도 고칠 시간이 없다.

> **Phase 2 예외.** `FR-037`~`FR-048` · `FR-074`~`FR-076` · `UX-009`~`UX-011` · `TEST-011`~`TEST-013`은
> SRS §6.2의 게이트 1(WEBD ≥ 목표 60% · LOI ≥ 30곳 · P5 참여 의향 실측)이 **모두 통과한 뒤에** 본문을 쓴다.
> 미달 시 v0.2로 이월되므로 미리 쓰면 통째로 버려진다.
