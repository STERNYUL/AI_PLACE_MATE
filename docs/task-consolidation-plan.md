# 태스크 축약 계획 — 99건 → 46건

**대상:** `TASKS-adtech-mvp-v1.0.md` v1.1 (99 태스크 · 93 이슈)
**목표:** 50건 내외
**결과:** **46건** (54% 감축) — 원장 태스크 ID는 전량 보존
**성격:** 분석·계획서. **실행 전 승인 대기.**

---

## 1. 축약의 원칙 — 무엇을 묶고 무엇을 지키는가

무리한 병합은 태스크를 줄이는 대신 **관리 불가능한 덩어리**를 만든다. 네 가지 원칙으로 경계를 그었다.

| # | 원칙 | 위반 시 |
| --- | --- | --- |
| **1** | **같은 도메인 + 같은 담당 조직** | 한 이슈에 두 팀이 걸려 책임이 흐려진다 |
| **2** | **합계 복잡도가 H를 넘지 않는다** — `L+L` · `L+M` 우선, `H+H` 금지 | 한 스프린트에 안 끝나는 이슈가 된다 |
| **3** | **`Blocks`가 5개 이상인 태스크는 단독 유지** | 크리티컬 패스가 커진 이슈에 묶여 지연이 증폭된다 |
| **4** | **차단 안건이 다른 태스크는 묶지 않는다** | **막힌 것과 안 막힌 것을 묶으면 둘 다 막힌다** |

**4번이 가장 중요하다.** 예를 들어 `NF-003`(부하 테스트 환경 · 차단 없음 · 조기 착수 대상)을
`NF-002`(100ms 최적화 · **D-05 차단**)와 묶으면, D-05 회신을 기다리는 동안 부하 환경 구축도 멈춘다.
**성능 문제를 조기에 발견하려던 목적 자체가 사라진다.**

### 병합 금지 8건 — 단독 유지

| 태스크 | 근거 |
| --- | --- |
| `SPEC-000` 공통 규약 | Blocks 11 (원칙 3) |
| `SPEC-007` 광고 요청 계약 | 크리티컬 패스 + 성능 예산 배분표 산출 |
| `FR-021` 타게팅 조건 | Blocks 5 · 조건 결합 규칙의 단일 진실 원천 |
| **`FR-035` 예산 원자적 차감** | **D-02의 핵심. 다른 태스크에 묶으면 동시성 요건이 희석된다** |
| `FR-049` User Profile Service | D-04 차단 · 외부 계약 성격 |
| `NF-001` API Gateway | 조기 착수 · Blocks 4 |
| `NF-003` 부하 테스트 환경 | 조기 착수 · **원칙 4** (D-05 차단과 분리) |
| `QA-008` 지표·어트리뷰션 검증 | H · 정산 직결 |

## 2. 도메인별 축약안

### 2-1. 계약 `SPEC` — 11 → 6

| 신규 | 병합 대상 | 근거 |
| --- | --- | --- |
| `SPEC-A` | SPEC-000 | **단독** — Blocks 11 |
| `SPEC-B` | SPEC-001 + 002 + 003 | Audience 3종. 동일 DTO 계열·동일 담당 |
| `SPEC-C` | SPEC-004 + 005 | Campaign 생성·타게팅. 동일 담당 |
| `SPEC-D` | SPEC-006 + 010 | **성과 조회 2종 — 스키마 통일이 목적이므로 한 이슈가 오히려 정확하다** |
| `SPEC-E` | SPEC-007 | **단독** — 크리티컬 패스 |
| `SPEC-F` | SPEC-008 + 009 | 이벤트 2종. **멱등키 규약을 공유해야 하므로 분리하면 어긋난다** |

`SPEC-D`와 `SPEC-F`는 감축이 아니라 **정합성 개선**이다. 원래 분리했던 것이 오히려 위험했다.

### 2-2. 모킹 `MOCK` — 4 → 2

| 신규 | 병합 | 근거 |
| --- | --- | --- |
| `MOCK-A` | MOCK-001 + 002 | 소비자가 동일 (Ad Serving 팀) |
| `MOCK-B` | MOCK-003 + 004 | 소비자가 동일 (클라이언트·UI 팀) |

**소비자 기준 병합**이라 인수 조건이 자연스럽게 하나가 된다.

### 2-3. 기반 `DB` — 11 → 4

| 신규 | 병합 (원장 ID) | 복잡도 |
| --- | --- | --- |
| `DB-A` | FR-001~005 (enum 11종 + 확장 패턴) | L×4 + M = M |
| `DB-B` | FR-006 + 007 (Audience + Campaign 스키마) | M + M = H |
| `DB-C` | FR-008 + 009 (이벤트 + 집계 뷰) | H + H → **H 유지** (원래 함께 설계해야 함) |
| `DB-D` | FR-010 + 011 (소프트 삭제) | M |

`DB-B`는 원칙 2의 경계선이다. **D-04가 FR-006만 차단하므로 원칙 4 위반 우려가 있으나**,
스키마는 함께 설계해야 색인·외래키 정합이 맞는다. **차단 시 FR-007 부분만 선행하는 조건**을 이슈에 명시한다.

### 2-4. Audience — 7 → 3

| 신규 | 병합 | 근거 |
| --- | --- | --- |
| `AUD-A` | FR-012 + 013 + 014 | 분류기 + 포맷 + MECE 제약 = **한 덩어리**. 따로 완성될 수 없다 |
| `AUD-B` | FR-015 | 단독 (H · 멀티태그) |
| `AUD-C` | FR-016 + 017 + 018 | API 3종 |

`AUD-C`는 Query 1건(FR-016)과 Command 2건(017·018)이 섞인다. **CQRS 절단을 일부 포기하는 지점**이며,
API 계층은 얇으므로 실무상 문제가 적다. 대신 이슈 안에서 체크박스로 구분한다.

### 2-5. Campaign — 11 → 4

| 신규 | 병합 | 근거 |
| --- | --- | --- |
| `CMP-A` | FR-019a + 020 + 025 | 쓰기 계열 — CRUD · 상태 전이 · 크리에이티브 |
| `CMP-B` | FR-021 | **단독** — Blocks 5 |
| `CMP-C` | FR-022 + 023 + 024 | 예산 상한 · 자동 중지 · 입찰 전략 |
| `CMP-D` | FR-019b + 026 + 027 + 028 | 조회 + API 3종 |

`CMP-C`는 D-02·D-03이 동시에 걸린 세 태스크를 묶은 것이라 **원칙 4를 만족**한다(차단 상태가 같다).

### 2-6. Ad Serving — 10 → 5

| 신규 | 병합 | 근거 |
| --- | --- | --- |
| `ADS-A` | FR-029 + 030 + 031 | 3단계 후보 조회. **조건 결합 규칙을 공유하므로 함께 구현해야 해석이 일치한다** |
| `ADS-B` | FR-032 + 033 | 오케스트레이션 + 단계 기록 |
| `ADS-C` | FR-034 + 036 | 선택 + 슬롯 제어 |
| `ADS-D` | **FR-035** | **단독** — 병합 금지 |
| `ADS-E` | FR-037 + 038 | API 2종 |

`ADS-A`가 이 축약안 최대의 개선이다. FR-029·030을 분리했을 때 **같은 결합 규칙을 두 사람이 다르게 해석할 위험**이 있었다.

### 2-9. 인프라 · 보안 — 12 → 6

| 신규 | 병합 | 차단 |
| --- | --- | --- |
| `INF-A` | NF-001 | **단독** — 조기 착수 |
| `INF-B` | NF-003 + 005 | **단독 그룹** — 차단 없음, 조기 착수 (원칙 4) |
| `INF-C` | NF-002 + 004 | D-05 |
| `INF-D` | NF-006 + 007 | — |

`INF-B`가 원칙 4의 모범이다. **차단 없는 두 건만 묶어 조기 착수 가능성을 보존**했다.

### 2-10. 테스트 — 14 → 6

| 신규 | 병합 | AC 준비도 |
| --- | --- | --- |
| `TST-A` | QA-001 + 002 | ⚠️ / 🔴 |
| `TST-B` | QA-003 + 006 + 007 | ⚠️ / 🔴 / ✅ |
| `TST-C` | QA-004 + 005 | ⚠️ / ⚠️ — **H+H이나 동일 도메인** |
| `TST-D` | QA-008 | **단독** — H · 정산 직결 |
| `TST-E` | QA-009 + 010 | **함께 측정하는 것이 정확하다** (응답 시간 × 처리량) |
| `TST-F` | QA-011 + 012 + 013 + 014 + NF-011 | 가용성 · 보안 · enum · §5 갱신 |

`TST-E`는 감축이 아니라 정합성 개선이다. REQ-NF-002에 응답 시간 조건이 없는 결함(부록 D)은
**두 검증을 묶어야 드러난다.**

`TST-C`는 원칙 2를 어기는 유일한 병합(`H+H`)이다. **분리안도 함께 제시한다** — 아래 §4.

### 2-11. 디자인 — 6 → 3

| 신규 | 병합 | 근거 |
| --- | --- | --- |
| `UX-A` | UX-001 + 004 | 배치 정의 + 규격. **둘 다 다른 태스크의 기준값을 산출** |
| `UX-B` | UX-002 + 003 | 모바일 + 데스크톱 레이아웃 |

`UX-A`는 차단이 없어 **즉시 착수 가능** 상태가 유지된다. 그리고 그 산출물이
`ADS-C`(슬롯 수)와 `CMP-A`(소재 규격)의 판정 불가 상태를 해소한다.

| 안 | 결과 |

## 5. 실행 절차 — 승인 후

| 단계 | 작업 | 영향 |
| --- | --- | --- |
| 1 | 원장 v1.2 — 병합 매핑표 추가 (신규 ID ↔ 원장 ID 99개) | 문서 |
| 2 | 이슈 본문 재구성 — 7개 Phase 파일을 46건 기준으로 재편 | 문서 |
| 3 | **기존 이슈 93건 중 47건 Close** — `superseded` 라벨 + 통합 대상 링크 | **GitHub** |
| 4 | 신규 병합 이슈 생성 후 번호 재매핑 | GitHub |
| 5 | 부록 A 의존 관계도 4종 갱신 | 문서 |
| 6 | 부록 B 커버리지 표 갱신 (역방향 99 → 46 기준) | 문서 |

**3단계에 주의가 필요하다.** GitHub 이슈는 삭제보다 Close가 원칙이고,
**93건을 만든 직후 47건을 닫는 것은 이력상 어수선하다.**

대안 두 가지가 있다.

| 안 | 방식 | 장단 |
| --- | --- | --- |
| **A** | 기존 93건 Close → 신규 46건 생성 | 깔끔한 최종 상태. 이력에 닫힌 이슈 93개 |
| **B** | 병합 대상 이슈를 **하위 체크박스로 흡수**하고 Close, 대표 이슈는 유지·수정 | 이슈 번호 절반 보존. 작업 복잡 |

**B를 권고한다.** 예를 들어 `AUD-A`는 기존 `#33`(C-01 FR-012)의 본문을 수정해
`FR-013`·`FR-014` 체크박스를 흡수하고, `#34`·`#35`를 `#33` 참조와 함께 Close한다.
**크리티컬 패스 이슈 번호(`#1` `#12` `#48` `#55` `#88`)가 그대로 유지되는 것이 실무상 이점이다.**
