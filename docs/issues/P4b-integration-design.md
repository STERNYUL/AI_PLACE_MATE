## 🔗 References
- SRS: **§1.2 범위** ("프로그래매틱 타게팅을 위한 웹/모바일 분리 API 연동") · **§3 클라이언트 애플리케이션**
- 계약: SPEC-007 · 선행: FR-037 · **MOCK-003으로 선행 착수 가능**

## ⚠️ "분리"의 의미가 정의되지 않았다

§3은 두 개의 주소를 제시한다.

```
모바일 웹 앱   https://api.adtech.example.com/mobile
데스크톱 웹 앱 https://api.adtech.example.com/desktop
```

**그런데 두 경로의 응답이 무엇이 다른지는 어디에도 없다.** 세 가지 해석이 가능하다.

| 해석 | 함의 |
| --- | --- |
| **A** 경로만 다르고 동작 동일 | 분리의 의미가 지표 분리뿐. 가장 단순 |
| **B** 위치(`AdPosition`)가 다름 | 사이드바 2종은 모바일에 부적합 — 자연스러운 해석 |
| **C** 크리에이티브 규격이 다름 | 화면 크기가 다르므로 필요. UX-004와 연결 |

**B와 C를 함께 적용하는 것을 권고한다.** `MAIN_LEFT_SIDEBAR`·`MAIN_RIGHT_SIDEBAR`를
모바일에서 요청하면 어떻게 되는지가 정의되어야 한다.

- **Then**: **(미정)** — 태그와 실제 접속 기기가 다를 때 어느 쪽을 따르는가

# [Integration] N-03 (FR-048): 클라이언트 이벤트 전송 모듈

**labels**: `integration, frontend, backend, priority:high`

## 🎯 Summary
- **Task ID**: FR-048 · **Must / M**
- **기능명**: 클라이언트 측 노출·클릭 이벤트 전송
- **목적**: **기록되지 않은 노출은 청구할 수 없다.** 이 모듈이 매출의 입구다.

## 🔗 References
- SRS: §3 시스템 맥락 · REQ-FUNC-008
- 계약: SPEC-008 (클릭) · SPEC-009 (일괄) · 선행: FR-038 · FR-040 · MOCK-003·004
- 학습 해설: `SRS-READER.html` 21장 (중복과 유실)

## ⚠️ 이 모듈이 유실과 중복 양쪽의 발생 지점이다

| 문제 | 발생 경로 | 대응 |
| --- | --- | --- |
| **유실** | 일괄 전송 대기 중 브라우저 종료 | 페이지 이탈 시 강제 전송 · 배치 크기·주기 조정 |
| **중복** | 응답 유실 → 클라이언트 재전송 | **멱등키(`eventId`) 클라이언트 생성** (SPEC-008) |
| 노출 판정 오류 | 광고가 화면 밖인데 노출로 기록 | 뷰어빌리티 — **SRS에 없음** |

**세 번째가 SRS의 공백이다.** "노출"이 응답한 것인지 화면에 보인 것인지 정의되지 않았다.
응답 기준이면 구현이 쉽지만 실제로 보이지 않은 광고도 청구하게 되어 광고주 신뢰 문제가 된다.

## ✅ Task Breakdown
- [ ] 노출 이벤트 감지 및 전송
- [ ] 클릭 이벤트 전송 (SPEC-008 — 즉시)
- [ ] **멱등키 클라이언트 생성**
- [ ] 일괄 전송 버퍼 (SPEC-009 — 배치)
- [ ] **페이지 이탈 시 강제 전송** — 유실 방어
- [ ] 전송 실패 재시도 정책
- [ ] `requestId` 연결 유지
- [ ] **노출 판정 기준 확정 (미정)**

## 🧪 Acceptance Criteria

**Scenario 1: 노출 전송**
- **Given**: 광고가 렌더링됨
- **When**: 노출 이벤트가 발생함
- **Then**: `requestId`와 함께 전송되고 집계된다

**Scenario 2: 클릭 즉시 전송**
- **Given**: 사용자가 광고를 클릭함
- **When**: 페이지 이동이 시작됨
- **Then**: 클릭 이벤트가 **이동 전에 전송된다** (유실 방지)

**Scenario 3: 멱등키**
- **Given**: 응답이 유실되어 클라이언트가 재전송함
- **When**: 서버가 수신함
- **Then**: 동일 `eventId`로 중복이 차단된다

**Scenario 4: 페이지 이탈 시 버퍼 전송**
- **Given**: 버퍼에 노출 이벤트 5건이 대기 중
- **When**: 사용자가 탭을 닫음
- **Then**: 버퍼가 전송된다 (또는 허용 유실률 내로 관리된다)

**Scenario 5: 전송 실패 재시도**
- **Given**: 네트워크 오류
- **When**: 전송이 실패함
- **Then**: 재시도하고, 재시도로 인한 중복은 멱등키로 차단된다

**Scenario 6: 노출 판정**
- **Given**: 광고가 응답됐으나 사용자가 스크롤하지 않아 화면 밖에 있음
- **When**: 노출 판정을 수행함
- **Then**: **(미정)** — 노출로 기록하는가

# [Integration] N-04 (FR-049): User Profile Service 연동

**labels**: `integration, backend, priority:high, blocked-d04`

## 🎯 Summary
- **Task ID**: FR-049 · **Must / H**
- **기능명**: 외부 User Profile Service에서 프로필 원천 데이터 수신
- **목적**: **인구통계 데이터의 유일한 출처다.** 이것이 없으면 36칸 격자에 넣을 데이터가 없다.
- **차단**: **D-04** (개인정보 수집 근거)

## 🔗 References
- SRS: **§3 외부 시스템 — "User Profile Service"** (이름 외 정보 없음)
- 선행: DB-002 · 확정 안건 **D-04**
- 원장: 부록 D 치명 04

## ⚠️ SRS가 이름만 제시한 시스템이다

§3은 `User Profile Service`를 외부 시스템으로 나열하지만 **그 외 정보가 전무하다.**

| 미정의 | 왜 필요한가 |
| --- | --- |
| 연동 방식 (API 호출 · 배치 · 이벤트 스트림) | 설계가 완전히 달라진다 |
| 제공 데이터 항목 | 나이·소득·주소를 실제로 주는가 |
| 갱신 주기 | 실시간인가 일 배치인가 |
| **개인정보 제공 근거** | **D-04의 핵심** |
| 장애 시 동작 | 이 시스템이 죽으면 세그먼트 갱신이 멈춘다 |

**그리고 이것이 E-09(행동 태그 호출 주체)와 연결된다.** §7.2가 동적 태깅을 향후로 미뤘으므로
MVP에서 태그를 채울 현실적 후보는 이 서비스의 배치 전송이다.

## ✅ Task Breakdown
- [ ] **연동 방식 확정** (호출 · 배치 · 스트림)
- [ ] 제공 데이터 항목 확인 — 나이·소득·주소 제공 여부
- [ ] **개인정보 제공 근거 확인 — D-04**
- [ ] 데이터 매핑 — 원천 값 → §6.2 enum (FR-012 분류기 입력)
- [ ] 갱신 주기 및 증분 처리
- [ ] **장애 시 동작** — 세그먼트 갱신 중단 시 기존 데이터 유지
- [ ] **행동 태그 제공 가능성 확인 (E-09)**
- [ ] 수신 데이터 마스킹 (NF-012)

## 🧪 Acceptance Criteria

**Scenario 1: 프로필 수신 및 분류**
- **Given**: 외부 서비스에서 사용자 데이터를 수신함
- **When**: 분류기(FR-012)에 전달함
- **Then**: 36칸 중 하나로 배정되어 저장된다

**Scenario 2: 데이터 항목 누락**
- **Given**: 소득 정보가 없는 사용자 데이터
- **When**: 수신·분류를 시도함
- **Then**: **(미정)** — `UNKNOWN` 부재로 저장 불가. **이 시나리오가 실제로는 대다수일 수 있다**

**Scenario 3: 외부 서비스 장애**
- **Given**: User Profile Service가 응답하지 않음
- **When**: 갱신이 시도됨
- **Then**: 기존 프로파일이 유지되고 광고 서빙은 계속된다

**Scenario 4: 갱신 주기**
- **Given**: 외부에서 사용자 정보가 변경됨
