# [Infra] I-01 (NF-001): API Gateway 구축 및 성능 계측

**labels**: `infra, gateway, priority:high, early-start`

## 🎯 Summary
- **Task ID**: NF-001 · **Must / H**
- **기능명**: API Gateway + `PerformanceMonitor` 계측
- **목적**: 모든 요청의 정문을 세우고, **REQ-NF-001을 측정할 수 있는 지점을 만든다.** 측정 없이는 성능 요구사항이 무의미하다.

## 🔗 References
- SRS: REQ-NF-001 · **§5 추적성 매트릭스 — 모듈 `API Gateway` · 클래스 `PerformanceMonitor`**
- 계약: SPEC-000 (인증 헤더 · 요청 추적 ID)
- 선행: FR-037 (계측 대상)
- 학습 해설: `SRS-READER.html` 9장 (API 게이트웨이) · 19장

## ⚠️ 문서 내 불일치를 먼저 정리할 것

**§5는 API Gateway를 모듈로 지정하지만, §3 시스템 맥락에는 API Gateway가 없다.**
§3은 클라이언트 2종 · 내부 마이크로서비스 4개 · 외부 시스템 3개만 나열한다.
아키텍처 구성 요소가 추적성 매트릭스에만 등장하는 상태이므로, **§3 갱신을 함께 요청할 것.**

## ✅ Task Breakdown
- [ ] 게이트웨이 배치 및 라우팅 구성 (4개 서비스)
- [ ] **인증 검증 지점 설치** (NF-008이 여기에 붙는다)
- [ ] `X-Request-Id` 발급·전파 (SPEC-000 규약)
- [ ] `PerformanceMonitor` — 요청별 소요 시간 계측
- [ ] **구간별 분해 계측** — SPEC-007 배분표와 대조 가능하게
- [ ] p50·p95·p99 집계 및 대시보드
- [ ] 속도 제한 (SPEC-000 제안)
- [ ] 모바일·데스크톱 경로 분리 (FR-046·047)

### 계측 설계 — 이것이 이 태스크의 핵심 산출물

REQ-NF-001을 검증하려면 **어디부터 어디까지를 재는지**가 코드에 박혀야 한다.

| 계측 지점 | 측정 대상 |
| --- | --- |
| 게이트웨이 진입 | 측정 시작 (D-05 확정 시 기준점) |
| 각 백엔드 호출 전·후 | Audience · Campaign · Ad Serving 구간 |
| 응답 최종 바이트 전송 | 측정 종료 |

**구간별 분해가 없으면 "느리다"는 사실만 알고 어디가 느린지는 모른다.**
성능 예산 배분표(SPEC-007)와 대조할 수 있어야 각 팀이 자기 몫을 확인한다.

## 🧪 Acceptance Criteria

**Scenario 1: 라우팅**
- **Given**: 4개 서비스가 기동된 상태
- **When**: 각 서비스의 엔드포인트를 게이트웨이로 호출함
- **Then**: 올바른 서비스로 전달되고 응답이 반환된다

**Scenario 2: 요청 추적 ID 전파**
- **Given**: `X-Request-Id`가 없는 요청
- **When**: 게이트웨이를 통과함
- **Then**: ID가 생성되어 하위 서비스에 전파되고, **4개 서비스 로그에서 동일 ID로 추적 가능**하다

**Scenario 3: 구간별 계측**
- **Given**: `/ads/request` 호출
- **When**: 응답이 완료됨
- **Then**: 게이트웨이·Audience·Campaign·Ad Serving 각 구간의 소요 시간이 기록된다

**Scenario 4: p95 집계**
- **Given**: 요청 1,000건
- **When**: 지표를 조회함
- **Then**: **평균이 아니라 p50·p95·p99**가 제공된다

**Scenario 5: 속도 제한**
- **Given**: 클라이언트별 상한이 설정됨
- **When**: 상한을 초과해 호출함
- **Then**: `429`가 반환되고 다른 클라이언트는 영향받지 않는다

**Scenario 6: 경로 분리**
- **Given**: `/mobile`과 `/desktop` 경로
- **When**: 각각 호출함
- **Then**: 구분되어 라우팅되고 지표도 분리 집계된다

## ⚙️ Constraints
- 게이트웨이 자체가 **단일 장애점이 되지 않아야 한다** (NF-006과 연계)
- 인증 검증 비용이 성능 예산에 포함된다 (배분표의 게이트웨이 구간)
- 설정은 코드로 관리 — 수동 설정은 재현 불가

# [Infra] I-02 (NF-003): 부하 테스트 환경 구축

**labels**: `infra, performance, priority:high, early-start`

## 🎯 Summary
- **Task ID**: NF-003 · **Must / H**
- **기능명**: 차원 쿼리를 포함한 부하 테스트 프로그램
- **목적**: **성능 문제를 조기에 발견한다.** 이 태스크를 마지막에 하면 문제를 발견해도 고칠 시간이 없다.

## 🔗 References
- SRS: **REQ-NF-001 검증 방식 — "차원 쿼리를 포함한 부하 테스트 프로그램"**
- 선행: NF-001
- 원장: 부록 A-3 Track 5 (조기 착수 권고)
- 학습 해설: `SRS-READER.html` 12장 (부하·스트레스·소크·스파이크)

## ⚠️ 왜 조기 착수인가

성능은 **누적된 결과**다. 매주 조금씩 느려진 것을 마지막 주에 발견하면
어느 변경이 원인인지 찾을 수 없고, 되돌릴 수도 없다.

**M1부터 매주 측정해 추이를 보는 것**이 이 태스크의 목적이다. 그러려면 환경이 먼저 있어야 한다.

## ✅ Task Breakdown
- [ ] 부하 도구 선정 (k6 · JMeter · Gatling 등)
- [ ] **운영급 테스트 데이터 생성** — 캠페인·사용자·이벤트 볼륨
- [ ] `/ads/request` 시나리오 작성 — **차원 쿼리 포함** (REQ-NF-001 명시)
- [ ] 단계별(1·2·3) 요청 비율 조절 가능하게 구성
- [ ] p50·p95·p99 리포트 자동 생성
- [ ] **주간 추이 리포트** 자동화
- [ ] CI 연동 (성능 회귀 감지)

### 테스트 데이터 볼륨 (제안)

| 데이터 | 볼륨 | 근거 |
| --- | --- | --- |
| 사용자 프로파일 | 100만 | 36칸 격자에 충분히 분산 |
| 행동 태그 | 500만 | 사용자당 평균 5개 |
| 캠페인 | 10만 (`ACTIVE` 5,000) | 후보 조회 색인 검증 |
| 이벤트 | 1억 (30일분) | 파티셔닝·집계 성능 검증 |

**데이터가 적으면 아무 구현이나 빠르다.** 개발자 노트북의 캠페인 5건으로는 색인 필요성이 드러나지 않는다.

## 🧪 Acceptance Criteria

**Scenario 1: 부하 실행**
- **Given**: 운영급 데이터가 적재된 스테이징 환경
- **When**: 부하 테스트를 실행함
- **Then**: 지정한 RPS로 요청이 발생하고 p95가 산출된다

**Scenario 2: 차원 쿼리 포함**
- **Given**: 다양한 세그먼트·태그 조합의 사용자
- **When**: 부하를 실행함
- **Then**: 세그먼트 조회와 타게팅 매칭이 실제로 수행된다 (캐시 히트만으로 통과하지 않음)

**Scenario 3: 단계 비율 조절**
- **Given**: 3단계 요청 비율을 20%로 설정함
- **When**: 부하를 실행함
- **Then**: 실제로 그 비율이 나오고 **p95가 어떻게 변하는지** 관찰된다

**Scenario 4: 주간 추이**
- **Given**: 4주간 매주 실행함
- **When**: 추이 리포트를 확인함
- **Then**: 주별 p95 변화가 보이고 회귀 시점을 특정할 수 있다

**Scenario 5: CI 회귀 감지**
- **Given**: 성능이 기준보다 저하된 변경
- **When**: CI가 실행됨
- **Then**: 경고가 발생한다

## ⚙️ Constraints

# [Infra] I-03 (NF-002): E2E 응답시간 최적화

**labels**: `infra, performance, priority:high, blocked-d05`

## 🎯 Summary
- **Task ID**: NF-002 · **Must / H**
- **기능명**: 95% 시나리오 100ms 이하 달성
- **목적**: REQ-NF-001의 목표를 실제로 달성한다.
- **차단**: **D-05** — 목표치와 측정 조건이 확정되지 않았다

## 🔗 References
- SRS: **REQ-NF-001** — *"모바일/데스크톱 API의 E2E 응답 시간이 차원 조회를 포함하여 95% 시나리오에서 100ms 이하"* · 출처 **"업계 가이드라인"**
- 확정 안건: **D-05** (근거·측정 5개 항목)
- 선행: NF-001 · NF-003 · FR-037
- 학습 해설: `SRS-READER.html` 19장

## ⚠️ 목표치의 근거가 없다

출처가 **"업계 가이드라인"** 이어서 되물을 대상이 없다.
100ms는 실시간 경매에서 거래소가 입찰 응답을 기다려주는 관행적 시간에 가까운데,
**§7.1이 RTB를 향후로 미뤄 이 MVP는 실시간 경매가 아니다.**

**100ms와 200ms는 필요한 인프라 비용이 크게 다르다.** D-05는 3일 타임박스 스파이크로 실측한 뒤
그 숫자를 근거로 목표를 확정할 것을 권고했다.

## ✅ Task Breakdown
- [ ] **성능 예산 배분표 적용** (SPEC-007 산출물)
- [ ] 병목 구간 식별 — NF-001 구간별 계측 활용
- [ ] 색인 최적화 (DB-002·003·004의 색인 검증)
- [ ] 캐시 도입 검토 — **예산 잔액은 캐시 금지**
- [ ] 단계별 타임아웃 조정 (FR-032)
- [ ] 서비스 간 호출 최적화 (불필요한 왕복 제거)
- [ ] 응답 직렬화 최적화

### 최적화 우선순위 — 근거 있는 순서

| 순위 | 대상 | 근거 |
| --- | --- | --- |
| 1 | **색인** | 조회 성능의 절반이 여기서 갈린다. 비용 대비 효과 최대 |
| 2 | **불필요한 서비스 간 왕복 제거** | 네트워크 홉 1회가 1~10ms |
| 3 | **단계별 타임아웃** | 3단계 요청의 롱테일을 자른다 |
| 4 | 캐시 | 효과가 크지만 **정합성 위험**이 따라온다 |
| 5 | 직렬화·압축 | 효과 작음 |

**캐시를 4순위에 둔 이유가 있다.** 가장 쉬운 해법으로 보이지만,
예산 잔액처럼 즉시 반영돼야 하는 값을 캐시하면 **초과 집행이 발생한다.**
무엇을 캐시하면 안 되는지 목록을 먼저 만들어야 한다.

## 🧪 Acceptance Criteria

- **Given**: D-05에서 확정된 측정 조건

- **Then**: **(미정)** p95가 확정 목표 이내다

**Scenario 3: 3단계 요청도 예산 내**
- **Given**: 3단계까지 내려가는 요청
- **When**: 측정함
- **Then**: 예산 이내다 (단계별 타임아웃이 동작)

**Scenario 4: 캐시 금지 항목 준수**

- **When**: 즉시 광고를 요청함

**Scenario 5: 색인 사용**

- **When**: 주요 조회의 실행 계획을 확인함

# [Sec] S-02 (NF-009): 인가 처리 — 자원 소유자 검증

**labels**: `security, priority:high, blocked-d01`

## 🎯 Summary
- **Task ID**: NF-009 · **Must / H**
- **기능명**: 비인가 접근 차단 — 광고주 간 데이터 격리
- **목적**: **광고주 A가 광고주 B의 예산과 성과를 볼 수 없게 한다.** 이 시스템에서 가장 중요한 보안 요건이다.
- **차단**: **D-01**

## 🔗 References
- SRS: REQ-NF-004 (제목에 "인가"가 있으나 **인수 기준에는 없음**)
- 확정 안건: **D-01**
- 선행: NF-008 · DB-003 (`advertiser_id` 컬럼)
- 원장: 부록 D 치명 01

## ⚠️ 요구사항에 인가 규칙이 없다

REQ-NF-004의 제목은 *"기본 인증 및 **인가**"* 인데, 인수 기준은 인증만 규정한다.
그런데 §6.1에는 **경로에 식별자가 노출되는 조회 API가 3개** 있다.

```
GET /api/v1/campaigns/{campaignId}/performance
GET /api/v1/tracking/campaigns/{campaignId}/metrics
GET /api/v1/audience/profiles/{userId}
```

**광고주 A가 B의 `campaignId`를 알아냈을 때 성과를 조회할 수 있는지가 지금 문서로는 정해지지 않았다.**
다중 광고주 플랫폼에서 이것은 보안 사고이자 계약 위반이다.

## ✅ Task Breakdown
- [ ] **D-01 확정안 반영** — 안 B(소유자 검증) 또는 안 C(역할 구분)
- [ ] 자원 소유자 판정 규칙 구현 (`advertiser_id` 기준)
- [ ] **캠페인 관련 전 엔드포인트에 적용**
- [ ] 사용자 프로파일 접근 권한 규칙 (내부 서비스만?)
- [ ] 역할 구분 (안 C 선택 시) — 광고주 · 내부 운영자 · 시스템
- [ ] 식별자 추측 방어 — 순차 증가 식별자 회피
- [ ] `403` 응답 (SPEC-000 형식)

### 엔드포인트별 인가 규칙 (제안)

| 엔드포인트 | 접근 가능 주체 |
| --- | --- |
| `POST /campaigns` | 광고주 (자기 것 생성) |
| `PUT /campaigns/{id}/targeting` | **해당 캠페인 소유자만** |
| `GET /campaigns/{id}/performance` | **해당 캠페인 소유자만** + 내부 운영자 |
| `GET /tracking/campaigns/{id}/metrics` | **해당 캠페인 소유자만** + 내부 운영자 |
| `GET /audience/profiles/{userId}` | **내부 서비스만** — 광고주는 개인 프로파일 접근 불가 |
| `POST /audience/...` | 내부 서비스 또는 지정된 연동 주체 |
| `POST /ads/request` | 클라이언트 (매체) |
| `POST /ads/events/click` · `/tracking/events` | 클라이언트 (매체) |

**프로파일 조회를 내부로 제한하는 것이 중요하다.** 광고주가 개인의 연령·소득·지역·관심사를

- **Then**: 평문으로 저장되지 않는다

**Scenario 3: 로그 개인정보 점검**

- **When**: 개인정보 패턴을 검색함
- **Then**: 소득·지역·연령이 평문으로 발견되지 않는다

**Scenario 4: 오류 메시지 누설**
- **Given**: 존재하지 않는 자원과 타인의 자원
- **When**: 각각 조회함
- **Then**: **응답이 구분되지 않는다** (존재 여부 누설 없음)

**Scenario 5: 조치 추적**
- **Given**: 감사에서 발견된 항목

## ⚠️ 왜 이 태스크가 신설되었는가

원장 v1.0에는 마스킹 태스크가 없었다. NF-008~010은 인증·인가·감사만 다루고,
**개인정보가 로그에 남는 문제를 아무도 담당하지 않았다.**

이 시스템은 연령 · **소득 구간** · 지역 · 행동 이력을 다루며, 소득은 특히 민감하게 취급되는 정보다.
그런데 **SRS에는 수집 근거도, 파기 경로도, 로깅 정책도 없다** (부록 D 치명 04).

### 마스킹 대상 (제안 — D-04 확정 후 조정)

| 필드 | 마스킹 수준 | 근거 |
| --- | --- | --- |
| `annualIncome` (원시 소득액) | **완전 제거** | 가장 민감. SPEC-002 안 A에서 요청 본문에 실림 |
| `incomeSegment` (LOW/MID/HIGH) | 부분 (내부 분석용 유지 검토) | 구간화되어 있어 원시값보다 덜 민감 |
| `age` (원시 나이) | 완전 제거 | — |
| `ageSegment` | 유지 | 구간값 |
| `region` (원시 주소) | **완전 제거** | 위치 정보 |
| `geographySegment` | 유지 | URBAN/SUBURBAN/RURAL — 식별력 낮음 |
| `userId` | 가명화 또는 해시 | 연결 추적은 필요하나 원본 노출 금지 |
| 행동 태그 | 유지 (검토) | 관심사 정보 — 조합 시 식별 가능성 검토 |

**원시값과 구간값을 구분한 것이 이 표의 핵심이다.**
`annualIncome: 72000`은 개인을 좁히지만 `incomeSegment: MID`는 3분의 1 집단을 가리킨다.
**원시값은 제거하고 구간값은 남기는 것이 운영성과 보호의 균형점**이다 — 단 D-04 회신에 따라 조정.

## 🧪 Acceptance Criteria

**Scenario 1: 요청 본문 마스킹**
- **Given**: `annualIncome`이 담긴 세그먼트 갱신 요청
- **When**: 요청이 처리되고 로그가 기록됨
- **Then**: 로그에 그 값이 평문으로 남지 않는다

**Scenario 2: 응답 마스킹**
- **Given**: 프로파일 조회 응답
- **When**: 응답 로깅이 발생함
- **Then**: 소득·지역 값이 마스킹된다

**Scenario 3: 오류 스택 트레이스**
- **Given**: 개인정보를 담은 객체 처리 중 예외 발생
- **When**: 스택 트레이스가 기록됨
- **Then**: 예외 메시지에 개인정보가 실리지 않는다

- **Given**: 4개 서비스를 거치는 요청
- **When**: 추적 데이터를 확인함
- **Then**: 태그·속성에 개인정보가 없다

**Scenario 5: 대시보드**
- **Given**: 모니터링 대시보드
- **When**: 요청 상세를 조회함
- **Then**: 개인정보가 노출되지 않는다

**Scenario 6: 누락 검출**
- **Given**: 운영 로그 표본
- **When**: 개인정보 패턴 검색을 실행함
- **Then**: 발견 0건이며, 발견 시 알림이 발생한다

## ⚙️ Constraints
