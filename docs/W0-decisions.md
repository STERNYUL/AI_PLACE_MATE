| 항목 | 결정 |
| --- | --- |
| 인증 방식 | **Bearer 토큰** (OAuth 2.0 Client Credentials). 광고주별 `client_id`/`client_secret` 발급 |
| 토큰 수명 | 액세스 토큰 1시간 · 갱신 토큰 30일 |
| 인가 기준 | `campaigns.advertiser_id` 와 토큰 주체의 `advertiser_id` 대조 |
| 역할 | `advertiser` · `operator` · `service` 3종. **MVP는 `advertiser`·`service`만 발급**, `operator`는 스키마 자리만 확보 |
| **타인 자원 응답** | **`404 Not Found`** — `403`이 아니다 |

## `403`이 아니라 `404`인 이유 — 앞서 쓴 것을 정정한다

이슈 본문(`#7` `#31` `#79` 등)에 `403`으로 적었다. **그것은 잘못된 설계다.**

```
403 Forbidden  → "그 캠페인은 존재하지만 당신 것이 아니다"   ← 존재 여부가 새어나간다
404 Not Found  → "그런 캠페인은 없다"                        ← 아무것도 알려주지 않는다
```

`campaignId`를 순차로 바꿔 조회하면 `403`이 오는 ID는 **실재하는 타인의 캠페인**이다.
광고주 수·캠페인 규모·경쟁사 활동 시점이 그대로 추론된다. **소유하지 않은 자원은 존재하지 않는 것과 동일하게 응답해야 한다.**

`401`(미인증)만 예외다 — 인증 자체가 없으면 자원 판정 전이므로 `401`이 맞다.

| 엔드포인트 | `advertiser` | `service` | `operator`(향후) |
| --- | --- | --- | --- |

| `PUT /campaigns/{id}/targeting` | ○ **소유자만** | ○ | ○ |
| `GET /campaigns/{id}/performance` | ○ **소유자만** | ○ | ○ (기록) |
| `GET /tracking/campaigns/{id}/metrics` | ○ **소유자만** | ○ | ○ (기록) |

직접 조회할 수 있으면 그 자체가 개인정보 유출이다 (D-04와 연결).

## 결정

**안 C(조건부 원자 갱신 + 차순위 재시도)를 채택한다. 허용 초과율은 0%다.**

| 항목 | 결정 |
| --- | --- |
| 차감 방식 | **조건부 원자 갱신** — 갱신문에 상한 조건을 포함 |
| 허용 초과율 | **0%** |
| 차감 실패 시 | 차순위 후보로 재시도. **최대 3회**, 이후 다음 폴백 단계로 |
| 동점 규칙 | ① 일일 소진율 낮은 쪽 → ② 동일하면 `campaign_id` 해시 기반 결정적 선택 |
| 소진 감지 | **차감 직후 동기 확인** (안 A) |
| 페이싱 | **MVP 제외** — §7로 명시 이관 |

## 허용 초과율을 0%로 정한 근거

W0 안건서는 사업 측에 허용 초과율을 요청했다. **그 질문은 철회한다.**

조건부 원자 갱신은 **초과를 구조적으로 0으로 만든다.** 허용치를 두는 것은
"조회 후 차감" 방식을 전제할 때만 의미가 있고, 그 방식은 채택하지 않는다.

```sql
UPDATE campaigns
   SET spent_today = spent_today + :amount,
       spent_total = spent_total + :amount
 WHERE campaign_id = :id
   AND deleted_at IS NULL
   AND status = 'ACTIVE'
   AND spent_date = CURRENT_DATE
   AND spent_today + :amount <= daily_budget_cap      -- 일일 상한
   AND spent_total + :amount <= total_budget;         -- 총예산
-- 갱신된 행이 0건이면 상한 초과 → 차순위 후보로
```

**읽고 나서 쓰는 것이 아니라 조건과 함께 쓰는 것**이 핵심이다.
DB가 원자적으로 판정하므로 동시 요청 100건 중 정확히 통과 가능한 수만 성공한다.
잠금이 없어 초당 1,000건 환경에서도 병목이 되지 않는다.

## 동점 규칙 — 무작위가 아니라 결정적으로

| 안 | 문제 |
| --- | --- |
| 먼저 등록된 캠페인 | **한 광고주가 구조적으로 유리해진다** — 공정성 위반 |
| 매번 무작위 | 재현 불가. 장애 분석과 테스트가 어려워진다 |
| **소진율 낮은 쪽 → 해시** | 예산 소진을 고르게 하고, **같은 입력에 같은 결과**라 테스트 가능 |

소진율을 1순위로 둔 것은 **페이싱의 최소 대체물**이기도 하다.
페이싱을 §7로 미루면서도 예산이 한쪽으로 쏠리는 것을 부분적으로 완화한다.

| 안 | 감지 지연 | 그 사이 초과 노출 |
| --- | --- | --- |
| 1분 주기 배치 | 최대 60초 | **최대 6만 건** (1,000 RPS) |
| **차감 직후 동기** | 0 | 0 |

배치 방식은 §6.3 규칙 7의 *"예산 소진 시 캠페인을 자동 일시중지"* 를 사실상 달성하지 못한다.
동기 확인은 이미 차감 트랜잭션 안에 있으므로 **추가 조회 비용이 없다** — 갱신 결과에서 잔액을 알 수 있다.

# D-03 · 캠페인 선택 기준 — ✅ 결정

## 결정

**안 C(eCPM 환산 비교)를 채택한다. 과금 방식 3종을 모두 유지한다.**

| 항목 | 결정 |
| --- | --- |

| CPA 환산 | `bid_amount × 예상CVR × 1000` |
| 예상 CTR·CVR | **3단 계단식** (아래) |
| 동점 | D-02 규칙 준용 |

## 예상 CTR·CVR — 3단 계단식

예측 모델은 MVP 범위 밖이다. 다음 규칙만으로 입찰가 비교보다 확실히 낫다.

| 단계 | 조건 | 값 |
| --- | --- | --- |
| **1** | 해당 캠페인 × 해당 인구통계 세그먼트의 **최근 7일** 실적, 노출 **1,000건 이상** | 실측 CTR |
| **2** | 해당 캠페인 전체 최근 7일 실적, 노출 **1,000건 이상** | 실측 CTR |
| **3** | 위 둘이 없거나 표본 부족 | **기본값** — CPC 0.30% · CPA 0.05% |

**노출 1,000건 문턱이 중요하다.** 노출 10건에 클릭 1건이면 CTR 10%로 계산되어
그 캠페인이 모든 경매를 독식한다. 표본이 적을 때는 기본값이 안전하다.

기본값 CPC 0.30%는 §6.4 예시 지표(노출 128,400 · 클릭 386 = 0.30%)와 일치시켰다.

## 안 B(CPM 단일화)를 택하지 않은 이유

MVP 범위를 줄이는 선택으로 합리적이지만, **§6.2가 이미 `BiddingStrategy` 3종을 정의**하고
§5가 클래스명을 `YieldOptimizer`로 지정했다. 설계 의도가 eCPM 비교였음이 분명하다.

그리고 계단식 규칙의 구현 비용이 낮다 — **집계 조회 한 번과 곱셈 하나**다.
이미 `FR-042`가 세그먼트별 지표를 산출하므로 그 결과를 재사용하면 된다.

## 성능 고려

예상 CTR 조회가 광고 요청 경로에 들어온다. **캐시가 필요하고, 캐시해도 안전하다.**

| 값 | 캐시 | 근거 |
| --- | --- | --- |
| 예상 CTR·CVR | **가능 — 5분 TTL** | 과거 7일 실적이므로 5분 지연이 무의미 |
| **예산 잔액** | **금지** | 초과 집행 직결 (D-02) |

이 구분을 `INF-C`(NF-002)의 캐시 금지 목록에 명시한다.

## SRS 수정안 — REQ-FUNC-005 인수 기준

> **현행**
> "타게팅 조건 내에서 가장 높은 입찰가를 선택하고, 예산 제약을 준수해야 한다"

> **수정안**
> "타게팅 조건과 예산 잔액을 만족하는 후보 중 **eCPM 환산값이 가장 높은 캠페인**을 선택해야 한다.
> eCPM 환산은 CPM은 입찰가를 그대로, CPC는 `입찰가 × 예상CTR × 1000`, CPA는 `입찰가 × 예상CVR × 1000`으로 계산한다.
> 예상 CTR·CVR은 ① 캠페인×세그먼트 최근 7일 실적(노출 1,000건 이상) ② 캠페인 전체 최근 7일 실적(노출 1,000건 이상)
> ③ 과금 방식별 기본값(CPC 0.30% · CPA 0.05%) 순서로 결정한다.
> 환산값이 동일한 경우 일일 소진율이 낮은 캠페인을 선택한다."

# D-04 · 개인정보 — ⚠️ 부분 결정

### ① `UNKNOWN` 값 추가 — MECE 복구

3개 차원 모두에 `UNKNOWN`을 추가한다. **이것이 없으면 정보를 모르는 사용자를 아예 저장할 수 없고,
그 결과 MECE의 전체 포괄 원칙이 물리적으로 깨진다.**

```java
public enum AgeSegment       { AGE_18_24, AGE_25_34, AGE_35_44, AGE_45_PLUS, UNKNOWN }
public enum IncomeSegment    { LOW, MID, HIGH, UNKNOWN }
public enum GeographySegment { URBAN, SUBURBAN, RURAL, UNKNOWN }
```

**격자가 36칸 → 5×4×4 = 80칸으로 늘어난다.** 대신 어떤 사용자도 분류에서 탈락하지 않는다.
`UNKNOWN`이 포함된 세그먼트는 1단계 정밀 타게팅에서 자연히 제외되고 2·3단계로 흐른다.

### ② 물리 삭제 예외 경로 — §6.3 규칙 5 수정

| 자원 | 삭제 방식 |
| --- | --- |
| 캠페인 · 타게팅 · 크리에이티브 | **논리 삭제만** (현행 유지) |
| **사용자 프로파일 · 행동 신호** | **물리 삭제 허용** (정보주체 요청 시) |
| 이벤트 원본의 `user_id` | **비식별화** — `user_id`를 `NULL` 또는 파기 표식으로 치환 |
| 집계 결과 | **유지** — 개인 식별성 없음 |

**③번이 이 설계의 핵심이다.** 프로파일은 지우고 집계는 남긴다.
`DB-004`의 세그먼트 스냅샷 설계 덕분에 **개인을 지워도 과거 리포트가 유지된다** — 이미 집계에 필요한 값이 이벤트에 복사돼 있다.

### ③ 보존 기간 확정

| 데이터 | 보존 | 근거 |
| --- | --- | --- |
| 이벤트 원본 (`ad_events`) | **90일** | 정산 분쟁 대응 + 파티션 폐기 주기 |
| 집계 결과 (구체화 뷰) | **25개월** | 전년 동월 비교 가능 (24개월 + 1) |
| 사용자 프로파일 | **마지막 활동 후 1년** | 휴면 처리 관행 |
| 논리 삭제된 캠페인 | **5년** | 계약·세무 보존 |

### ④ 프로파일 접근 차단 — D-01과 연결

`GET /audience/profiles/{userId}`를 `advertiser` 역할에서 **완전 차단**한다(D-01 표).
광고주는 개인 프로파일을 조회할 수 없고 **집계된 세그먼트별 지표만** 본다.

## 결정할 수 없는 것 — 법무 판단

**소득 데이터(`IncomeSegment`)의 수집 근거만 남는다.**

SRS는 소득 구간을 정의하지만 **어디서 수집하는지, 어떤 동의를 받는지가 어디에도 없다.**
`User Profile Service`가 제공한다면 그 서비스의 수집 근거와 위탁 계약이 필요하다.
**이것은 기술 판단이 아니라 법률 판단이며 내가 결정할 수 없다.**

### 착수를 막지 않는 우회 — 조건부 설계

법무 회신을 기다리는 동안 개발이 멈추지 않도록 **소득 차원을 설정으로 분리**한다.

```
income_segmentation_enabled = false   ← 기본값
```

| 설정 | 격자 | 동작 |
| --- | --- | --- |
| `false` (기본) | 연령 5 × 지역 4 = **20칸** | 소득 차원을 분류에서 제외. `IncomeSegment`는 항상 `UNKNOWN` |
| `true` (법무 승인 후) | 5 × 4 × 4 = **80칸** | 소득 차원 활성 |

**분류기·스키마·API는 80칸 기준으로 구현하고 설정으로 20칸 운영을 시작한다.**
법무 회신이 늦어져도 `DB-002`·`AUD-A`·`INT-C`가 차단되지 않고, 승인이 나면 설정 하나로 활성된다.

## SRS 수정안 — §6.3 규칙 5

> **현행**
> "물리 삭제를 수행하지 않고 항상 `deleted_at` 타임스탬프를 사용해야 한다"

> **수정안**
> "캠페인·타게팅·크리에이티브 등 사업 자원은 물리 삭제 없이 `deleted_at`으로 논리 삭제한다.
> **단 사용자 프로파일 및 행동 신호는 정보주체의 삭제 요청 시 물리 삭제하며,
> 이벤트 원본의 사용자 식별자는 비식별화한다. 집계 결과는 개인 식별성이 없으므로 유지한다.**
> 데이터별 보존 기간은 이벤트 원본 90일, 집계 25개월, 프로파일 마지막 활동 후 1년,

# D-05 · 100ms 근거와 측정 정의 — ⚠️ 부분 결정

## 결정할 수 있는 것 — 측정 정의

**측정 5개 항목을 확정한다. 이것이 실제 병목이었다.**

| 항목 | 결정 |
| --- | --- |
| **측정 구간** | API Gateway **진입** ~ 응답 **최종 바이트 전송 완료**. 클라이언트 네트워크 **제외** |
| **측정 대상** | `POST /api/v1/ads/request` **단독**. 다른 엔드포인트는 별도 목표 |
| **부하 조건** | **1,000 RPS 지속 5분** (REQ-NF-002와 동일 조건에서 측정) |
| **데이터 조건** | 사용자 100만 · 태그 500만 · 캠페인 10만(`ACTIVE` 5,000) · 이벤트 1억(30일분) |
| **캐시 상태** | **웜 캐시** 기준. 콜드 캐시는 별도 참고 측정 |
| 지표 | **p95**. p50·p99도 함께 보고 |

## 성능 예산 배분표 — 확정

| 구간 | 배분 | 담당 |
| --- | --- | --- |
| Gateway 진입 · 인증 | 8ms | INF-A / SEC-A |
| Audience 프로파일 조회 | 15ms | AUD-C |
| Campaign 후보 조회 (1·2단계) | 30ms | CMP-D / ADS-A |
| eCPM 계산 · 정렬 · 슬롯 | 10ms | ADS-C |
| 예산 원자적 차감 | 7ms | ADS-D |
| 응답 직렬화 · 전송 | 5ms | ADS-E |
| **예비 여유** | **25ms** | — |
| **합계** | **100ms** | |

**예비 여유 25%가 3단계 폴백을 위한 것이다.** 3단계까지 내려간 요청은 후보 조회를 3회 수행하므로
Campaign 구간이 30ms에서 최대 70ms까지 늘어난다. 여유가 그것을 흡수한다.

**단계별 타임아웃도 함께 확정한다** — 1단계 20ms · 2단계 20ms · 3단계 15ms.
초과 시 다음 단계로 넘긴다. 이 상한이 없으면 3단계 요청이 예산을 무너뜨린다.

## 결정할 수 없는 것 — 목표치

**100ms가 달성 가능한 숫자인지는 측정 없이 알 수 없다.** 출처가 "업계 가이드라인"이고,
실시간 경매(§7.1이 향후로 이관)의 관행에서 온 값으로 보인다.

여기서 100ms를 200ms로 바꾸는 것도 근거 없는 추정이다. **대신 2단계 게이트로 우회한다.**

| 게이트 | 시점 | 목표 | 미달 시 |
| --- | --- | --- | --- |
| **G1 · 개발 게이트** | M1 ~ M3 매주 | **p95 ≤ 200ms** | 회귀 원인 추적. 배포 차단은 없음 |
| **G2 · 인수 게이트** | 통합 완료 시 | **p95 ≤ 100ms** | 미달 시 **사업 측과 목표 재협상** |

**G1이 이 결정의 실질이다.** 200ms를 개발 기간 내내 통과시키면
①회귀를 조기에 잡고 ②100ms 달성 가능성에 대한 실측 데이터가 쌓인다.
G2 시점에 100ms가 무리라는 데이터가 있으면, 그때는 **근거를 갖고** 재협상할 수 있다.

## REQ-NF-002도 함께 고친다

> **현행** "서비스 간 수직/수평 확장을 통해 1k+ RPS를 처리할 수 있어야 한다"

**"어떤 응답 시간을 유지한 채"가 없어 느려도 통과한다.** 두 조항을 묶는다.

## SRS 수정안 — REQ-NF-001 · REQ-NF-002

> **REQ-NF-001 수정안**
> "`POST /api/v1/ads/request`의 응답 시간은 **API Gateway 진입부터 응답 최종 바이트 전송 완료까지**를 측정하며
> (클라이언트 네트워크 제외), 사용자 100만·태그 500만·캠페인 10만·이벤트 1억이 적재된 상태에서
> **1,000 RPS 지속 5분** 부하 시 웜 캐시 기준 **p95 100ms 이하**여야 한다.
> 개발 기간 중에는 **p95 200ms를 주간 게이트(G1)** 로 적용하고, 통합 완료 시 100ms를 인수 게이트(G2)로 적용한다.
> 3단계 폴백의 단계별 타임아웃은 각 20ms·20ms·15ms로 한다."

> **REQ-NF-002 수정안**
> "1,000 RPS 지속 부하에서 **REQ-NF-001의 응답 시간 목표를 유지하며** 처리할 수 있어야 하고,
> 이벤트 유실률은 **0.1% 이하**여야 한다."
