# UX-G — 대화방 및 제안 비교 화면 설계

> 대상: `UX-009`, `UX-010` · 이슈: #146 · 선행: `UX-A` (#140)
>
> **Phase 2 조건부 산출물.** Phase 1 게이트가 통과되지 않으면 `docs/design/ux/phase2/` 디렉터리와 함께 이 문서를 이월 또는 제거한다. Phase 1 화면과 구현 순서를 바꾸지 않는다.
>
> 근거: SRS §3.1.2, §3.1.4, §8.3 규칙 1·3·4·5·13, `REQ-FUNC-022`~`025`, `REQ-NF-009`, `UX-A`, `UX-C`

## 1. 화면 목록

| 화면 또는 영역 | 진입 조건 | 화면이 보이는 내용 |
| --- | --- | --- |
| 대화방 시작 | 참여자가 대화방을 열었을 때 | 대화방 식별 정보, 서버 시각을 기준으로 한 남은 시간, 참여 매장 3~5곳의 응답 상태, 도착한 제안 목록 |
| 제안 도착 | 매장 제안이 서버에 수신됐을 때 | 새 제안 카드와 수신 시각. 카드는 수신 순서와 무관하게 적합도 순서로 배치한다. |
| 제안 비교 | 제안이 1건 이상일 때 | 적합도 순서의 제안 카드, 각 카드의 근거 4항목, 참여 매장별 응답 상태 |
| 제안 0건 회귀 | 서버 시각 기준 180초가 끝났고 유효 제안이 없을 때 | 빈 결과 대신 `UX-C` Top-3와 조건 조정 또는 다시 조회 경로 |
| 오류 또는 갱신 | 제안 목록을 가져오지 못했을 때 | 마지막으로 확인한 제안과 오류 사유, 다시 불러오기 수단 |

대화방의 제한 시간은 클라이언트 타이머가 아니라 서버가 기록한 시작·종료 시각으로 계산한다. 클라이언트의 카운트다운은 그 서버 값을 표현할 뿐, 종료 또는 제안 수용 여부를 판단하지 않는다.

## 2. 상태

어느 상태에서도 제목만 남거나 제안 영역만 비어 있는 화면을 만들지 않는다. 제안이 아직 없을 때도 참여 매장 상태, 남은 시간, 이미 적용된 조건 또는 다음 행동 중 하나 이상을 본문에 둔다.

| 상태 | 진입 조건 | 표시와 전이 |
| --- | --- | --- |
| 진행 중·제안 없음 | 서버 종료 시각 전이며 유효 제안이 0건 | 참여 매장별 `응답 전` 또는 수신 상태, 남은 시간, 조건 요약을 표시한다. 제안 수신 시 제안 도착으로 전이한다. |
| 진행 중·제안 도착 | 유효 제안이 1건 이상 | 수신되는 즉시 카드 목록에 반영하고, 적합도를 첫 정렬 키로 다시 정렬한다. 가격·거리·수신 순서는 적합도보다 앞서지 않는다. |
| 제안 비교 | 종료 전후에 유효 제안이 1건 이상 | 근거 4항목을 모두 통과한 제안 카드만 표시한다. 근거 누락 제안은 목록과 정렬 입력에서 제외하고 제외 사유를 상태 영역에 표시한다. |
| 종료·제안 0건 | 서버 시각 기준 180초가 끝났고 유효 제안이 0건 | `UX-C` Top-3로 회귀한다. 회귀 화면에는 Top-3와 조건 조정 또는 다시 조회 수단을 함께 둔다. |
| 목록 갱신 실패 | 제안 목록 갱신 요청이 실패 | 마지막으로 확인한 카드와 확인 시각을 유지하고, 오류 사유와 다시 불러오기 수단을 표시한다. 마지막 결과가 없으면 참여 매장 상태와 다시 불러오기 수단을 표시한다. |

마감 직전 도착한 제안의 수용 기준, 표시 여부, 종료 시점의 목록 확정 순서는 **(미정 — 확정 필요)**이며 `AGT-B` 담당자와 PM이 서버 시각 경계 규칙을 확정한다. 참여 매장이 끝까지 응답하지 않았을 때 표시할 문구와 상태 값도 **(미정 — 확정 필요)**이며 PM과 매장 운영 담당자가 확정한다.

## 3. 카피

아래 카피는 사실 값과 출처·시각을 넣는 형식이다. 값은 실제 응답으로 대체하며, 정렬 결과나 매장 상태를 평가하는 표현은 추가하지 않는다.

| 사용 맥락 | 화면 카피 형식 |
| --- | --- |
| 대화방 진행 | `서버 기준 종료 시각 14:03:00 · 남은 시간 02:14` |
| 참여 매장 상태 | `매장 A · 응답 전` / `매장 B · 제안 수신 14:01:18` |
| 제안 수신 | `제안 1건이 도착했습니다 · 수신 14:01:18` |
| 정렬 기준 | `제안은 적합도 순서로 표시합니다.` |
| 선정 이유 | `좌석 간격 1.2m가 입력 조건 항목에 포함됨` |
| 근거 속성 | `좌석 간격 1.2m` |
| 확인 일자 | `확인 일자 2026-07-15` |
| 확인 주체 | `확인 주체 매장` |
| 근거 누락 제외 | `근거 항목 누락으로 표시 대상에서 제외 1건` |
| 종료·0건 | `수신된 유효 제안이 없습니다. 조건에 맞는 후보를 표시합니다.` |
| 목록 갱신 실패 | `제안 목록을 불러오지 못했습니다. 다시 불러올 수 있습니다.` |

무응답 상태의 이용자 노출 문구는 **(미정 — 확정 필요)**이다. 확정 전에는 상태 코드와 마지막 갱신 시각만 표시하고, 책임 또는 이유를 단정하는 문장을 만들지 않는다.

## 4. 컴포넌트

`UX-A`의 shadcn/ui 조합과 테마 토큰만 사용한다. 화면별 CSS 파일이나 색상·간격의 임의 값은 추가하지 않는다.

| 컴포넌트 | 구성 | 표시 조건 |
| --- | --- | --- |
| `AgentRoomHeader` | 대화방 식별 정보, 서버 종료 시각, `ServerCountdown` | 모든 대화방 상태에서 표시 |
| `ServerCountdown` | 서버 시작·종료 시각에서 계산한 남은 시간 | 클라이언트는 표시 갱신만 수행하고 종료 판정은 서버 응답을 사용 |
| `ParticipantStatusList` | 참여 매장 3~5곳, 응답 상태, 마지막 갱신 시각 | 제안 수와 관계없이 표시 |
| `ProposalCard` | 제안 정보와 `EvidenceBlock` | `EvidenceGate`를 통과해 선정 이유·근거 속성·확인 일자·확인 주체가 모두 있을 때만 표시 |
| `ProposalComparisonList` | 적합도 순서의 `ProposalCard` 목록 | 유효 제안이 1건 이상일 때 표시 |
| `ProposalArrivalNotice` | 새 제안 수신 시각 | 제안이 추가된 시점에 상태 영역에 표시 |
| `RoomStatusPanel` | 0건 회귀, 근거 누락 제외, 갱신 실패, 다시 불러오기 경로 | 빈 본문 대신 해당 상태의 사실과 다음 행동을 표시 |

`ProposalCard`는 `UX-C`의 `CandidateCard` 근거 블록 규격을 그대로 사용한다. `EvidenceGate`가 네 필드를 확인한 뒤에만 카드 props를 구성하며, 대화방 화면은 그 값을 임의로 보완하지 않는다.

## 5. 근거

| 요구 또는 제약 | 설계 반영 |
| --- | --- |
| `REQ-FUNC-022` | 대화방 시작 화면에 참여 매장 3~5곳의 상태 목록과 대화방 식별 정보를 둔다. |
| `REQ-FUNC-023`, §8.3 규칙 13 | 180초는 서버 시각 기준이다. `ServerCountdown`은 서버 시작·종료 시각을 표현하며 클라이언트 시계로 종료를 결정하지 않는다. |
| `REQ-FUNC-024`, §1.1 원칙 | 제안 목록은 적합도를 첫 정렬 키로 사용한다. 가격·거리·수신 순서로 노출 순서를 판매하지 않는다. |
| `REQ-FUNC-025`, §8.3 규칙 5 | 유효 제안 0건이면 오류 또는 빈 결과가 아니라 `UX-C` Top-3로 회귀하고, 조건 조정 또는 다시 조회 경로를 표시한다. |
| §8.3 규칙 1·4, `UX-C` | 제안도 선정 이유·근거 속성·확인 일자·확인 주체가 모두 검증된 경우에만 카드로 표시하며, 이 검증은 정렬보다 먼저 수행한다. |
| §8.3 규칙 3 | 카피는 사실 값, 일자, 확인 주체, 상태 코드 형식으로 한정한다. |
| `REQ-NF-009` | 진행·도착·0건·갱신 실패 모두에 본문 정보와 다음 행동을 둔다. |

## 6. CLI 인계

| 후속 태스크 | 인계 내용 | 확인 기준 |
| --- | --- | --- |
| `CLI-F` | 서버가 제공한 대화방 시작·종료 시각을 단일 기준으로 사용해 180초 카운트다운을 표현한다. 제안 도착은 점진적으로 목록에 반영하고 매 수신 후 적합도 우선으로 정렬한다. | 클라이언트 시간 변경만으로 종료 판정이 바뀌지 않고, 180초 동안 제안이 없어도 참여 매장 상태·시간·행동이 보인다. |
| `CLI-F` | `EvidenceGate` 통과 제안만 `ProposalCard`로 렌더한다. 카드에는 선정 이유·근거 속성·확인 일자·확인 주체를 모두 표시한다. | 네 필드 중 하나라도 없으면 카드 및 정렬 입력에서 제외되고, 제외 수가 상태 영역에 표시된다. |
| `CLI-F` | 유효 제안 0건이면 `UX-C` Top-3와 조건 조정 또는 다시 조회 경로로 회귀한다. | 180초 종료 후 빈 결과 화면이 없고 Top-3 영역과 다음 행동이 표시된다. |
| `CLI-F` | 마감 직전 제안과 무응답 상태는 **(미정 — 확정 필요)**인 서버 계약을 임의로 해석하지 않는다. `AGT-B`·PM의 확정값을 수신한 뒤 반영한다. | 경계 처리와 무응답 표기가 확정 전에는 하드코딩되지 않는다. |
