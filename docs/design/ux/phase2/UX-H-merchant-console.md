# UX-H · 매장 콘솔

> Phase 2 조건부 산출물이다. Phase 1 게이트가 통과되지 않으면 `docs/design/ux/phase2/`와 함께 제거한다. 근거: SRS §3.1.2, §8.3 규칙 3·7, `REQ-FUNC-019`, `REQ-FUNC-021`, `REQ-FUNC-027`.

## 1. 화면 목록

매장 계정이 2단계 인증을 마친 뒤 콘솔에 진입한다. 설정은 세 화면으로 끝나며, 필수 입력은 다섯 항목을 넘지 않는다.

| 화면 | 목적 | 필수 항목 |
| --- | --- | --- |
| 1. 사실 속성 | 매장에 관해 확인 가능한 값을 등록 | 좌석·공간 속성, 제공 서비스 |
| 2. 수용 조건 | 소환 가능 범위를 등록 | 인원 조건, 시간·예약 조건 |
| 3. 근거 문구 검토 | 속성을 참조하는 문구와 등록값을 확인 | 근거 속성 참조 |

필수 다섯 항목은 `좌석·공간 속성`, `제공 서비스`, `인원 조건`, `시간·예약 조건`, `근거 속성 참조`다. 각 항목은 한 화면에만 나타나며, 중복 입력을 만들지 않는다. 기존 프로필이 있으면 콘솔 첫 화면의 `기존 항목 수정` 버튼 한 번으로 같은 세 화면에 등록값을 채워서 연다.

## 2. 상태

| 상태 | 표시 내용 | 다음 동작 |
| --- | --- | --- |
| 최초 등록 | 세 화면 진행 표시, 현재 화면의 입력 항목, 이전·다음 제어 | 다섯 항목을 입력해 검토 화면으로 이동 |
| 기존 항목 수정 | 기존값이 채워진 세 화면과 확인 일자·주체 | 값 수정 또는 취소 |
| 필수 항목 누락 | 누락한 항목명과 현재 입력값 | 해당 항목으로 이동 |
| 근거 참조 누락 | 문구와 연결되지 않은 속성 항목, 저장 불가 안내 | 속성을 등록하거나 문구를 삭제 |
| 판정형 입력 감지 | 입력 문구, 차단 사유, 사실 값 입력 안내 | 속성값을 추가하거나 문구를 수정 |
| 저장 처리 | 저장 중인 항목과 저장 전 마지막 값 | 완료 기록 확인 |
| 저장 실패 | 실패한 처리와 다시 시도 제어 | 같은 값으로 재시도 또는 이전 화면으로 이동 |

어느 상태에서도 화면 본문을 비우지 않는다. 저장 처리 중에는 이전 등록값 또는 입력값과 처리 상태를 함께 보이며, 실패 시에도 입력값을 유지한다. 저장이 완료되면 확인 주체는 로그인한 매장, 확인 일자는 서버 저장 시각으로 자동 기록해 검토 화면과 수정 화면에 표시한다. 이용자가 두 값을 편집하는 입력칸은 두지 않는다.

## 3. 카피

화면 문구는 평가나 순위를 말하지 않고, 입력한 사실·단위·확인 기록만 보여 준다. 실제 문구는 `UX-C`의 판정형 어휘 기준을 따른다.

| 사용 위치 | 카피 |
| --- | --- |
| 사실 속성 예시 | `좌석 간격 1.2m` |
| 제공 서비스 예시 | `유아 의자 4개` |
| 수용 조건 예시 | `동시 수용 인원 12명` |
| 자동 기록 | `확인 주체: OO매장` / `확인 일자: 2026-08-27 14:30 KST` |
| 근거 참조 누락 | `문구에 연결된 근거 속성이 없습니다. 속성을 등록하거나 문구를 삭제해 주세요.` |
| 판정형 입력 차단 | `사실 값과 단위를 입력해 주세요. 예: 좌석 간격 1.2m` |
| 저장 실패 | `등록 내용을 저장하지 못했습니다. 입력값은 유지되어 있습니다.` |

입력값이 판정형 어휘 목록에 맞거나 등록된 사실 속성을 참조하지 않으면 저장 버튼은 처리 요청을 보내지 않는다. 차단 안내는 입력값을 지우지 않으며, 어떤 속성을 추가하거나 어떤 문구를 제거할지 선택할 수 있게 한다.

## 4. 컴포넌트

`CLI-G`는 `UX-A`의 토큰과 shadcn/ui 구성 요소로 아래 구조를 구현한다. 색상·간격·서체 값이나 화면별 CSS 파일을 새로 만들지 않는다.

| 컴포넌트 | 구성 | 제약 |
| --- | --- | --- |
| `MerchantSetupStepper` | 세 화면 진행 상태와 현재 단계 | 세 단계만 표시 |
| `FactAttributeForm` | 사실 속성·제공 서비스 입력 | 단위 또는 개수와 함께 입력 |
| `CapacityConditionForm` | 인원, 시간·예약 조건 입력 | 수용 범위를 값으로 표시 |
| `EvidenceReferenceEditor` | 문구와 등록 속성 연결 | 연결되지 않은 문구는 저장 요청에서 제외 |
| `ValidationPanel` | 누락·차단·저장 실패 사유 | 입력값과 다음 동작을 유지 |
| `VerificationRecord` | 자동 기록된 확인 주체·일자 | 사용자가 수정할 수 없음 |
| `EditProfileButton` | 기존 항목을 채운 수정 흐름 진입 | 클릭 한 번으로 세 화면 진입 |

`Card`, `Input`, `Textarea`, `Button`, `Badge`, `Alert`, `Tooltip`을 우선 사용한다. `MCH-A`의 서버 검증은 최종 차단선이며, 화면의 사전 차단은 이를 대체하지 않는다.

## 5. 근거

| 요구사항·규칙 | 설계 반영 |
| --- | --- |
| `REQ-FUNC-019` | 설정 화면은 3개, 필수 입력은 5개로 고정했다. 사실 속성·제공 서비스·수용 조건을 각 항목에 등록한다. |
| `REQ-FUNC-027` | 기존 항목 수정 버튼 한 번으로 기존값을 채운 설정 흐름에 진입한다. |
| `REQ-FUNC-021`, SRS §8.3 규칙 7 | 속성 참조가 없는 문구와 판정형 입력은 저장 전에 차단하며, 등록할 사실 값을 안내한다. |
| 근거 4항목 규칙 | 콘솔이 등록하는 근거 속성은 후보 노출 전 `EvidenceGate`가 선정 이유·근거 속성·확인 일자·확인 주체와 함께 검증한다. 콘솔은 이 게이트를 우회하지 않는다. |
| 빈 화면 금지 | 최초 등록, 수정, 누락, 차단, 저장 처리, 실패에 모두 표시 내용과 다음 동작을 둔다. |
| 신선도 규칙 | 자동 기록한 확인 일자는 후보 카드의 경과 일수 계산에 쓰이며, 90일 초과 속성은 카드에서 상태로 보인다. |

`SPEC-010` 콘솔 API 계약 신설은 **(미정 — 확정 필요)** 이다. 확정 담당자는 API 계약 책임자이며, Phase 2 구현 시작 전에 등록·조회·수정 요청의 입력값, 서버 기록값, 오류 응답을 결정해야 한다. 이 문서는 계약 필드나 상태 코드를 임의로 정하지 않는다.

## 6. CLI 인계

| 대상 | 인계 내용 | 확인 기준 |
| --- | --- | --- |
| `CLI-G` | 세 화면·필수 다섯 항목·한 번 클릭 수정·입력값 유지 상태를 구현한다. `VerificationRecord`는 읽기 전용으로 렌더한다. | 신규 등록과 기존 항목 수정 모두 세 화면 이내이며, 수정 버튼 한 번으로 기존값이 채워진다. |
| `CLI-G` | `UX-C` 판정형 기준을 사용해 저장 전 입력을 차단하고 `MCH-A` 거부 응답도 `ValidationPanel`에 표시한다. | 근거 속성 참조가 없는 문구는 저장 요청으로 보내지 않으며, 차단 상태에서도 입력값과 다음 동작이 보인다. |
| `MCH-A` | 로그인 매장을 확인 주체로, 서버 저장 시각을 확인 일자로 기록하고, 근거 없는 문구를 서버에서도 거부한다. | 클라이언트가 전달한 확인 주체·일자로 기록하지 않고, 거부 사유를 화면에 전달할 수 있다. |
| `SPEC-010` 담당자 | **(미정 — 확정 필요)** 콘솔 등록·조회·수정 계약을 신설한다. | `CLI-G`와 `MCH-A`가 같은 입력·응답·오류 계약으로 연결된다. |
