### 인증 규약 (확정 · Grill T7)

| | 내용 |
| --- | --- |
| 진입 | `signInAnonymously()` — **로그인을 요구하지 않는다** |
| 전송 | `Authorization: Bearer <JWT>` |
| RLS | `auth.uid()`가 익명 사용자를 가리킨다 |
| 매장 콘솔 | 정식 로그인 + **MFA(TOTP) 승격** (`C-DRV-008`) |
| 미인증 | `401` |

**세 요구가 동시에 성립하는 유일한 경로다.**

| 요구 | 어떻게 만족하나 |
| --- | --- |
| `REQ-FUNC-008` 필수 입력 **0개** | 익명이므로 로그인 화면이 없다 |
| `REQ-NF-018` **전 API 인증** | 익명이라도 주체가 있고 JWT가 붙는다 |
| `C-DRV-004` **RLS가 유일한 방어선** | `auth.uid()`가 있어야 정책을 쓸 수 있다 |

**쿠키가 아니라 헤더인 이유** — 진입이 네이버 지도 앱 내 탭(ADR-006 · R6)이고 **인앱 브라우저의 쿠키·스토리지 정책이 제한될 수 있다**(`CLI-A` 실측 미완). `Authorization` 헤더는 그 제한과 무관하다.
API 키 안은 클라이언트 번들에 들어가 공개되고 `auth.uid()`가 없어 **`C-DRV-004`를 무력화**한다.

> **이월 (범위 밖)** — 익명 사용자 id와 `TRK-B` `session_id` 중 **어느 쪽이 KPI 분모**인가. 계약이 아니라 `CLI-A`·`TRK-B` 사안이다. `CLI-A` DoD의 *"`session_id`가 `TRK-B` 세션 정의와 일치하는가"* 에서 함께 정한다.

### 임계값 경계 규약 — 이 계약이 담는 이유 (확정 · Grill T1)

`EXEC` §6.3이 *"비용 대비 효과가 가장 크다"* 고 지목한 항목이다. **개별 확정은 7번의 논의가 필요하지만 규약 하나로 정리된다.**

| 임계값 | 읽는 법 | 소비처 |
| --- | --- | --- |
| 신선도 **90일** | `verified_at + 90일` **이상** 경과 → `STALE`. **90일 당일부터 경고** | `SPEC-008` · `SPEC-003` · `MOCK-004` |
| 파싱 실패율 **3%** | 3% **이하** → Phase 0 게이트 통과 | `SRC-A` · `TEST-005` |
| 경고 누락률 · 결측률 | 목표치 **이하** → 통과 | `TRK-D` · `TEST-007` |
| 취소 시한 **2시간** | 2시간 **이상** 남음 → 무료 취소 | `RSV-D` · `TEST-010` |
| 예산 기준값 · 수용 조건 상한 · 유사도 기준 | 기준값 **포함** | `SRC-B` · `SRC-C` · `MCH-A` |
| p95 **1,000 / 400 / 3,000ms** | 경계값 달성은 **통과** | `SPEC-002` · `SPEC-003` · `SPEC-004` |

**`SPEC-008` Scenario 3이 이미 이 규약을 전제하고 있다** — *"정확히 90일이 경과한 후보 → `STALE`로 전이"*. 경계 배제로 정하면 그 인수 기준을 고쳐야 했다.
**항목마다 방향이 다른 것은 의도된 것이다** — 신선도는 경고를 이르게 붙이는 보수적 방향, 게이트는 관대한 방향이다.
`<` / `>`를 쓰려면 **그 자리에 근거를 남긴다.** 정본은 `CLAUDE.md` §7.

### 상태 코드 체계 (제안 — SRS에 `400`·`5xx`만 존재)

| 코드 | 사용 조건 | SRS 근거 |
| --- | --- | --- |
| `200` | 정상 | — |
| `400` | 계약 위반 — **근거 4항목 누락**(§4.5.1) · 등록 속성 미참조 문구(§8.1.1) · 조건 2개 미만 | §8.1.1 명시 |
| `401` | 미인증 | `REQ-NF-018` |
| `5xx` | 서버 오류 — **`REQ-NF-008` 오류율 산정 대상** | `REQ-NF-008` |

**상태 코드는 이 넷뿐이다. `422`를 만들지 않는다. (확정 · Grill T8)**

`REQ-FUNC-009`는 파싱 실패 시 **구조화 필터로 폴백**하라고 규정한다 — 오류가 아니라 §4.5.3의 **정상 흐름 분기**다.
그래서 `200`과 함께 응답 최상위 **`fallbackApplied: true`** 로 반환한다 (`SPEC-002` · Grill T4).

**`422`도 `4xx`라 `400`과 같은 문제를 그대로 갖는다** — 클라이언트가 오류 경로(catch 블록)에서 화면을 전환해야 하고, `REQ-NF-009`(파싱 실패율 5분 윈도 집계)의 분모가 오염된다.
`SPEC-001` Scenario 2가 이미 *"`422`가 아니라 폴백 전환 신호를 반환"* 이라고 서술해 이 결정을 전제하고 있었다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 추적 ID 전파**
- **Given** `X-Request-Id`가 없는 요청
- **When** Gateway를 통과해 3개 서비스를 거침
- **Then** ID가 생성되어 전 구간에 전파되고, `IN-C`(IN-004) 계측에서 **하나의 요청으로 추적**된다

**Scenario 2 · 예외 (§4.5.3) — 외부 추론 서비스 장애**
- **Given** 조건 파서(`SRC-A` · FR-011)가 응답하지 않음
- **When** `POST /v1/query`를 호출함
- **Then** `422`가 아니라 **폴백 전환 신호**를 반환하고, 클라이언트가 구조화 필터 UI로 전환한다. `5xx`가 아니므로 `REQ-NF-008` 오류율에 포함되지 않는다

**Scenario 3 · 경계 — 오류율 산정 경계**
- **Given** `4xx` 100건 · `5xx` 1건이 발생한 1,000건 구간
- **When** `REQ-NF-008` 오류율을 산정함
- **Then** **0.1%** 로 계산된다 (`4xx`는 분자에서 제외)

**Scenario 4 · 근거 무결성 — 해당 없음**
- 이 태스크는 후보·제안을 반환하지 않는다. `SPEC-008`이 담당한다
