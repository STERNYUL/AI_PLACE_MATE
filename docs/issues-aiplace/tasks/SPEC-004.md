### 근거 누락 `400`의 본문 (확정 · Grill T10)

```json
{ "code": "EVIDENCE_MISSING", "message": "확인 주체 누락", "requestId": "..." }
```

**`message`에 누락된 항목명을 넣는다.** `SPEC-008`의 4항목은 **동등하게** 취급되므로 구현이 실수로 3개만 검사할 수 있고, 항목명이 없으면 그 실수가 드러나지 않는다.
`MOCK-003`의 **항목별 누락 4종**이 이 표기를 그대로 검증한다 — 4종 각각에서 다른 항목명이 나와야 한다.

**유효하지 않은 후보 id도 `400`이다** (Scenario 3 제안 확정). `404`를 신설하지 않는다 — 상태 코드는 `200`·`400`·`401`·`5xx` 넷 (`SPEC-001` · Grill T8).

### 카드 유효기간 (확정 · Grill T12)

| 대상 | 만료 | 이유 |
| --- | --- | --- |
| **딥링크** | `verifiedAt + 90일` **이상** 경과 시 만료 | 통제 가능한 유일한 부분. 만료 시 `근거대기` 상태로 보낸다 (`UX-F`) |
| **이미지** | **없음** | **물리적으로 불가능하다** — 메신저에 저장된 파일은 회수할 수 없다 |

**이미지를 만료시킬 수 없으므로, 카드 안의 확인 일자가 유일한 방어다.** `UX-D`가 *"확인 일자와 주체가 이미지 안에 읽히는 크기로 들어가야 한다"* 고 요구하는 이유가 이것이다 — **카드가 스스로 자기 나이를 말한다.**

**90일은 `REQ-FUNC-011` 신선도 임계와 같은 값이다.** 새 임계값을 만들지 않는다. T1의 경계 규약이 그대로 적용된다 — **90일 당일부터 만료**다.

> 이미지·딥링크 둘 다 만료시키는 안은 **계약이 지킬 수 없는 약속**이 된다. URL은 만료시켜도 이미 재공유된 파일은 그대로 남는다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상**
- **Given** 근거 4항목이 완비된 후보 id와 조건 요약
- **When** 호출함
- **Then** `200`과 이미지 URL·딥링크가 반환되고 **p95 ≤ 3,000ms**다

**Scenario 2 · 예외 (§4.5.3) — 이미지 생성 실패**
- **Given** 카드 이미지 생성이 실패함
- **When** 호출함
- **Then** **`5xx`와 함께 전체 실패한다. 카드가 생성되지 않는다** (확정 · Grill T11). 화면은 `재시도안내` 상태로 간다 (`UX-F`)
  - **딥링크만 반환하지 않는다.** 그러면 **근거 4항목이 이미지 안에 없는 채로 외부에 유통된다** — `UX-D` Scenario 2의 *"누락 시 대체 템플릿을 두지 않는다"* 를 우회하는 경로가 되고, `EVD-C`의 근거 누락 `400`이 무력해진다
  - 생성된 카드는 **회수가 불가능하다.** 부분 산출물을 내보내지 않는 쪽이 안전하다

**Scenario 3 · 경계 — 유효하지 않은 후보 id**
- **Given** query 응답에 없던 후보 id
- **When** 호출함
- **Then** **`400`** (확정 · Grill T10). §8.1.1은 후보 id가 query에서 온다고만 규정하며, 맞지 않는 id는 계약 위반이다. `404`를 신설하지 않는다

**Scenario 4 · 근거 무결성 — 이 태스크의 핵심**
- **Given** 근거 4항목 중 **확인 주체**가 누락된 후보 id
- **When** 호출함
- **Then** **`400`이 반환되고 카드가 생성되지 않는다** (§8.1 명시)

### ⚙️ Technical & Non-Functional Constraints
- **§8.1** p95 **≤ 3,000ms** · 근거 4항목 누락 시 **`400`**
- **§4.5.1** 근거 무결성이 생성의 전제
- 생성된 카드는 **외부로 유통된다** — 근거 없는 카드가 나가면 회수 불가
