### 응답 최상위 필드 — 후보 항목이 아닌 곳 (확정 · Grill T4)

`SPEC-002` 안에 모순이 있었다. 응답 항목 표는 *"여섯 필드에 임의로 추가하지 않는다"* 인데 Task Breakdown은 **폴백 신호·예산 초과 요약·유사 대체 필드를 확정하라**고 한다.

**해소 — 넷은 후보 하나의 속성이 아니라 질의 결과 전체의 속성이므로 응답 최상위에 둔다.** 두 규정이 문자 그대로 둘 다 지켜진다.

```
{
  candidates: [ … ],          ← SRS 여섯 항목 · JSON 키 7개. 추가 없음
  fallbackApplied: boolean,   ← REQ-FUNC-009 폴백 전환 신호
  overBudgetCount: number,    ← REQ-FUNC-003 '예산 초과 N곳' · 단위 곳
  substitutedDish: { … },     ← REQ-FUNC-007 유사 메뉴 대체 사실 명시
  excludedByEvidence: number, ← 근거 4항목 결락으로 제외된 수 (Grill T1·T3)
  excludedByRecheck: number   ← RECHECK_REQUIRED 로 제외된 수 (Grill T2)
}
```

**게이트 통과 건수를 따로 싣지 않는다** — `candidates.length`가 곧 통과 건수라 중복이다.
화면이 실제로 필요한 것은 *"왜 3개가 아닌가"* 이므로 **제외 사유별 건수** 둘을 싣는다. `UX-F`의 `근거생략` 상태 카피가 이 값을 쓴다.

**후보 0개일 때도 최상위 필드는 온다.** 후보 항목에 넣었다면 0개 응답에서 실을 곳이 사라진다 — 최상위 배치의 실질 이유 하나가 이것이다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 조건 있는 질의**
- **Given** 자연어 조건 1줄과 지역·인원이 주어짐
- **When** `POST /v1/query`를 호출함
- **Then** `200`과 함께 후보가 **정확히 3개** 반환되고, 각 후보에 여섯 필드가 모두 있으며, **p95 ≤ 1,000ms**다

**Scenario 2 · 예외 (§4.5.3) — 파싱 실패 후 폴백**
- **Given** 자연어 파서가 조건을 해석하지 못함
- **When** 동일 호출을 함
- **Then** 오류가 아니라 **폴백 전환 신호**와 구조화 필터 후보군이 반환되고, 클라이언트가 전환 고지를 표시한다 (`REQ-FUNC-009`)

**Scenario 3 · 경계 — 조건 0개**
- **Given** 조건·지역·인원이 **전부 비어 있는** 요청 (§8.1.1 "조건 0개 허용")
- **When** 호출함
- **Then** `400`이 아니라 `200`과 후보 3개가 반환된다 (`REQ-FUNC-008` 필수 입력 필드 0개)

**Scenario 4 · 근거 무결성 — 근거 없는 후보 반환 금지**
- **Given** 근거 4항목 중 하나가 결락된 후보가 정렬 대상에 있음
- **When** 호출함
- **Then** **그 후보는 응답에서 제외**된다. 3개를 채우지 못하면 **통과한 만큼만 반환한다** (0~3개 · Grill T3)

### 3개 고정 ↔ 근거 미비 제외 충돌 — 해소 (확정 · Grill T3)

§8.1이 *"후보 정확히 3개"* 와 *"근거 없는 후보 반환 금지"* 를 동시에 요구하고, 충돌 구간 동작이 SRS에 없었다.

**`REQ-FUNC-014`의 3을 상한으로 읽는다.** 게이트 통과분만 반환한다.

| 게이트 통과 | 응답 | 화면 |
| --- | --- | --- |
| 3곳 | 3개 | 정상 |
| 2곳 · 1곳 | **그만큼** + 통과 건수를 응답에 실음 | 사실로 고지 — *"조건을 만족한 후보가 2곳"* |
| 0곳 | 0개 | **열화 상태 `제안없음`** — 빈 화면이 아니다 (`UX-F`) |

**제외 사유는 둘이다** — ① 근거 4항목 결락 ② `RECHECK_REQUIRED` (Grill T2). 둘 다 정렬 이전 단계에서 걸러진다 (§4.5.2 · `REQ-IMPL-010`).

**왜 3개를 채우지 않는가** — 채우려면 기준을 낮춰야 하고, 그것이 불변 규칙 1과 `REQ-IMPL-010`을 정면으로 깬다. 반대로 3개를 못 채웠다고 0건으로 반환하면 통과한 2곳을 버리는 것이라 불변 규칙 2의 취지에 반한다. **상한 해석이 네 규칙 중 셋을 지키는 유일한 경로다.**

### `REQ-NF-001` 측정 조건 — `IN-C`에 위임한다 (확정 · Grill T9)

**측정 조건은 계약이 아니라 관측 체계의 속성이다.** 계약에 숫자를 박으면 관측 체계가 다른 조건으로 재기 시작할 때 계약을 고쳐야 한다.
`CLI-E`가 이미 *"측정 방법이 요구의 일부다 — `IN-C` 관측 체계와 같은 자리에서 정해야 한다"* 고 적었고, `TEST-014a`의 선행이 `IN-C`·`IN-D`·`IN-E`·`IN-G`다.

**계약이 위임하는 항목 — `IN-C`가 이 다섯을 빠뜨리면 `TEST-014a`가 판정 불가가 된다.**

| # | 위임 항목 |
| --- | --- |
| 1 | **데이터량** — 색인 규모 |
| 2 | **RPS** — 동시 부하 |
| 3 | **캐시 상태** — 콜드 스타트인가 워밍업 후인가 |
| 4 | **측정 지점** — Gateway 입구인가 클라이언트 수신인가 |
| 5 | **선정 이유 생성 비용 포함 여부** — `EVD-B`가 매 응답 생성한다 (Grill T5). **p95 안에 들어간다** |

**5번이 새로 생긴 항목이다.** T5로 선정 이유를 저장하지 않기로 해 **매 응답 생성 비용이 p95 예산을 소모한다.** 측정에서 빼면 실제와 다른 수치가 나온다.
