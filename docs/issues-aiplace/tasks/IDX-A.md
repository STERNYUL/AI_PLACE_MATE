### `IDX-A1` / `IDX-A2` 분할 경계 — 무엇이 1주 안에 얼어붙나 (확정 · Grill S3-T1)

압축 §2.1이 `IDX-A`를 둘로 쪼갰다. **얼린 것은 되돌릴 수 없다** (ADR-001 — 사후 변경 = 전면 재색인).

| 분할 | 담는 것 | 얼어붙나 |
| --- | --- | --- |
| **`IDX-A1`** (1주) | 5개 엔터티 · 관계 · PK/FK · 인덱스 키 · **`verification` 전 필드**(3상태 · `verified_at` · `verified_by`) | **얼어붙는다** |
| **`IDX-A2`** (1주) | `PriceProfile` 구조 · `Attribute.scope` · 성분·접근성 필드 · 마이그레이션·롤백 검증 | 이 시점에 확정 |

**후행이 무엇을 언제 필요로 하는지가 이 경계를 정했다.**

| 후행 | 주차 | A1에서 필요한 것 |
| --- | --- | --- |
| `IDX-B` 정규화 | 2~4 | `dish` + `canonical_key` 컬럼 |
| `IDX-D` `Verification` | 2~4 | **`verification` 엔터티 + 필드 전부** |
| `IDX-C` 파이프라인 | 4~6 | 필수 필드 5개 — **원래 `IDX-A2` 뒤다** |

**`IDX-C`가 원래 `A2` 뒤이므로 필드 상세를 `A1`에 넣어도 앞당겨지는 것이 없다.** 반면 `IDX-D`는 2주차에 `verification` 필드가 필요하다.
그래서 **압축 문서의 분할선을 그대로 두고 `verification`이 `A1`이라는 것만 명시**한다 — 최소 변경으로 후행 3건이 전부 계획대로 착수한다.

### `Proposal` 참조 계약을 여기서 고정하는 이유

원장 v1.0 ‡ 주석이 경고한 항목이다. §8.6.3은 `Reservation.proposalId`가 `Proposal`을 참조하도록 규정하지만,
§4.3.1과 **ADR-005**는 예약·결제(F9)를 제안(F7)보다 **먼저** 배치한다 — *"선결제 없이 제안을 열면 첫 노쇼에서 가맹점이 이탈"* 하기 때문이다.

**따라서 `RSV-A`(FR-029)는 `Proposal` 스키마 계약만 확정된 상태에서 착수하고, 실제 참조 연결은 `AGT-C`(FR-044) 완료 시점에 결선된다.**
**이 계약을 여기서 고정하지 않으면 Phase 2에서 예약 도메인을 다시 손대게 된다.**

### 고정 내용 (확정 · Grill S3-T4) — `EXEC` §6.4 구조 결함 1건 해소

| 시점 | 무엇 |
| --- | --- |
| **`IDX-A1`** | `reservation.proposal_id` **컬럼만.** `NULL` 허용 · **FK 제약 없음** · `proposal` 테이블 만들지 않음 |
| **Phase 1 말** | 값이 **항상 `NULL`.** 예약이 제안 없이 독립 동작한다 (ADR-005 — 선결제가 제안보다 먼저) |
| **Phase 2 `AGT-C`** | `proposal` 테이블 생성 + **FK 제약 추가**로 결선 |

**셋을 동시에 지킨다.**

| 규칙 | 어떻게 |
| --- | --- |
| `CLAUDE.md` §7 — Phase 2에 Phase 1을 의존시키지 않는다 | Phase 2 스키마가 Phase 1에 들어오지 않는다. **게이트 미통과 시 컬럼을 `NULL`인 채로 두면 끝** |
| **ADR-001** — 사후 변경 = 전면 재색인 | 컬럼을 나중에 **추가하지 않는다.** FK 제약 추가는 재색인이 아니다 |
| §8.6.3 — `Reservation.proposalId` 참조 | 컬럼이 처음부터 있으므로 `RSV-A`가 참조 계약을 알고 설계한다 |

**`proposal` 테이블을 `A1`에 함께 만드는 안을 기각한 이유** — Phase 2 스키마가 Phase 1에 산다. 게이트 미통과 시 *"15건을 통째로 버린다"* 는 전제가 깨지고 무엇을 버릴지가 불분명해진다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 5개 엔터티 정의**
- **Given** §8.2의 데이터 모델 정의
- **When** 스키마를 생성하고 마이그레이션을 실행함
- **Then** `place` · `dish` · `attribute` · `price_profile` · `verification` 5개가 §8.6.3 정합성 제약과 함께 생성된다

**Scenario 2 · 예외 — 마이그레이션 롤백**
- **Given** 마이그레이션 중 오류 발생
- **When** 롤백을 실행함
- **Then** 이전 상태로 완전히 복원되고 **부분 적용이 남지 않는다**

**Scenario 3 · 경계 — `PriceProfile` 하한 = 상한**
- **Given** 단일 가격만 확인된 메뉴 (하한 = 평균 = 상한)
- **When** 저장하고 조회함
- **Then** **세 값이 모두 같은 값으로 저장되고**(`NOT NULL`), 화면은 `lib/search`가 **단일값으로 축약해 렌더**한다 (확정 · Grill S3-T3)

### `PriceProfile` 단일값 — 스키마는 3필드, 축약은 표시 계층 (확정 · Grill S3-T3)

| 계층 | 처리 |
| --- | --- |
| 스키마 | `min` · `avg` · `max` **전부 `NOT NULL`.** 단일 가격이면 셋이 같은 값 |
| 표시 (`lib/search`) | `min === max` → `"18,000원"` · `min !== max` → `"15,000~22,000원"` |

**세션 2 T4와 같은 판단이다** — *"다른 값으로 알 수 있는 것은 싣지 않는다."* 단일값 여부는 `min`·`max` 두 값에서 그대로 나오므로 `isSingleValue` 플래그는 중복이고, **`min ≠ max`인데 플래그가 `true`인 상태**를 막을 정합성 제약이 새로 필요해진다.

**하한·상한을 `nullable`로 두는 안을 기각한 이유** — `SRC-B` 예산 필터·정렬·비교가 전부 `null` 분기를 타게 되고, `REQ-FUNC-003`의 **'예산 초과 N곳' 집계**가 `COALESCE` 범벅이 된다. 세 값이 항상 있으면 분기가 없다.

**Scenario 4 · 근거 무결성 — `Attribute` 참조 가능성**
- **Given** 근거 속성이 될 `attribute` 레코드
- **When** `EVD-A`(FR-021)가 근거 4항목을 검증함
- **Then** **`attribute`를 참조해 근거 속성을 확인할 수 있다.** 참조 불가면 근거 4항목이 성립하지 않는다

### 성분·접근성 — `Attribute.scope` 열거값으로 흡수 (확정 · Grill S3-T5)

`REQ-NF-024`는 성분(F1a)·접근성(F1b)을 **v0.1에서 필드만 확보하고 적재는 하지 않는다**고 규정한다(§0.4 제외).
**미리 확보하는 이유는 ADR-001** — 나중에 컬럼을 추가하면 전면 재색인이다.

| 방식 | 새 테이블 | 새 컬럼 | 재색인 |
| --- | --- | --- | --- |
| **`Attribute.scope`에 `INGREDIENT`·`ACCESSIBILITY` 추가** | 0 | 0 | **없음** |

**열거값 추가는 컬럼 추가가 아니다.** `attribute` 엔터티가 `IDX-A1`에서 얼어붙으면 v0.2는 **해당 `scope`로 행을 쌓기만 하면 되고 스키마가 바뀌지 않는다.**
`REQ-NF-024`의 *"필드 사전 확보"* 는 **저장할 자리가 있다**는 뜻으로 충족된다 — 빈 컬럼 둘을 v0.1 내내 들고 있을 이유가 없다.

**v0.1에서는 이 `scope`의 `attribute` 행을 만들지 않는다.** 근거 4항목의 `evidenceAttribute`가 이 `scope`를 참조하는 일도 없다.
- [x] `PriceProfile` 단일값 표기가 확정되었는가? — **3필드 `NOT NULL` · 축약은 `lib/search`** (Grill S3-T3)

### 조건 카테고리 어휘 — 운영자 단독 관리 (확정 · Grill S3-T9)

| | 내용 |
| --- | --- |
| 관리 주체 | **운영자 단독.** 상권별로 나누지 않고 **전국 단일 사전** |
| 매장 콘솔 | **드롭다운 선택만** (`UX-H`) — 자유 입력을 두지 않는다 |
| 신규 어휘 | 매장이 **요청** → 운영자 **검토** → 사전 **반영** |

**S3-T2에서 `verified_by`를 열거형으로 만든 것과 같은 판단이다.** 조건 카테고리는 `SRC-B` 필터의 어휘이자 `Attribute`의 값이라 **화면에 그대로 나간다.**
자유 입력이면 `UX-H`의 *"근거 없는 문구 입력 차단"* 이 **콘솔 UI에만 의존**하게 되고, `"분위기 좋은 룸"` 같은 값이 정리 전까지 필터 어휘로 살아 있다 (§8.3 규칙 7 저촉). **드롭다운이면 애초에 입력할 수 없다.**

**상권별 분산을 기각한 이유** — 상권마다 어휘가 갈리면 `SRC-B` 필터가 상권별로 달라져 **Top-3가 상권을 가로지를 때 비교가 성립하지 않는다.** v0.1은 상권 1곳이라 분산할 이유도 없다.
