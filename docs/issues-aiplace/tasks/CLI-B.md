### ⚠️ 전환 고지는 사과가 아니다

`REQ-FUNC-009`가 전환 고지를 요구하는 이유는 **사용자가 왜 화면이 바뀌었는지 알아야** 하기 때문이다.
`SPEC-002`에서 정리한 대로 **파싱 실패는 오류가 아니라 정상 분기**다.

| 나쁜 고지 | 좋은 고지 |
| --- | --- |
| "오류가 발생했습니다" | "직접 조건을 선택해 주세요" |
| 조용히 화면 교체 | 입력한 내용을 남긴 채 필터로 전환 |

**부분 파싱된 필드를 버리면 사용자는 처음부터 다시 입력한다.** 이월 여부가 확정돼야 한다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 자연어 입력**
- **Given** 사용자가 조건을 자연어로 입력함
- **When** 전송함
- **Then** 파싱 결과가 확인 가능한 형태로 표시되고 탐색이 시작된다

**Scenario 2 · 예외 (§4.5.3) — 파싱 실패**
- **Given** 파싱이 실패함 (`MOCK-002`)
- **When** 응답을 받음
- **Then** **폴백 필터로 전환되고 전환 사실이 고지된다.** 오류 화면이 아니다 (`REQ-FUNC-009`)

**Scenario 3 · 경계 — 부분 파싱**
- **Given** 인원은 인식되고 예산은 인식되지 않음
- **When** 폴백으로 전환함
- **Then** **(미정 — 확정 필요)** 인식된 인원이 필터에 이월되는가

**Scenario 4 · 근거 무결성 — 조건 왜곡 없음**
- **Given** 사용자가 입력한 원문 조건
- **When** 파싱 결과를 표시함
- **Then** **입력하지 않은 조건이 임의로 추가되지 않는다.** 추정 조건이 결과를 좌우하면 안 된다
