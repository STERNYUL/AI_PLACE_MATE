### ⚠️ TTL 6h ↔ 신선도 90일 — `P1a`에서 제기된 충돌

`P1a-contracts.md`가 지적한 항목이다.

| 규칙 | 값 |
| --- | --- |
| 캐시 TTL | **6시간** |
| 확인 정보 신선도 | **90일** |

**두 값은 서로 다른 것을 관리한다** — TTL은 조회 응답의 캐시 수명, 90일은 확인 정보의 유효 기간.
그런데 **캐시된 응답에 담긴 확인 상태가 6시간 안에 `STALE`로 바뀌면**, 캐시가 옛 상태를 6시간 더 서빙한다.

`EVD-D`의 신고 → `RECHECK_REQUIRED` **60초 전이**(`REQ-FUNC-013`)와도 충돌한다 —
**60초 안에 전이해도 캐시가 6시간 옛 상태를 보여주면 요구가 무의미하다.**

**확인 상태 변경 시 캐시 무효화 경로가 필요하다.**

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 캐시 히트**
- **Given** 반복 조회
- **When** 히트율을 측정함
- **Then** **70% 이상**이다 (`REQ-NF-020`)

**Scenario 2 · 예외 (§4.5.3) — 확인 상태 변경**
- **Given** 신고로 `RECHECK_REQUIRED`가 됨
- **When** 캐시된 응답이 조회됨
- **Then** **무효화되어 최신 상태가 반환된다.** 60초 요구가 캐시로 무력화되지 않는다

**Scenario 3 · 경계 — TTL 6시간 만료**
- **Given** 캐시 생성 후 6시간
- **When** 조회함
- **Then** 재조회되어 갱신된다

**Scenario 4 · 근거 무결성 — 캐시된 근거의 유효성**
- **Given** 캐시된 후보 응답
- **When** 근거 4항목을 확인함
- **Then** **캐시 시점이 아니라 현재 기준으로 유효**하다. `STALE` 전이가 반영된다
