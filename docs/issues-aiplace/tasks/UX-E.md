### ⚠️ 옵트인 동의는 '받는 것'이 아니라 '이해시키는 것'이다

`REQ-NF-014`는 개인 제약을 **단말에 저장**한다고 규정한다. `REQ-NF-032`는 서버 전송을 옵트인으로 한다.
**사용자 입장에서 이 둘의 차이가 보이지 않으면 동의는 형식이 된다.**

동의 화면이 답해야 하는 것 —

| 질문 | 답해야 할 내용 |
| --- | --- |
| 무엇이 전송되는가 | 알레르기 등 개인 제약 항목 |
| 동의하지 않으면 | 단말에만 남고 기능 일부가 제한 |
| 언제까지 | 보존 기간 (`PRV-A` §8.6.5 미정) |
| 되돌릴 수 있는가 | 철회 경로 |

**보존 기간이 미정이면 동의 화면 카피를 완성할 수 없다.** `PRV-A`의 미정 항목이 여기서 막힌다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 재입력 0개 플로우**
- **Given** 선택된 후보의 조건
- **When** 예약 플로우를 통과함
- **Then** **사용자가 입력하는 필드가 0개**다 (`REQ-FUNC-015`)

**Scenario 2 · 예외 (§4.5.3) — 미동의 상태**
- **Given** 사용자가 옵트인하지 않음
- **When** 개인 제약이 필요한 화면에 도달함
- **Then** **전송 없이 진행 가능한 경로**가 있다. 동의를 강요하는 구조가 아니다 (`REQ-NF-032`)

**Scenario 3 · 경계 — 취소 시한 임박**
- **Given** 예약 2시간 전 경계
- **When** 취소 화면을 봄
- **Then** 환불 가능 여부가 **행동 전에** 명시된다. 판정은 `RSV-D` 확정을 따른다

**Scenario 4 · 근거 무결성 — 동의 내용의 사실성**
- **Given** 동의 화면 카피
- **When** 실제 처리(`PRV-A` 보존 기간 · `PRV-B` 전송 범위)와 대조함
- **Then** **일치한다.** 카피가 실제보다 좁게 쓰이면 그것이 위반이다
