## IN-A · API Gateway 구축 {#in-a}

**labels** `infra, platform, priority:critical, phase-0, blocks-all`

### ✅ Task Breakdown

- [ ] 라우팅 규칙 — `SPEC-` 계약의 엔드포인트 체계 반영
- [ ] 인증 진입점 — `IN-B` 미들웨어 연결 지점
- [ ] 요청 식별자 전파 — `requestId` (`SRC-D` 동점 tie-break에 사용)

### ⚠️ `requestId` 전파가 여기서 정해진다

`SRC-D`의 정렬 동점 처리(`P2a` 2번)가 `requestId` 해시를 tie-break로 쓰는 방안을 검토 중이다.
**게이트웨이가 요청마다 안정적인 식별자를 부여하고 하위 서비스에 전파해야** 그 방안이 성립한다.

`TRK-B`의 세션 식별자, `RSV-C`의 결제 멱등키와도 연결된다 —
**"같은 요청인지 어떻게 아는가"** 가 세 곳에서 반복되는 질문이며, 게이트웨이가 그 기반이다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 라우팅**
- **Given** `SPEC-` 계약의 엔드포인트로 요청이 옴
- **When** 게이트웨이가 처리함
- **Then** 해당 서비스로 라우팅되고 `requestId`가 전파된다

**Scenario 2 · 예외 (§4.5.3) — 하위 서비스 장애**
- **Given** 대상 서비스가 응답하지 않음
- **When** 요청이 들어옴
- **Then** **정의된 오류 응답**이 반환된다. 게이트웨이가 함께 멈추지 않는다

**Scenario 3 · 경계 — 레이트 리밋**
- **Given** 단일 클라이언트의 급증 요청
- **When** 처리함
- **Then** **(미정 — SRS에 값이 없다)** 제한 정책이 필요하다

**Scenario 4 · 근거 무결성 — 식별자 안정성**
- **Given** 하나의 요청이 여러 서비스를 거침
- **When** 로그를 추적함
- **Then** **동일 `requestId`로 전 구간이 연결**된다 (`IN-C` 관측성의 전제)

### ⚙️ Technical & Non-Functional Constraints
- **원장 §4 순위 1** — 후행이 사실상 전부
- **Phase 0 최선행** — 이 태스크의 지연이 전체 일정 지연
- `SPEC-` 계약의 엔드포인트 체계와 정합

- [ ] `requestId` 전파가 전 구간에서 유지되는가?
- [ ] 하위 서비스 장애가 게이트웨이를 멈추지 않는가?
- [ ] 레이트 리밋 정책이 확정되었는가?

### 🚧 Dependencies & Blockers

### ⚠️ 감사 로그가 `PRV-A`의 검증 수단이다

`REQ-NF-031`(목적 제한 접근)은 **출발지 정보에 목적 외 접근이 없음**을 요구한다.
`PRV-A`(FR-059)가 그것을 **점검**하는데, **점검할 로그가 없으면 점검할 수 없다.**

따라서 감사 로그는 **무엇을 남길지**가 요구에서 역산돼야 한다 —
누가·언제·어느 데이터에·어떤 목적으로 접근했는지.
**"목적"을 로그에 어떻게 기록할지가 미정이다.**

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 인증 통과**
- **Given** 유효한 자격 증명
- **When** 보호된 엔드포인트에 접근함
- **Then** 통과하고 감사 로그가 남는다

**Scenario 2 · 예외 (§4.5.3) — 인증 실패**
- **Given** 무효한 자격 증명
- **When** 접근함
- **Then** 거부되고 **실패도 감사 로그에 남는다**

**Scenario 3 · 경계 — 2FA 우회 시도**
- **Given** 1차 인증만 통과한 매장 계정
- **When** 콘솔에 접근함
- **Then** **차단된다** (`FR-041`)

**Scenario 4 · 근거 무결성 — 접근 목적 기록**
- **Given** 출발지 정보에 대한 접근
- **When** 감사 로그를 조회함
- **Then** **목적이 식별 가능**하다 (`REQ-NF-031` · `PRV-A` 점검 가능)

### ⚙️ Technical & Non-Functional Constraints
- **`REQ-NF-017`** 저장 암호화 **AES-256** — 결제·정산 데이터
- **`REQ-NF-031`** 목적 제한 접근 — 감사 로그로 점검
- **`FR-041`** 콘솔 2FA
- **공통 계층** — 서비스별 개별 구현 금지

## IN-D · 수평 확장 구성 {#in-d}

**labels** `infra, scalability, priority:high, phase-1`
**원문** `IN-005`

### 🎯 Summary
- **Task ID** `IN-D` · **Must / H**
- **목적** **피크 3,000 RPS**를 견딘다. Phase 1 규모(사용자 500)와 이 숫자의 간극이 논점이다.

### 🔗 References
- **`REQ-NF-005`**(피크 **3,000 RPS**) · §4.2 · 선행 `IN-A`
- 후행 `IN-E` `IN-G`

### ⚠️ 3,000 RPS는 Phase 1 규모와 맞지 않는다

| 항목 | 값 |
| --- | --- |
| Phase 1 사용자 | **500명** |
| Phase 1 가맹 | 150곳 · 상권 3곳 |
| `REQ-NF-005` 피크 | **3,000 RPS** |

**500명이 3,000 RPS를 만들지 않는다.** 이 수치는 **정식 출시 규모의 요구**로 보인다.

그렇다면 **Phase 1에 3,000 RPS 구성을 갖출 필요가 있는가**가 질문이다.
`IN-G`(부하 테스트)가 **조기 착수**로 표기된 것은 이 수치를 미리 검증하려는 의도로 읽히지만,
**Phase 1 인프라 비용이 과할 수 있다.**

**대안** — 구성은 확장 가능하게 만들되(오토스케일 정책), 실제 용량은 Phase별로 조정.
**`REQ-NF-005`가 어느 시점의 요구인지 PM 확정이 필요하다.**

### ✅ Task Breakdown
- [ ] **`IN-005`** 서비스별 수평 확장 구성
- [ ] 오토스케일 정책 — 지표·임계·쿨다운
- [ ] **3,000 RPS 적용 시점 확정 (미정)**
- [ ] 서비스별 병목 식별 — `SRC-D`(p95 1,000ms)가 최대 부하 경로
- [ ] `IN-G` 부하 테스트 대상 구성 제공

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 부하 증가 시 확장**
- **Given** 요청량이 임계를 넘음
- **When** 오토스케일이 발동함
- **Then** 인스턴스가 증가하고 p95가 유지된다

**Scenario 2 · 예외 (§4.5.3) — 확장 한계**
- **Given** 최대 인스턴스에 도달함
- **When** 부하가 계속 증가함
- **Then** **(미정)** 요청 거절인가 지연 수용인가. §8.3 규칙 5(빈 화면 금지)와 연결

**Scenario 3 · 경계 — 3,000 RPS**
- **Given** 피크 부하 3,000 RPS
- **When** `IN-G`로 측정함
- **Then** p95 요구가 유지된다 (`REQ-NF-005`)

**Scenario 4 · 근거 무결성 — 확장 중 데이터 정합**
