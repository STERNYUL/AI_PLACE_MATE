## RSV-A · Reservation 엔터티 및 조건 승계 {#rsv-a}

**labels** `feature, backend, reservation-service, priority:high, phase-1-late`
**원문** `FR-028` `FR-029`

### 🎯 Summary
- **Task ID** `RSV-A` · **Must / M (M×2)**
- **목적** 예약의 뼈대. **재입력 필드 0개**(`REQ-FUNC-015`)를 성립시키는 조건 승계가 핵심이다.

### 🔗 References
- §8.2 · §8.6.3 · §4.5.5 · `REQ-FUNC-015`
- **ADR-005** · 선행 `IDX-A`(`Proposal` 참조 계약)

### ⚠️ `Proposal` 참조는 계약만 있고 대상은 아직 없다

§8.6.3은 `Reservation.proposalId`가 `Proposal`을 참조하도록 규정한다.
그런데 `Proposal`을 만드는 `AGT-C`(FR-044)는 **Phase 2**다.

**`IDX-A`에서 스키마 계약을 고정했으므로 이 태스크는 착수할 수 있다.**
실제 참조 연결은 `AGT-C` 완료 시점에 결선된다. Phase 2가 이월되면 **참조가 비어 있는 상태로 운영**된다 —
그 경우의 동작이 정의돼야 한다.

### ✅ Task Breakdown
- [ ] **`FR-028`** `Reservation` 엔터티 + 상태 전이 (§8.2)
- [ ] **`FR-029`** 제안 조건 자동 승계 — **인원 · 메뉴 구성 · 시간**
- [ ] `proposalId` 참조 — **Phase 2 미착수 시 null 허용 여부 확정 (미정)**
- [ ] 재입력 필드 0개 검증 (`REQ-FUNC-015`)
- [ ] Top-3 후보에서 직접 예약하는 경로 (제안 없이)

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 조건 승계**
- **Given** 선택된 제안 또는 후보의 인원·메뉴 구성·시간
- **When** 예약을 생성함
- **Then** 조건이 자동 승계되고 **사용자가 재입력할 필드가 0개**다

**Scenario 2 · 예외 (§4.5.3) — 제안 없는 예약**
- **Given** Phase 2 미착수로 `Proposal`이 존재하지 않음
- **When** Top-3 후보에서 직접 예약함
- **Then** **(미정 — 확정 필요)** `proposalId` null 허용인지, 별도 경로인지

**Scenario 3 · 경계 — 승계 조건 불완전**
- **Given** 제안에 시간 정보가 없음
- **When** 승계함
- **Then** **(미정)** 누락 필드를 사용자에게 물으면 "재입력 0개"가 깨진다

**Scenario 4 · 근거 무결성 — 승계 값 출처 추적**
- **Given** 승계된 예약 조건
- **When** 출처를 확인함
- **Then** 어느 제안·후보에서 왔는지 추적 가능하다 (분쟁 대응)

### ⚙️ Technical & Non-Functional Constraints
- **`REQ-FUNC-015`** 재입력 필드 **0개**
- **§8.6.3** `Reservation.proposalId` 참조 제약
- **ADR-005** 이 태스크가 Phase 2보다 먼저 — 참조 대상이 나중에 생긴다
- 상태 전이는 §8.2 도식과 일치

공통 DoD 5개. 추가로 —

- [ ] 재입력 필드가 실제로 0개인가? (`UX-E` 플로우로 검증)
- [ ] 승계 출처가 추적 가능한가?

### 🚧 Dependencies & Blockers
- **Depends on** `IDX-A`(`Proposal` 스키마 계약)
- **Blocks** `RSV-B` `RSV-C` `CLI-D`

## RSV-D · 취소·환불 및 노쇼 정산 {#rsv-d}

**labels** `feature, command, backend, reservation-service, priority:high, phase-1-late`
**원문** `FR-033` `FR-034` `FR-035`

### 🎯 Summary
- **Task ID** `RSV-D` · **Must / H (H×1+M×2)**
- **목적** 예약의 종료 처리. **노쇼 정산이 가맹점 이탈을 막는 장치**이며 ADR-005의 목적이 여기서 실현된다.

### 🔗 References
- `REQ-FUNC-017`(취소·환불 · 2시간 전 시한 · ≤24h) · `REQ-FUNC-018`(방문 확인 · 노쇼 정산)
- §8.2 상태 전이(`VISITED` · `NO_SHOW` → `SETTLED`) · §8.6.3 · §4.5.4
- **Phase 1 말 게이트** — 선택 제안 노쇼율 계측 개시

### ✅ Task Breakdown
- [ ] **`FR-033`** 취소 접수 + 전액 환불 — **2시간 전 시한** · **≤24h 처리**
- [ ] **`FR-034`** 방문 확인 처리 — `VISITED` 전이
- [ ] **`FR-035`** 노쇼 판정 + 매장 정산 — `NO_SHOW` → `SETTLED`
- [ ] **방문 확인 주체와 방법 확정 (미정 — SRS에 없다)**
- [ ] 노쇼 판정 시점 확정 **(미정)**
- [ ] 정산 금액 산정 규칙 **(미정)**

### ⚠️ 방문 확인을 누가 어떻게 하는지가 없다

`FR-034`는 *"방문 확인 처리(`VISITED` 전이)"* 를 규정하지만 **주체와 방법이 SRS에 없다.**

| 후보 | 문제 |
| --- | --- |
| 매장이 확인 | 매장이 노쇼를 방문으로 처리할 유인이 있다 (정산 차이) |
| 사용자가 확인 | 사용자가 확인하지 않으면 영원히 미확정 |
| 자동 (시간 경과) | 실제 방문 여부를 알 수 없다 |

**노쇼 정산은 돈이 오가는 판정**이므로 이 공백이 그대로 분쟁이 된다.
`FR-035`의 노쇼 판정 시점(예약 시각 + N분?)과 정산 금액 산정 규칙도 없다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 방문 및 정산**
- **Given** 예약 시각에 사용자가 방문함
- **When** 방문이 확인됨
- **Then** `VISITED`로 전이하고 정산 대상이 된다

**Scenario 2 · 예외 (§4.5.3) — 노쇼**
- **Given** 사용자가 방문하지 않음
- **When** 노쇼가 판정됨
- **Then** `NO_SHOW` → `SETTLED`로 전이하고 **매장에 정산**된다. 판정 시점 **(미정)**

**Scenario 3 · 경계 — 2시간 전 취소 시한**
- **Given** 예약 시각 **정확히 2시간 전** 취소 요청
- **When** 접수함
- **Then** **(미정 — 확정 필요)** 이상/초과 판정. 전액 환불 대상인지 경계가 SRS에 없다

**Scenario 4 · 근거 무결성 — 상태 전이 이력**
- **Given** 예약의 전 생애
- **When** 이력을 조회함
- **Then** 모든 상태 전이가 **시각과 함께 보존**된다 (§8.6.5 · 정산 분쟁 대응)

## PRV-A · 서버 측 개인정보 처리 {#prv-a}

**labels** `feature, backend, privacy, priority:high, phase-1-late`
**원문** `FR-058` `FR-059` `FR-062` `FR-063`

### 🎯 Summary
- **Task ID** `PRV-A` · **Must / M (M×3+L×1)**
- **목적** 수집한 것을 **정해진 기간만 갖고 목적 외로 쓰지 않는다.** 그리고 **애초에 안 받는 것**을 검증한다.

### 🔗 References
- `REQ-NF-013`(출발지 30일 파기) · `REQ-NF-015`(취향·비고 미수집) · `REQ-NF-031`(목적 제한 접근)
- §4.4 · §8.6.4 · §8.6.5(보존 정책)
- 선행 `TRK-B` `IN-B`(감사 로그) `IN-F`(파티셔닝) `IDX-A`

### ✅ Task Breakdown
- [ ] **`FR-058`** 참석자 출발지 정보 **30일 내 파기 배치**
- [ ] **`FR-059`** 출발지 목적 제한 접근 통제 + **로그 점검**
- [ ] **`FR-062`** 참석자 취향·비고 **미수집 검증** — 스키마에 필드가 없음을 확인
- [ ] **`FR-063`** 데이터 보존 정책 배치 — 이벤트 · 확인 상태 · 예약 · 결제
- [ ] 보존 기간 확정 **(미정 — §8.6.5 상세 확인 필요)**
- [ ] 파기 실행 이력 기록

### `FR-062`가 "구현"이 아니라 "검증"인 이유

`REQ-NF-015`는 취향·비고를 **수집하지 않는다**고 규정한다.
**구현할 것이 없다 — 없음을 증명하는 것이 이 태스크다.**

스키마에 필드가 없는지, API가 그 값을 받지 않는지, 로그에 흘러들지 않는지를 **전수 확인**한다.
복잡도 `L`인 이유이자, **자동 검증으로 만들어 회귀를 막아야 하는 이유**다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 30일 파기**
- **Given** 30일이 경과한 출발지 정보
- **When** 파기 배치를 실행함
- **Then** 삭제되고 파기 이력이 기록된다 (`REQ-NF-013`)

**Scenario 2 · 예외 (§4.5.3) — 파기 배치 실패**
- **Given** 배치 실행 중 오류
- **When** 다음 주기가 도래함
- **Then** 재시도되고, **연속 실패 시 경보**가 발생한다. 파기 지연은 법령 위반이다

**Scenario 3 · 경계 — 30일 당일**
- **Given** 수집 후 정확히 30일 경과
- **When** 파기 대상을 판정함
- **Then** 파기된다 (이상 판정)

**Scenario 4 · 근거 무결성 — 미수집 필드 전수 검증**
- **Given** 스키마 · API · 로그 · 이벤트 전체
- **When** 취향·비고 관련 필드를 검색함
- **Then** **0건**이다. 자동 검증으로 회귀를 막는다 (`REQ-NF-015`)

### ⚙️ Technical & Non-Functional Constraints
- **`REQ-NF-013`** 출발지 **30일 내 파기**
- **`REQ-NF-015`** 취향·비고 **미수집** — 필드 부재를 증명
- **`REQ-NF-031`** 목적 제한 접근 — 감사 로그(`IN-B`)로 점검
- **§8.6.5** 보존 정책 — 이벤트·확인 상태·예약·결제 각각

### 🏁 DoD
공통 DoD 5개. 추가로 —

- [ ] **미수집 검증이 자동화되어 회귀를 막는가?**
- [ ] 목적 외 접근이 감사 로그에서 탐지되는가?
- [ ] 4종 데이터의 보존 기간이 확정되었는가?

## PRV-B · 개인 제약 정보 단말 저장 및 옵트인 {#prv-b}

**labels** `feature, frontend, privacy, priority:high, phase-1-late`
**원문** `FR-060` `FR-061`

### 🎯 Summary
- **Task ID** `PRV-B` · **Must / M (M×2)**
- **목적** 개인 제약(알레르기 등)을 **기본적으로 서버에 보내지 않는다.** 동의한 경우에만 전송한다.

### 🔗 References
- `REQ-NF-014`(단말 저장) · `REQ-NF-032`(옵트인 · 미동의 전송 차단) · §4.4 · §8.6.4
- 선행 `CLI-A`(앱 셸) · **`UX-E`**(옵트인 동의 화면)

### ✅ Task Breakdown
- [ ] **`FR-060`** 개인 제약 정보 **단말 저장** 구현
- [ ] **`FR-061`** 서버 전송 **옵트인** + **미동의 전송 차단**
- [ ] 미동의 상태에서 전송 시도가 **구조적으로 불가능**하게
- [ ] 동의 철회 경로
- [ ] 단말 저장 데이터의 초기화 경로
- [ ] 동의 이력 기록 위치 확정 **(미정 — 동의 자체가 개인정보다)**

### ⚠️ 동의 이력을 어디에 남기는가

옵트인 동의는 **증명 가능해야** 한다 — 나중에 "동의한 적 없다"는 분쟁이 생긴다.
그런데 동의 이력을 서버에 남기면 **"이 사용자가 개인 제약 정보를 가지고 있다"는 사실 자체가 서버에 남는다.**

`REQ-NF-014`의 단말 저장 원칙과 긴장 관계에 있다. **확정 필요.**

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 단말 저장**
- **Given** 사용자가 개인 제약을 입력함
- **When** 저장함
- **Then** **단말에만** 저장되고 서버로 전송되지 않는다 (`REQ-NF-014`)

**Scenario 2 · 예외 (§4.5.3) — 미동의 상태 전송 시도**
- **Given** 옵트인하지 않은 사용자
- **When** 전송을 유발하는 동작을 수행함
- **Then** **전송이 차단된다** (`REQ-NF-032`). 실수로도 나갈 수 없는 구조여야 한다

**Scenario 3 · 경계 — 동의 철회**
- **Given** 옵트인했던 사용자가 동의를 철회함
- **When** 철회함
- **Then** 이후 전송이 중단되고, **이미 전송된 데이터의 처리** **(미정 — 확정 필요)**

**Scenario 4 · 근거 무결성 — 전송 경로 전수 점검**
- **Given** 클라이언트 전 코드 경로
- **When** 개인 제약 정보의 전송 지점을 검색함
- **Then** **옵트인 게이트를 거치지 않는 경로가 0건**이다

### ⚙️ Technical & Non-Functional Constraints
- **`REQ-NF-014`** 단말 저장 원칙
- **`REQ-NF-032`** 미동의 전송 **차단** — 기본값이 차단
- **§8.6.4** 개인정보 처리 방침
- 클라이언트 저장소는 **사용자가 지울 수 있다** — 복구 불가를 안내해야 함

- [ ] 전송 경로 전수 점검이 통과했는가?
- [ ] **동의 이력 저장 위치가 확정되었는가?**
- [ ] 철회 후 기존 데이터 처리가 확정되었는가?
