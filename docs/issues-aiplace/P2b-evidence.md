### 🎯 Summary

### 🔗 References

### ✅ Task Breakdown
- [ ] 4항목 검증 로직 — 선정 이유 · 근거 속성 · 확인 일자 · 확인 주체

### ⚠️ 정렬 이전 배치가 이 태스크의 설계 조건이다

§4.5.2가 *"정렬 이전 단계 배치"* 를 규정한 이유가 있다.

```
정렬 후 필터   후보 10개 정렬 → 상위 3개 선택 → 근거 검증 → 1개 탈락 → 2개만 남음
정렬 전 검증   후보 10개 → 근거 검증 → 7개 통과 → 정렬 → 상위 3개  ✓
```

**정렬 후에 거르면 Top-3가 3개 미만이 된다.** 검증을 앞에 두어야 3개를 채울 수 있다.
그럼에도 통과 후보가 3개 미만이면 `SRC-D`의 미정 항목("3개 고정 ↔ 근거 제외 충돌")이 발동한다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 4항목 완비 통과**
- **Given** 선정 이유·근거 속성·확인 일자·확인 주체가 모두 있는 후보
- **When** 검증함
- **Then** 통과하고 정렬 대상에 포함된다

**Scenario 2 · 예외 (§4.5.3) — `Attribute` 참조 실패**
- **Given** 근거 속성이 가리키는 `attribute` 레코드가 없음
- **When** 검증함
- **Then** **탈락**하고 결락 사유가 기록된다. 참조 없는 근거는 근거가 아니다

**Scenario 3 · 경계 — `STALE` 후보**
- **Given** `verified_at + 90일`이 경과한 `STALE` 후보
- **When** 검증함
- **Then** **(미정 — 확정 필요)** `SPEC-008`의 판정을 따른다. 통과 + 경고 병기인지, 탈락인지

**Scenario 4 · 근거 무결성 — 네 소비처 일관성**
- **Given** 동일 후보를 `SRC-D` · `EVD-C` · `AGT-C` · `CLI-C`가 각각 판정함
- **When** 결과를 대조함
- **Then** **네 곳이 동일한 결론**을 낸다. 이 시나리오가 `SPEC-008`이 존재하는 이유다

### ⚙️ Technical & Non-Functional Constraints
- **§4.5.2** 정렬 이전 배치 — 파이프라인 순서가 설계 조건
- **§8.1** 근거 없는 후보 반환 **금지**
- **§8.3 규칙 1** 근거 무결성이 모든 노출의 전제
- 성능 — `SRC-D`의 p95 1,000ms 예산 안에서 후보 전수를 검증해야 한다

## EVD-B · 문장 생성 · 신선도 경고 · 판정형 차단 {#evd-b}

**labels** `feature, backend, evidence-service, priority:high, phase-1`
**원문** `FR-022` `FR-023` `FR-024`

### 🎯 Summary

### 🔗 References

### ✅ Task Breakdown
- [ ] **`FR-022`** 선정 이유 문장 생성 (외부 추론 서비스)
- [ ] **`FR-023`** 90일 신선도 경고 표기 + `STALE` 전이 반영
- [ ] **`FR-024`** **판정형 문구 차단 검증**
- [ ] 판정형 어휘 사전 구축 **(미정 — 기준이 SRS에 없다)**
- [ ] 추론 서비스 장애 시 대체 문안 (§4.5.3)
- [ ] 세션당 추론 비용 계측 (`REQ-NF-019` 12원 상한 · `TRK-E`)

### ⚠️ '판정형 문구'의 판정 기준이 없다

§8.3 규칙 3과 §1.1은 판정을 금지한다. 예시도 있다 — *"'조용하다' 같은 주관적 판정"*.
그런데 **무엇이 판정형인지 가르는 규칙이 SRS에 없다.**

| 문장 | 판정형인가 |
| --- | --- |
| "2026-08-01 매장 확인: 좌석 간 간격 1.2m" | ✗ 사실 진술 |
| "조용한 분위기입니다" | ○ 주관적 판정 |
| "소음 측정 45dB (2026-08-01 매장 확인)" | ✗ 사실 + 출처 |
| "단체 모임에 적합합니다" | **?** — 적합 판단인가 조건 매칭 진술인가 |

**세 번째 행이 경계다.** 조건 매칭 결과를 문장으로 쓰면 판정처럼 읽힌다.
`UX-C` 라이팅 가이드와 **같은 자리에서** 어휘 기준을 정해야 한다.

**차단 방식도 정해야 한다** — 어휘 사전 차단인지, 생성 후 검증인지, 둘 다인지.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 근거 문장 생성**
- **Given** 근거 4항목이 완비된 후보
- **When** 선정 이유 문장을 생성함
- **Then** 근거 속성과 확인 일자·주체가 문장에 드러나고 **판정형 표현이 없다**

**Scenario 2 · 예외 (§4.5.3) — 추론 서비스 장애**
- **Given** 문장 생성 서비스가 응답하지 않음
- **When** 후보를 반환함
- **Then** **(미정 — 확정 필요)** 대체 문안인지 후보 제외인지. 제외하면 `SRC-D` 3개 고정과 충돌

**Scenario 3 · 경계 — 90일 당일**
- **Given** `verified_at + 90일`이 정확히 경과한 후보
- **When** 표기를 생성함
- **Then** 경고가 **병기**되고 `STALE` 전이가 반영된다 (`REQ-FUNC-011`)

**Scenario 4 · 근거 무결성 — 판정형 0건**
- **Given** 생성된 문장 전수
- **When** 판정형 검증을 실행함
- **Then** **0건**이다. `REQ-NF-011` 경고 누락률 0%와 함께 이 제품의 두 불변 규칙이다

### ⚙️ Technical & Non-Functional Constraints
- **§8.3 규칙 3** 판정 금지 — **이 제품의 정체성**
- **`REQ-NF-011`** 경고 누락률 **0%**
- **`REQ-NF-019`** 세션당 추론 비용 **12원 상한** — 문장 생성이 주요 소비처
- 외부 추론 서비스 의존 — 장애 시 서비스가 멈추면 안 된다

공통 DoD 5개. 추가로 —

- [ ] 판정형 검증이 생성 문장 전수에 적용되는가?

### 🔗 References

### ✅ Task Breakdown
- [ ] **`FR-026`** 신고 접수 + **`RECHECK_REQUIRED` 전환 (≤60s)**
- [ ] **`FR-027`** 재확인 큐 등록 및 처리 — **이력 보존** (§8.6.5)

### ⚠️ 재확인을 누가 언제 하는지가 없다

`FR-027`은 *"재확인 큐 등록 및 처리"* 를 규정하지만 **처리 주체와 기한이 SRS에 없다.**

`RECHECK_REQUIRED` 상태의 후보는 `EVD-A` 검증에서 어떻게 취급되는가 — 이것도 `SPEC-008` 미정 항목이다.
**큐에 쌓이기만 하고 처리되지 않으면 그 매장은 영원히 후보에서 빠지거나, 영원히 잘못된 정보로 노출된다.**

| 미정 | 영향 |
| --- | --- |
| 처리 주체 | 운영팀? 매장 자신? 자동 재크롤링? |
| 처리 SLA | 24h? 7일? 없으면 큐가 무한히 쌓인다 |
| 처리 중 노출 여부 | `RECHECK_REQUIRED` 후보를 반환하는가 (`SPEC-008`) |

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 신고 접수**
- **Given** 사용자가 조건 불일치를 신고함
- **When** 접수함
- **Then** **60초 이내**에 해당 `Verification`이 `RECHECK_REQUIRED`로 전이하고 재확인 큐에 등록된다

**Scenario 2 · 예외 (§4.5.3) — 중복 신고**
- **Given** 이미 `RECHECK_REQUIRED` 상태인 대상에 추가 신고
- **When** 접수함
- **Then** **(제안)** 접수는 받되 상태 전이는 중복 실행하지 않고, 신고 건수는 누적한다 (KPI 정확성)

**Scenario 3 · 경계 — 60초 경계**
- **Given** 신고 접수 시각
- **When** 전이 완료 시각을 측정함
- **Then** **60초 이내**다 (`REQ-FUNC-013`)

**Scenario 4 · 근거 무결성 — 이력 보존**
- **Given** 재확인이 완료되어 상태가 갱신됨
- **When** 이력을 조회함
- **Then** **이전 확인 정보와 신고 내역이 보존**된다 (§8.6.5). 덮어쓰지 않는다

### ⚙️ Technical & Non-Functional Constraints
- **`REQ-FUNC-013`** 신고 → 전이 **≤ 60s**
- **§8.6.5** 이력 보존 — 재확인 전후를 모두 남긴다
- **Phase 1 게이트** 불일치 신고 **≤ 15%** — 이 태스크가 그 수치의 원천
- 신고는 **사용자 신뢰의 마지막 경로**다. 접수 실패는 신뢰 실패다
