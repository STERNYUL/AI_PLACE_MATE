## CLI-A · 앱 셸 · 라우팅 · 지도 내 탭 진입 {#cli-a}

**labels** `feature, frontend, client, priority:high, phase-1, foundation`
**원문** `FR-064` `FR-065`

### 🎯 Summary
- **Task ID** `CLI-A` · **Must / M (M×2)**
- **목적** 클라이언트 전체의 토대. **진입 경로가 네이버 지도 앱 안**이라는 제약이 이 태스크의 성격을 결정한다.

### 🔗 References
- §3.1(모바일 웹) · §1.2 · §3.1.1 · **ADR-006**(지도 내 탭 진입) · **R6**
- 선행 `IN-A`(환경) · 계약 `SPEC-002`

### ⚠️ R6 — 진입 경로가 자사 통제 밖이다

**ADR-006**은 네이버 지도 앱 내 탭을 진입 경로로 정했고, **R6**은 그 위험을 기록한다.

| 통제 가능 | 통제 불가 |
| --- | --- |
| 앱 셸·라우팅 구현 | 인앱 브라우저의 엔진·버전 |
| 세션 개시 로직 | 지도 앱 정책 변경 |
| 성능 최적화 | 화면 크기·안전 영역 제약 |

**인앱 브라우저는 일반 브라우저가 아니다** — 스토리지 정책, 새 창 열기, 파일 다운로드, 클립보드가 제한될 수 있다.
`CLI-C`의 공유 카드 외부 전송과 `PRV-B`의 단말 저장이 여기 걸린다. **초기에 실측해야 한다.**

### ✅ Task Breakdown
- [ ] **`FR-064`** 모바일 웹 앱 셸 · 라우팅 · API 클라이언트
- [ ] **`FR-065`** 네이버 지도 앱 **내 탭 진입** · **세션 개시**
- [ ] API 클라이언트 — `SPEC-` 계약 기반, `MOCK-` 전환 스위치
- [ ] **인앱 브라우저 제약 실측** — 스토리지 · 외부 전송 · 안전 영역
- [ ] 세션 식별자 발급 (`TRK-B` 세션 정의와 정합)
- [ ] 오류 경계 — 어느 화면에서도 빈 화면이 나오지 않게 (§8.3 규칙 5)

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 지도 내 탭 진입**
- **Given** 사용자가 네이버 지도 앱에서 탭을 엶
- **When** 앱이 로드됨
- **Then** 세션이 개시되고 조건 입력 화면으로 진입한다

**Scenario 2 · 예외 (§4.5.3) — API 응답 실패**
- **Given** 백엔드가 `5xx`를 반환함
- **When** 화면을 렌더함
- **Then** **빈 화면이 아니라** 상태와 다음 행동이 표시된다 (§8.3 규칙 5 · `UX-F`)

**Scenario 3 · 경계 — 인앱 브라우저 제약**
- **Given** 지도 앱 내 브라우저가 로컬 스토리지를 제한함
- **When** 저장을 시도함
- **Then** **(미정 — 실측 필요)** 대체 경로가 필요하다. `PRV-B` 단말 저장이 이것에 달려 있다

**Scenario 4 · 근거 무결성 — 세션 정의 정합**
- **Given** 클라이언트가 발급한 `session_id`
- **When** `TRK-B`의 세션 판정과 대조함
- **Then** **동일한 세션 경계**를 가리킨다. 어긋나면 모든 KPI 분모가 틀린다

### ⚙️ Technical & Non-Functional Constraints

- **§3.1** 모바일 웹 — 네이티브 앱이 아니다
- **`REQ-NF-006`** 성능 예산의 기반이 이 셸에서 정해진다
- **§8.3 규칙 5** 빈 화면 금지 — 오류 경계가 필수

## CLI-B · 조건 입력 및 폴백 필터 UI {#cli-b}

**labels** `feature, frontend, client, priority:high, phase-1`
**원문** `FR-066` `FR-067`

### 🎯 Summary
- **Task ID** `CLI-B` · **Must / M (M×2)**
- **목적** 사용자가 조건을 넣는 유일한 입구. **자연어 파싱 실패 시 폴백 전환을 고지**하는 것이 핵심 요구다.

### 🔗 References
- `REQ-FUNC-008`(자연어 조건 입력) · `REQ-FUNC-009`(**폴백 필터 · 전환 고지**) · §3.1.2
- 선행 `CLI-A` `UX-B` · 계약 `SPEC-002` · `MOCK-002`(파싱 실패 케이스)

### ✅ Task Breakdown

- [ ] **`FR-067`** 폴백 필터 UI + **전환 고지**

- [ ] 부분 파싱 시 채워진 필드 이월 **(미정)**
- [ ] 입력 이벤트 계측 (`CLI-E` 연동)

### ⚠️ 전환 고지는 사과가 아니다

`REQ-FUNC-009`가 전환 고지를 요구하는 이유는 **사용자가 왜 화면이 바뀌었는지 알아야** 하기 때문이다.
`SPEC-002`에서 정리한 대로 **파싱 실패는 오류가 아니라 정상 분기**다.

| 나쁜 고지 | 좋은 고지 |
| --- | --- |
| "오류가 발생했습니다" | "직접 조건을 선택해 주세요" |
| 조용히 화면 교체 | 입력한 내용을 남긴 채 필터로 전환 |

**부분 파싱된 필드를 버리면 사용자는 처음부터 다시 입력한다.** 이월 여부가 확정돼야 한다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 자연어 입력**
- **Given** 사용자가 조건을 자연어로 입력함
- **When** 전송함
- **Then** 파싱 결과가 확인 가능한 형태로 표시되고 탐색이 시작된다

**Scenario 2 · 예외 (§4.5.3) — 파싱 실패**
- **Given** 파싱이 실패함 (`MOCK-002`)
- **When** 응답을 받음
- **Then** **폴백 필터로 전환되고 전환 사실이 고지된다.** 오류 화면이 아니다 (`REQ-FUNC-009`)

**Scenario 3 · 경계 — 부분 파싱**
- **Given** 인원은 인식되고 예산은 인식되지 않음
- **When** 폴백으로 전환함
- **Then** **(미정 — 확정 필요)** 인식된 인원이 필터에 이월되는가

**Scenario 4 · 근거 무결성 — 조건 왜곡 없음**
- **Given** 사용자가 입력한 원문 조건
- **When** 파싱 결과를 표시함
- **Then** **입력하지 않은 조건이 임의로 추가되지 않는다.** 추정 조건이 결과를 좌우하면 안 된다

### ⚙️ Technical & Non-Functional Constraints
- **`REQ-FUNC-009`** 폴백 전환 시 **고지 필수**
- **§3.1.2** 화면 요건
- `MOCK-002`로 파싱 실패 케이스를 **백엔드 없이** 검증할 수 있어야 한다

### 🏁 DoD
공통 DoD 5개. 추가로 —
- [ ] 폴백 전환이 **고지와 함께** 이뤄지는가?
- [ ] 부분 파싱 이월 정책이 확정되었는가?
- [ ] 입력하지 않은 조건이 추가되지 않는가?

### 🚧 Dependencies & Blockers
- **Depends on** `CLI-A` `UX-B` `SPEC-002`
- **Blocks** `CLI-C`
- **미정 — 확정 필요** 부분 파싱 시 필드 이월 여부

### ⚠️ 클라이언트가 마지막 방어선이다

`EVD-A`가 서버에서 근거를 검증하지만, **클라이언트도 렌더 직전에 확인해야 한다.**

이유는 단순하다 — 서버 검증을 우회하는 경로(캐시, 이전 버전 응답, 목 잔존)가 실제로 생긴다.
**`REQ-NF-011`의 경고 누락률 0%는 화면에 나온 것으로만 판정된다.**
서버가 경고를 보냈어도 화면에 안 뜨면 누락이다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — Top-3 렌더**
- **Given** 근거 4항목이 완비된 후보 3곳
- **When** 화면을 렌더함
- **Then** 각 카드에 **선정 이유 · 근거 속성 · 확인 일자 · 확인 주체**가 표시된다

**Scenario 2 · 예외 (§4.5.3) — 근거 누락 응답**
- **Given** 응답에 확인 주체가 없는 후보가 섞임 (`MOCK-003`)
- **When** 렌더를 시도함
- **Then** **그 후보를 렌더하지 않고** 상태를 표시한다. 근거 없는 카드는 화면에 나오지 않는다

**Scenario 3 · 경계 — `STALE` 후보**
- **Given** 90일이 경과한 확인 정보 (`MOCK-004`)
- **When** 카드를 렌더함
- **Then** **신선도 경고가 반드시 표시**된다. 누락률 **0%** (`REQ-NF-011`)

**Scenario 4 · 근거 무결성 — 판정형 문구 0건**
- **Given** 화면에 렌더된 모든 문구
- **When** 판정형 검증을 수행함
- **Then** **0건**이다. 서버(`EVD-B`)와 클라이언트(`UX-C` 가이드)가 같은 기준을 쓴다

### ⚙️ Technical & Non-Functional Constraints

결제 요청을 보낸 뒤 인앱 브라우저가 닫히거나 지도 앱으로 돌아가면,
**사용자는 결제됐는지 모르고 우리도 모른다.**

`RSV-C`의 멱등키 미정 항목이 이 화면에서 실제 사고가 된다 — 사용자가 다시 시도하면 이중 결제다.
**클라이언트 중복 방지만으로는 부족하고 서버 멱등키가 있어야 한다.**

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 재입력 0개**
- **Given** 선택된 후보·제안의 조건
- **When** 예약 화면에 진입함
- **Then** 조건이 채워져 있고 **사용자가 입력할 필드가 0개**다 (`REQ-FUNC-015`)

**Scenario 2 · 예외 (§4.5.3) — 결제 중 이탈**

- **When** 다시 진입함
- **Then** **현재 결제 상태가 조회되어 표시**된다. 무조건 재시도 화면을 띄우지 않는다

**Scenario 3 · 경계 — 취소 시한**
- **Given** 예약 시각 2시간 전 경계
- **When** 취소 화면에 진입함
- **Then** **(미정)** 환불 가능 여부가 명시된다. 판정은 `RSV-D` 확정을 따른다

**Scenario 4 · 근거 무결성 — 금액 표기 일치**
- **Given** 화면에 표시된 결제 금액
- **When** 실제 승인 금액과 대조함
- **Then** **일치한다.** 표기와 청구가 다르면 그대로 분쟁이다

### ⚙️ Technical & Non-Functional Constraints

### ⚠️ 4G 실측이 요구의 핵심이다

`REQ-NF-006`은 LCP 2.5초를 **4G 실측 조건**으로 규정한다.
개발 장비의 wifi에서 측정한 값은 이 요구를 충족한 증거가 되지 않는다.

**측정 방법이 요구의 일부다** — 어떤 네트워크 프로파일로, 어떤 단말에서, 몇 회 측정해 p95를 내는지.
`IN-C` 관측 체계와 같은 자리에서 정해야 한다.

**그리고 인앱 브라우저에서 측정해야 한다** (`CLI-A` R6) — 일반 모바일 브라우저 값과 다를 수 있다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — LCP 달성**
- **Given** 4G 프로파일 · 지도 앱 내 탭
- **When** 초기 화면을 로드함
- **Then** **LCP p95 ≤ 2.5s** (`REQ-NF-006`)

**Scenario 2 · 예외 (§4.5.3) — 이벤트 전송 실패**
- **Given** 네트워크가 끊김
- **When** 이벤트가 발생함
- **Then** **버퍼링 후 재전송**된다. 유실되면 KPI 누락률이 올라가 `TRK-D` 미공표로 이어진다

**Scenario 3 · 경계 — 22종 전수 발생**
- **Given** 전체 사용자 여정을 완주함
- **When** 발생 이벤트를 수집함
- **Then** **클라이언트 발생분이 빠짐없이 발생**한다. 어느 이벤트가 클라이언트 책임인지가 확정돼 있어야 한다

**Scenario 4 · 근거 무결성 — 개인정보 미포함**
- **Given** 전송되는 모든 이벤트
- **When** 페이로드를 검사함
- **Then** 취향·비고·출발지 원문이 **평문으로 실리지 않는다** (`REQ-NF-015` · `REQ-NF-013`)
