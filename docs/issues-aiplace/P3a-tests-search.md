**웨이브:** 제작 순서 11번 · **Phase 0~1**
**근거:** `[SRS]ai-place -mate-SRSv1.0.md` v1.9 **§5.1** · 정본 [`task-extraction-assessment-aiplace.md`](../task-extraction-assessment-aiplace.md) Step 3

> **이 웨이브가 존재하는 이유 — 원장 v1.1에 검증 태스크가 0건이었다.**
> SRS §5.1은 `TC-FUNC-001`~`TC-NF-032` 총 **59개 테스트 케이스 ID를 이미 부여**했는데,
> 111개 태스크 어디에도 그것을 실행하는 태스크가 없었다.
> **"AC를 쓸 수 없는 요구사항은 완료 판정도 할 수 없다"** 는 문제가 여기서 반대편으로 드러난다 —
> **TC ID가 있어도 실행 태스크가 없으면 판정되지 않는다.**

## 이 웨이브의 두 번째 목적 — AC 역류

각 `TEST-` 태스크를 쓰는 과정에서 **구현 이슈의 DoD가 보강된다.**

```
TEST-00N 작성 → "이 TC를 실행하려면 무엇이 필요한가" → 빠진 조건 발견
                                                        ↓
                                    P1b·P2a·P2b 등의 DoD로 역류
```

**역류가 이 웨이브의 산출물이다.** 테스트를 실제로 설계해야만 보이는 공백이 있다.

구현 이슈의 AC 4시나리오와 같은 구조이며, **여기서는 그것을 자동화한다.**

## 이 웨이브에서 구현 이슈로 역류할 항목

| # | 발견 | 역류 대상 | 성격 |
| --- | --- | --- | --- |
| 1 | **정규화 평가셋 부재** — 92% 기준의 정답셋이 없다 | `IDX-C` DoD | **차단** |
| 2 | **예산 판정 기준값 미정** — 케이스를 쓸 수 없다 | `SRC-B` DoD | **차단** |
| 3 | 유사도 판정 기준 미정 | `SRC-C` DoD | 차단 |
| 4 | 파싱 실패 응답 코드 (`SPEC-002` `422`) | `SPEC-002` | 확정 |
| 5 | 거짓 양성 0건 요구 — `SRC-B`에 명시 필요 | `SRC-B` DoD | 보강 |
| 6 | 대체 표기 누락 0건 요구 | `SRC-C` DoD | 보강 |
| 7 | 3% · 예산 · 유사도의 **경계 판정(이하/미만)** 일괄 미정 | 다수 | 확정 |

**1·2·3번은 테스트를 착수조차 할 수 없게 만든다.**
정본이 예고한 *"AC 내용이 구현 이슈 DoD로 역류"* 가 실제로는 **차단 관계**로 나타났다 —
평가셋과 판정 기준이 없으면 검증 태스크는 코드 한 줄도 쓸 수 없다.

**7번은 이 프로젝트 전반의 패턴이다.** SRS가 임계값을 주면서 **이상/초과를 명시하지 않는다.**
개별 확정보다 **일괄 규약**(예: 모든 임계값은 "이하 포함")을 정하는 편이 낫다.
