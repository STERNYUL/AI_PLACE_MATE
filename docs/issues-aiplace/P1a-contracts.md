## 이 문서가 첫 번째인 이유

평가서 §3이 규정한 그대로다 — **여기가 흔들리면 이후 문서가 전부 무효**다.

여러 태스크가 같은 계약을 공유한다. `SRC-D`(FR-019 · `POST /v1/query`)와 `EVD-C`(FR-025 · `POST /v1/share-cards`)는
둘 다 *"근거 4항목이 없으면 어떻게 하는가"* 를 써야 하고, `EVD-A`(FR-021)·`AGT-C`(FR-046)·`CLI-C`(FR-068)은
셋 다 *"근거 4항목이란 무엇인가"* 를 정의해야 한다.

**계약을 먼저 한 번 확정하지 않고 태스크별로 본문을 쓰면 세 문서가 미묘하게 다른 세 정의를 갖는다.**
그 차이는 코드 리뷰가 아니라 통합 테스트에서 드러난다.

### 확정할 규약

| 항목 | 규약 | 근거 |
| --- | --- | --- |
| 형식 | 요청·응답 JSON | §8.1.1 "데이터 형식" |

### 상태 코드 체계 (제안 — SRS에 `400`·`5xx`만 존재)

| 코드 | 사용 조건 | SRS 근거 |
| --- | --- | --- |
| `200` | 정상 | — |
| `400` | 계약 위반 — **근거 4항목 누락**(§4.5.1) · 등록 속성 미참조 문구(§8.1.1) · 조건 2개 미만 | §8.1.1 명시 |
| `401` | 미인증 | `REQ-NF-018` |
| `422` | 파싱 불가 **(제안)** | `REQ-FUNC-009` 폴백 전환과 구분 필요 |
| `5xx` | 서버 오류 — **`REQ-NF-008` 오류율 산정 대상** | `REQ-NF-008` |

**`422`를 제안하는 이유가 있다.** `REQ-FUNC-009`는 파싱 실패 시 **구조화 필터로 폴백**하라고 규정한다.
즉 파싱 실패는 오류가 아니라 **정상 흐름의 분기**다. `400`으로 반환하면 클라이언트가 폴백을 트리거할 수 없고,
`REQ-NF-009`(파싱 실패율 5분 윈도 집계)의 분모도 오염된다.

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 추적 ID 전파**
- **Given** `X-Request-Id`가 없는 요청
- **When** Gateway를 통과해 3개 서비스를 거침
- **Then** ID가 생성되어 전 구간에 전파되고, `IN-C`(IN-004) 계측에서 **하나의 요청으로 추적**된다

**Scenario 2 · 예외 (§4.5.3) — 외부 추론 서비스 장애**
- **Given** 조건 파서(`SRC-A` · FR-011)가 응답하지 않음
- **When** `POST /v1/query`를 호출함
- **Then** `422`가 아니라 **폴백 전환 신호**를 반환하고, 클라이언트가 구조화 필터 UI로 전환한다. `5xx`가 아니므로 `REQ-NF-008` 오류율에 포함되지 않는다

**Scenario 3 · 경계 — 오류율 산정 경계**
- **Given** `4xx` 100건 · `5xx` 1건이 발생한 1,000건 구간
- **When** `REQ-NF-008` 오류율을 산정함
- **Then** **0.1%** 로 계산된다 (`4xx`는 분자에서 제외)

**Scenario 4 · 근거 무결성 — 해당 없음**
- 이 태스크는 후보·제안을 반환하지 않는다. `SPEC-008`이 담당한다

### ⚙️ Technical & Non-Functional Constraints
- **`REQ-NF-008`** — 결제 API 오류율 **≤ 0.1%**, 분리 계측
- **`REQ-NF-018`** — 전 API 인증 강제
- **`REQ-NF-026`** — 전송 구간 TLS 1.3
- 이 규약은 **8개 API·8건 Mock·클라이언트 13건에 모두 적용**된다. 나중에 바꾸면 전량 수정이다

### 확정해야 할 핵심 3가지

**① 누락 판정 시점.** §4.5.2는 *"정렬 이전 단계 배치"* 를 규정한다.
즉 근거가 없는 후보는 **정렬에 참여하지 않는다.** 정렬 후 필터링이 아니다 — 그러면 Top-3가 3개 미만이 될 수 있다.

**② `STALE` 상태의 근거는 유효한가. (미정 — 확정 필요)**
`REQ-FUNC-011`은 90일 초과 시 **경고를 병기**하라고만 한다. 제외하라고 하지 않는다.
그런데 §8.1은 *"근거 없는 후보 반환 금지"* 다. **`STALE`이 "근거 없음"인지 "근거 있으나 오래됨"인지 SRS가 구분하지 않는다.**

| 해석 | 결과 |
| --- | --- |
| `STALE` = 근거 있음 (경고만) | 후보로 반환. `REQ-FUNC-011` 문언에 충실 |
| `STALE` = 근거 없음 | 후보에서 제외. `REQ-NF-011` 경고 누락률 0%에 안전하나 **Fill이 줄어든다** |

**③ `RECHECK_REQUIRED` 상태.** 불일치 신고 수신 시 전이된다(§8.2). 이 상태의 후보 취급도 같은 문제를 갖는다.
