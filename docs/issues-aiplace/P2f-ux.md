**웨이브:** 제작 순서 9번 · **Phase 0 / 1 / 1말**
**근거:** `SRS-ai-place-v1.0.md` v1.9 · **원장** v1.1
**대응 구현:** [`P2e-client.md`](P2e-client.md) — `CLI-A`~`CLI-E`

> **디자인 태스크는 구현 태스크가 아니다.** 이 문서의 산출물은 **화면·플로우·가이드**이며 코드가 아니다.
> 같은 요구사항(`REQ-FUNC-009` 등)을 `UX-B`와 `CLI-B`가 각각 다루지만,
> **`UX-`는 "무엇을 어떻게 보여줄지", `CLI-`는 "그것을 어떻게 만들지"** 로 갈린다.
> `UX-`가 선행이며, 완료 판정도 **디자인 산출물의 존재와 합의**로 한다.

## UX-A · 디자인 시스템 및 모바일 성능 가이드 {#ux-a}

**labels** `design, ux, foundation, priority:high, phase-0, needs-pm-approval`
**원문** `UX-001` `UX-013`

### 🎯 Summary
- **Task ID** `UX-A` · **Must / M (M×2)** · **Phase 0**
- **목적** 이후 모든 화면의 토대. **성능 가이드가 함께 오는 이유는 `REQ-NF-006`이 디자인 결정으로 정해지기 때문**이다.

### 🔗 References
- §3.1.2(화면 요건) · **`REQ-NF-006`**(LCP ≤ 2.5s · 4G) · §6.3

### ⚠️ 이 태스크의 절반은 SRS 근거가 없다

| 부분 | 근거 | 상태 |
| --- | --- | --- |
| `UX-013` 모바일 성능 가이드 | `REQ-NF-006` · §6.3 | 근거 있음 |

**SRS에 없는 것을 만들지 않는다**는 원칙과, **디자인 시스템 없이 화면을 만들 수 없다**는 현실이 부딪힌다.
원장은 이것을 유일한 근거 없는 항목으로 표기하고 **PM 승인 대상**으로 남겼다.

**승인 없이 착수하면 범위 확장이 된다.** 승인 시에는 SRS §3.1.2에 시각 설계 범위를 명시하는 것이 정합적이다.

- [ ] **`UX-013`** 모바일 성능 가이드 — LCP 예산을 디자인 결정으로 환산

- [ ] 이미지·폰트 예산 — LCP 2.5s 역산
- [ ] 상태 컴포넌트 규격 — 로딩·빈 상태·오류 (`UX-F` 기반)

### 성능 가이드가 디자인 산출물인 이유

`REQ-NF-006`의 LCP 2.5초는 구현 최적화만으로 지킬 수 없다.
**히어로 이미지의 크기, 웹폰트의 개수, 첫 화면의 요소 수가 디자인 단계에서 이미 예산을 소진한다.**

가이드는 "빠르게 만들라"가 아니라 **숫자로 된 예산**이어야 한다 — 첫 화면 이미지 N KB 이하, 웹폰트 N종 이하 등.
`CLI-E`가 그 예산 안에서 측정한다.

**Scenario 3 · 경계 — LCP 예산 초과 디자인**

**Scenario 4 · 근거 무결성 — 근거 표시 슬롯**
- **Given** 후보 카드 컴포넌트

### 🔗 References
- `REQ-FUNC-008`(자연어 조건 입력) · **`REQ-FUNC-009`**(폴백 필터 · **전환 고지**) · §3.1.2
- 선행 `UX-A` · 대응 구현 `CLI-B`

### ✅ Task Breakdown
- [ ] **`UX-002`** 조건 입력 화면 설계 — 자연어 입력
- [ ] **`UX-003`** 폴백 필터 UI + **전환 고지 카피**
- [ ] 전환 시 입력 내용 보존 표현
- [ ] 부분 파싱 결과 표시 방식 **(미정 — `CLI-B`와 동일 항목)**
- [ ] 파싱 결과 확인·수정 경로
- [ ] 입력 예시 제시 — 무엇을 쓸 수 있는지 알려주기

### ⚠️ 전환 고지의 카피가 이 태스크의 산출물이다

`REQ-FUNC-009`는 전환을 **고지**하라고만 규정한다. **무엇이 좋은 고지인지는 디자인 판단**이다.

파싱 실패는 §4.5.3의 **정상 분기**이지 오류가 아니다(`SPEC-002` 참조).
그런데 카피가 "오류가 발생했습니다"가 되면 **정상 동작이 실패로 전달**된다.

| 원칙 | 적용 |
| --- | --- |
| 사용자를 탓하지 않는다 | "잘못 입력하셨습니다" ✗ |
| 다음 행동을 준다 | "조건을 직접 선택해 주세요" ○ |
| 입력을 버리지 않는다 | 인식된 값은 필터에 채워 둔다 |

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — 자연어 입력 흐름**
- **Given** 조건 입력 화면
- **When** 사용자가 자연어를 입력함
- **Then** 파싱 결과가 **확인·수정 가능한 형태**로 표시된다

**Scenario 2 · 예외 (§4.5.3) — 폴백 전환**
- **Given** 파싱이 실패함
- **When** 폴백 필터로 전환함
- **Then** **전환이 고지되고, 오류가 아니라 다음 행동으로 읽히는 카피**가 표시된다

**Scenario 3 · 경계 — 부분 파싱**
- **Given** 일부 조건만 인식됨
- **When** 화면을 설계함
- **Then** **(미정)** 인식분 이월 표현. `CLI-B`와 같은 결정을 공유한다

**Scenario 4 · 근거 무결성 — 임의 조건 추가 없음**
- **Given** 파싱 결과 화면
- **When** 표시 내용을 확인함
- **Then** **사용자가 말하지 않은 조건이 기본값으로 채워지지 않는다.** 채운다면 그 사실이 보여야 한다

### ⚙️ Technical & Non-Functional Constraints
- **`REQ-FUNC-009`** 전환 고지 필수
- **§4.5.3** 파싱 실패는 정상 분기 — 카피가 이를 반영
- **§3.1.2** 화면 요건
- 모바일 · 지도 앱 내 탭 — 입력 영역이 키보드에 가리지 않아야 한다

공통 DoD 5개. 추가로 —
- [ ] 전환 고지 카피가 **오류 어조가 아닌가?**
- [ ] 부분 파싱 표현이 `CLI-B`와 합의되었는가?
- [ ] 말하지 않은 조건이 조용히 채워지지 않는가?

## UX-C · Top-3 카드 · 신선도 경고 · 근거 라이팅 가이드 {#ux-c}

**labels** `design, ux, evidence, priority:high, phase-1, identity`
**원문** `UX-004` `UX-005` `UX-015`

### 🎯 Summary
- **Task ID** `UX-C` · **Must / H (H×1+M×2)**
- **목적** **§1.1의 제품 정체성이 화면 언어가 되는 지점.** 라이팅 가이드가 `EVD-B`의 판정형 차단 기준과 **같은 문서**여야 한다.

### 🔗 References
- **§1.1**(판정하지 않고 재료를 제공한다) · **§8.3 규칙 3**(판정 금지)
- `REQ-FUNC-002`(Top-3) · `REQ-FUNC-010`(선정 이유) · `REQ-FUNC-011`(90일 신선도) · `REQ-FUNC-014`
- §3.1.2 · 선행 `UX-A` · 대응 구현 `CLI-C` · 서버 대응 `EVD-B`

### ✅ Task Breakdown
- [ ] **`UX-004`** Top-3 카드 설계 — **근거 4항목 배치**
- [ ] **`UX-005`** 신선도 경고 표기 설계 — `FRESH` · `STALE` · `RECHECK_REQUIRED`
- [ ] **`UX-015`** **근거 라이팅 가이드** — 판정형 어휘 기준
- [ ] **`EVD-B`와 판정형 기준 통합** — 서버 검증과 같은 사전
- [ ] 후보 3개 미만 시 화면 (`SRC-D` 미정 연동)
- [ ] 경고 표기의 시각 위계 — 경고가 묻히면 누락과 같다

### ⚠️ 라이팅 가이드가 서버 검증 기준이 된다

`EVD-B`는 생성 문장에서 **판정형 문구를 차단**해야 하는데, **무엇이 판정형인지 SRS에 규칙이 없다**(P2b 미정 1번).

**그 기준을 만드는 것이 `UX-015`다.** 그리고 그 기준은 두 곳에서 쓰인다 —

```
UX-015 라이팅 가이드
   ├─→ EVD-B 서버 문장 생성 시 판정형 차단 사전
   └─→ CLI-C 화면 카피 작성 기준
```

**두 곳이 다른 기준을 쓰면 서버가 통과시킨 문장이 화면에서 판정형이 된다.**
가이드는 디자인 문서이자 **검증 규격**이다.

| 판정형 (금지) | 사실 진술 (허용) |
| --- | --- |
| "조용한 분위기입니다" | "소음 45dB · 2026-08-01 매장 확인" |
| "단체에 적합합니다" | "8인 테이블 보유 · 2026-08-01 매장 확인" |
| "가성비가 좋습니다" | "인당 18,000원 · 2026-07-15 메뉴판 확인" |

### 🧪 Acceptance Criteria

**Scenario 1 · 정상 — Top-3 카드**
- **Given** 근거 4항목을 가진 후보 3곳
- **When** 카드를 설계함
- **Then** **선정 이유 · 근거 속성 · 확인 일자 · 확인 주체**가 모두 카드 안에 자리를 갖는다

**Scenario 2 · 예외 (§4.5.3) — 후보 3개 미만**
- **Given** 근거 검증 통과 후보가 2곳
- **When** 화면을 설계함
- **Then** **(미정)** 2곳만 보이는가, 상태를 알리는가. `SRC-D`의 "3개 고정 ↔ 근거 제외" 충돌과 같은 항목

**Scenario 3 · 경계 — `STALE` 카드**
- **Given** 90일 경과 후보
- **When** 카드를 설계함
- **Then** **경고가 묻히지 않는 위계**로 표시된다. 작게 회색으로 넣으면 `REQ-NF-011` 0%를 형식만 충족한다

**Scenario 4 · 근거 무결성 — 라이팅 가이드 일치**
- **Given** `UX-015` 가이드와 `EVD-B` 판정형 사전
- **When** 대조함
- **Then** **동일하다.** 별도 문서라면 한쪽이 정본이고 다른 쪽이 참조한다

### ⚠️ 공유 카드는 앱 밖에서 혼자 읽힌다

카드는 메신저·SNS로 나가 **우리 화면의 맥락 없이** 읽힌다.
확인 일자와 주체가 카드 이미지 안에 없으면, **근거 없는 추천으로 유통된다.**

`EVD-C`가 근거 누락 시 `400`을 반환하는 이유가 이것이고,
**템플릿이 4항목을 담을 자리를 확보하지 못하면 서버 검증이 무의미해진다.**

- **When** 카드를 만들려 함
- **Then** **생성되지 않는다** (`EVD-C` `400`). 디자인에도 "누락 시 대체 템플릿"을 두지 않는다

**Scenario 3 · 경계 — 긴 근거 문장**
- **Given** 선정 이유가 템플릿 영역을 넘음
- **When** 렌더함
- **Then** **잘리지 않는 처리**가 필요하다. 잘린 근거는 왜곡이다

**Scenario 4 · 근거 무결성 — 신고 후 피드백**
- **Given** 사용자가 불일치를 신고함
- **When** 완료 화면을 봄
- **Then** **재확인 절차가 진행됨이 안내**된다. `EVD-D`의 처리 SLA 미정이 여기서 카피 공백이 된다

### ⚙️ Technical & Non-Functional Constraints
- **`REQ-FUNC-012`** 공유 카드 — 근거 포함
- **§8.3 규칙 1** 외부 유통물에도 근거 무결성 적용
- **회수 불가** — 나간 카드는 되돌릴 수 없다
- 신고 플로우는 **신뢰의 마지막 경로** — 마찰이 크면 아무도 신고하지 않는다

### ⚠️ 옵트인 동의는 '받는 것'이 아니라 '이해시키는 것'이다

`REQ-NF-014`는 개인 제약을 **단말에 저장**한다고 규정한다. `REQ-NF-032`는 서버 전송을 옵트인으로 한다.
**사용자 입장에서 이 둘의 차이가 보이지 않으면 동의는 형식이 된다.**

동의 화면이 답해야 하는 것 —

| 질문 | 답해야 할 내용 |
| --- | --- |
| 무엇이 전송되는가 | 알레르기 등 개인 제약 항목 |
| 동의하지 않으면 | 단말에만 남고 기능 일부가 제한 |
| 언제까지 | 보존 기간 (`PRV-A` §8.6.5 미정) |
| 되돌릴 수 있는가 | 철회 경로 |

**보존 기간이 미정이면 동의 화면 카피를 완성할 수 없다.** `PRV-A`의 미정 항목이 여기서 막힌다.
