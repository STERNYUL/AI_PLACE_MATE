## 0. 왜 순서가 문제인가

원장의 111건은 **의존성 순서**로 정렬돼 있다. 그런데 **본문 작성 순서는 의존성 순서와 다르다.**

풀버전 본문에는 Acceptance Criteria와 API 계약이 들어간다. 그런데 여러 태스크가 **같은 계약을 공유**한다 —
`FR-019`(`POST /v1/query`)와 `FR-025`(`POST /v1/share-cards`)는 둘 다 "근거 4항목이 없으면 어떻게 하는가"를 써야 하고,
`FR-021`·`FR-046`·`FR-068`은 셋 다 "근거 4항목이란 무엇인가"를 정의해야 한다.

**이 공통 계약을 먼저 한 번 확정하지 않고 태스크별로 본문을 쓰면, 세 문서가 미묘하게 다른 세 개의 정의를 갖게 된다.**
그 차이는 코드 리뷰가 아니라 통합 테스트에서 드러난다.

> **원칙 — 계약을 먼저, 구현을 나중에.**
> W0에서 공유 계약을 **한 번** 확정하고, 이후 모든 태스크 본문은 그것을 **참조만** 한다. 재정의하지 않는다.

## 4. 본문 추출 지시문 (재사용 프롬프트)

각 웨이브를 뽑을 때 아래를 그대로 쓴다. `{ }` 안만 교체한다.

```
역할: 시니어 Technical Project Manager / System Architect

대상: TASKS-ai-place-v1.0.md 의 {웨이브 ID} — 태스크 {ID 목록}
템플릿: .github/ISSUE_TEMPLATE/aiplace_feature_task.md
근거: [SRS]ai-place -mate-SRSv1.0.md (SRS-AIPLACE-MVP-001 v1.9)
확정된 공유 계약: docs/issues-aiplace/W0-contracts.md (SPEC-A~G)

지시
1. 각 태스크마다 템플릿의 전 항목을 채운 풀버전 본문을 작성한다.
   해당 없는 행은 지우고, 채우지 못한 항목은 "미정 — 확정 필요"로 남긴다. 빈칸 금지.
2. Acceptance Criteria는 SRS 인수 기준 열을 GWT 시나리오로 전개한다.
   시나리오마다 숫자·경계·측정 조건 셋을 넣는다.
   정상 1건 + 예외 1건(§4.5.3에서 가져올 것) + 경계·동시성 1건을 최소로 한다.
   후보나 제안을 반환하는 태스크는 근거 무결성 시나리오를 추가한다.
3. Technical & Non-Functional Constraints의 수치는 SRS 원문에서 그대로 옮긴다.
   반올림하거나 요약하지 않는다.
4. 공유 계약(SPEC-A~G)은 참조만 하고 재정의하지 않는다.
5. Dependencies는 원장의 선행 태스크 열과 일치해야 한다. 새 의존성을 발명하지 않는다.
6. SRS에 근거가 없는 내용을 추가하지 않는다.
   판정 수치를 SRS에서 찾을 수 없으면 Blockers에 확정 담당자와 기한을 함께 적는다.
```
