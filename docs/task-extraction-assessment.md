**평가 기준:** 사용자 제시 표준 방법론 4단계 — 계약·데이터 → 로직(CQRS) → AC→테스트 → NFR·의존성

## 2. Step별 상세 진단

### Step 1-1 · 데이터베이스 Task — 🟢 충족

현재 `FR-001~009`가 그 역할을 한다. SRS §6.2 enum 11종과 §6.4 테이블 7개를 빠짐없이 덮는다(부록 B-2 확인).

| 현재 ID | 방법론 유형 | 비고 |
| --- | --- | --- |
| FR-001~004 | `[DB]` 데이터 모델 정의 | enum 11종 |
| FR-005 | `[DB]` 확장 패턴 | REQ-NF-005 |
| FR-006~009 | `[DB]` 스키마·마이그레이션 | 테이블 7개 + 구체화 뷰 |

**조치:** 유형 접두어 표기만 추가. 태스크 자체는 수정 불필요.

**단, 마이그레이션 스크립트가 명시되지 않았다.** 방법론 예시(`[DB] ... 마이그레이션 스크립트 작성`)는 스크립트를 산출물로 지목한다.
현재 FR-006~009의 Feature 명은 "DB 스키마 구축"으로, 마이그레이션 산출물 여부가 불명확하다. **본문 작성 시 Task Breakdown에 명시할 것.**

### Step 1-2 · API Spec Task — 🟡 구현과 혼재

**진단.** 현재 API 태스크 10건은 **계약 정의와 구현을 한 태스크에 묶고 있다.**

| 현재 | 문제 |
| --- | --- |
| `FR-016 API — GET /audience/profiles/{userId} 프로파일 조회` | DTO 정의 · 에러코드 정의 · 서비스 로직 · 컨트롤러가 한 덩어리 |

방법론은 이를 분리한다 — `[API Spec] ... Request/Response DTO 및 에러 코드 정의`.
**이 분리가 이 프로젝트에서 특히 중요한 이유**는 §3이 마이크로서비스를 4개로 쪼갰기 때문이다.
계약이 먼저 얼지 않으면 네 팀의 병렬 개발이 착시가 되고, 통합 시점에 전부 다시 맞춘다.

**조치 — 10건 신설 (구현 태스크에서 계약 부분 분리).**

| 신설 ID (제안) | 계약 대상 | 분리되는 구현 태스크 |
| --- | --- | --- |
| `SPEC-001` | `GET /audience/profiles/{userId}` | FR-016 |
| `SPEC-002` | `POST .../segments` | FR-017 |
| `SPEC-003` | `POST .../behavioral-signals` | FR-018 |
| `SPEC-004` | `POST /campaigns` | FR-026 |
| `SPEC-005` | `PUT /campaigns/{id}/targeting` | FR-027 |
| `SPEC-006` | `GET /campaigns/{id}/performance` | FR-028 |
| `SPEC-007` | `POST /ads/request` **(최우선)** | FR-037 |
| `SPEC-008` | `POST /ads/events/click` | FR-038 |
| `SPEC-009` | `POST /tracking/events` | FR-040 |
| `SPEC-010` | `GET /tracking/campaigns/{id}/metrics` | FR-045 |

**공통 규약도 태스크여야 한다.** 인증 헤더 · 오류 응답 형식 · 요청 추적 ID · 소프트 삭제 기본 필터는
10개 계약에 모두 걸리므로 `SPEC-000`(공통 규약 확정)을 앞에 두는 것이 옳다. → **총 11건 신설**

### Step 1-3 · Mock 데이터 Task — 🔴 전무

**82건 중 Mock 관련 태스크가 하나도 없다.** 이것이 이번 평가에서 가장 실질적인 결함이다.

**왜 결함인가.** 부록 A-2의 크리티컬 패스는 다음과 같다.

```
FR-012 (Audience) ┐
                  ├→ FR-032 → FR-034 → FR-037
FR-021 (Campaign) ┘
```

Ad Serving Engine은 **Audience와 Campaign이 둘 다 완성돼야** 통합 테스트를 시작할 수 있다.
Mock이 없으면 Ad Serving 팀은 앞의 두 팀을 기다리며 대기하고, **크리티컬 패스가 그만큼 길어진다.**
Mock 4건을 넣으면 Ad Serving이 계약만으로 착수할 수 있어 **직렬 구간이 병렬로 바뀐다.**

**조치 — 4건 신설.**

| 신설 ID (제안) | 대상 | 소비 주체 |
| --- | --- | --- |
| `MOCK-001` | Audience Service 응답 모킹 | Ad Serving (FR-029·030) |
| `MOCK-002` | Campaign Service 응답 모킹 | Ad Serving (FR-029·030·034) |
| `MOCK-003` | Ad Serving 응답 모킹 | 클라이언트 · UI (FR-046·047, UX-002·003) |
| `MOCK-004` | Tracking 수집·조회 모킹 | Campaign 성과 조회(FR-028) · 대시보드(UX-006) |

**의존성:** 각 `MOCK-00n`은 대응 `SPEC-00n` 완료 후 착수. 구현 태스크와는 **무관하게 병렬**.

### Step 2 · CQRS 분해 — 🔴 미적용

**진단.** 현재 절단 기준은 **서비스 경계와 엔드포인트**다. 방법론이 요구하는 **Read/Write 분리**가 적용되지 않았다.

**가장 명확한 위반 사례.**

| 현재 | 문제 |
| --- | --- |
| `FR-019 캠페인 CRUD (CampaignManager)` | Create·Read·Update·Delete가 한 태스크. **CQRS의 정반대** |

CRUD 묶음은 진척 측정도 막는다. "캠페인 CRUD 60% 완료"는 의미가 없는 보고다.
(이 문서는 이미 REQ-FUNC-003의 단일성 위반을 지적해 FR-019/021/022로 쪼갰으나, **FR-019 내부는 여전히 묶여 있다.**)

**조치 — 3건 분할.**

| 현재 | 분할안 |
| --- | --- |
| FR-019 캠페인 CRUD | `FR-019a [Command]` 캠페인 생성·수정·삭제 / `FR-019b [Query]` 캠페인 단건·목록 조회 |
| FR-041 성과 지표 산출 | `FR-041 [Query]` 유지 (읽기 집계) |
| FR-043 5분 주기 집계 배치 | `FR-043 [Command]` 유지 (구체화 뷰 갱신 = 쓰기) |

#### CQRS 관점이 드러낸 설계 결함 — 주목할 것

`FR-037 POST /ads/request`는 **읽기 경로 안에서 쓰기를 수행한다.**

| 단계 | 성격 |
| --- | --- |
| FR-029·030·031 후보 조회 | **Query** |
| FR-034 수익 최적화 선택 | **Query** (계산) |
| **FR-035 예산 검증·차감** | **Command** ← 읽기 경로 안의 쓰기 |
| FR-033 단계 기록 | Command (비동기 가능) |

**이것이 부록 D의 D-02(예산 초과 집행)가 발생하는 구조적 원인이다.**
초당 1,000건이 흐르는 Query 경로에 Command가 끼어 있고, 그 Command에 동시성 제어가 없다.
방법론의 CQRS 렌즈를 적용하면 이 결함이 **태스크 구조 단계에서 드러난다** — 현재 절단으로는 보이지 않는다.

**권고:** `FR-035`를 독립 `[Command]` 태스크로 명확히 표기하고, 동시성 제어를 Task Breakdown의 필수 항목으로 못박을 것.

### Step 3 · AC → 테스트 Task 변환 — 🟡 AC 필드 자체가 없음

**진단 ①  테스트 태스크는 있다.** `QA-001~014`가 SRS §5의 TC ID와 §4.2 검증 방식 열에 1:1 대응한다(부록 B-4).
커버리지도 13/13이다. **이 부분은 방법론을 충족한다.**

**진단 ②  그러나 AC가 문서에 없다.** 현재 82건의 표는 6개 열이다.

```
Task ID | Epic | Feature | 관련 SRS 섹션 | 선행 태스크 | 복잡도
```

**Acceptance Criteria 열이 없다.** 방법론의 Step 3 Tip —
*"추출된 AC 내용들은 Step 2 Feature 이슈의 DoD 체크리스트 항목으로 바로 삽입됩니다"* — 이 흐름이 성립하지 않는다.
삽입할 원본이 문서에 존재하지 않기 때문이다.

**진단 ③  AC를 채울 수 없는 태스크가 있다.** 부록 D의 13개 미정의 항목이 걸린 태스크는
Then 절에 판정 수치를 넣을 수 없다. AC 열을 만들면 **어느 태스크가 AC를 못 쓰는 상태인지가 표에서 바로 보인다** — 이것이 오히려 이득이다.

**조치 — 열 2개 신설.**

| 신설 열 | 내용 |
| --- | --- |
| `인수 기준 출처` | SRS §4.1·§4.2의 해당 인수 기준 문장 (또는 "원문 부재") |
| `AC 작성 가능` | ✅ 가능 / ⚠️ 부분 / 🔴 불가(부록 D 항목번호) |

부록 B-5의 "인수 판정 가능성 62%"가 이 열로 태스크 단위까지 내려온다.

### Step 4-1 · NFR → Infra/Sec Task — 🟢 충족

`NF-001~011`이 REQ-NF-001~005를 전부 덮는다. 방법론 예시와 대조하면 대응이 정확하다.

| 방법론 예시 | 현재 태스크 |
| --- | --- |
| `[Infra] ... p95 검증을 위한 k6 부하 테스트 스크립트 작성` | NF-003 (부하 테스트 프로그램) · NF-005 · QA-009 · QA-010 |
| `[Sec] ... 암호화 및 로깅 마스킹 파이프라인 구축` | NF-008 (인증) · NF-009 (인가) · NF-010 (보안 감사) |

**조치:** `[Infra]`(NF-001~007, NF-011)와 `[Sec]`(NF-008~010) 구분 표기.

**추가 권고 — 마스킹 태스크 부재.** 방법론 예시는 로깅 마스킹을 명시적 태스크로 든다.
현재 NF-008~010은 인증·인가·감사만 다루고, **개인정보(연령·소득·지역) 로깅 마스킹 태스크가 없다.**
D-04(개인정보)와 직결되므로 `NF-012 [Sec] 개인정보 로깅 마스킹 파이프라인` 신설을 권고한다.
SRS 원문 근거는 REQ-NF-004 + §6.2 `IncomeSegment`의 민감 정보 성격이다.

### Step 4-2 · 의존성 매핑 — 🟢 충족, 한 방향만

**진단.** `선행 태스크` 열 + 부록 A의 Mermaid 도식 4종으로 이미 잘 갖춰져 있다.
방법론이 요구하는 오케스트레이션은 성립한다.

**부족한 것은 역방향이다.** 현재 `Depends on`은 표에 있으나 `Blocks`는 부록 A 도식에서만 읽을 수 있다.
이슈 본문에는 양방향이 다 필요하다 — 지연이 발생했을 때 **무엇이 같이 지연되는지**를 이슈에서 즉시 봐야 한다.

**조치:** `후행 태스크(Blocks)` 열 추가. 선행 열에서 기계적으로 역산 가능하므로 작업량은 작다.

### ID 체계 — 재번호는 하지 말 것

**기존 `FR-` / `NF-` / `QA-` / `UX-` 번호를 유지하고, `Type` 열을 추가하는 방식을 권고한다.**

재번호를 하면 다음이 모두 깨진다 — 부록 A의 Mermaid 도식 4종, 부록 B의 커버리지 표 5종(82행 상호참조),
커밋 이력 5건의 본문, `SRS-READER.html`의 조항 참조. **얻는 것은 표기 일관성뿐이고, 잃는 것은 추적성이다.**

신설분만 `SPEC-` `MOCK-` 접두어를 쓰고, 기존 ID는 `Type` 열로 분류를 표현한다.
분류 축(무엇인가)과 식별 축(어느 것인가)을 분리하는 것이 정석이다.

## 4. 풀버전 본문 제작 순서

수정 없이 본문을 쓰면 SPEC·MOCK 태스크가 없는 상태로 작성되어 전량 재작업이 된다.

| **P0** | **태스크 리스트 문서 수정** (M1~M9) | — | 1회 | 없음 — **즉시 착수** |
| **P1a** | `SPEC-000` 공통 규약 | 1 | 1회 | P0 |
| **P1b** | `SPEC-001~010` 엔드포인트 계약 | 10 | 2배치 (5+5) | P1a · **D-01 회신** (SPEC-006·010) |
| **P1c** | `[DB]` FR-001~009 | 9 → 5이슈 | 1배치 | P1a · **D-04 회신** (FR-006) |
| **P1d** | `MOCK-001~004` | 4 | 1배치 | 대응 SPEC 완료 |
| **P2a** | `[Feature/Query]` | 12 | 2배치 | P1b · P1c |
| **P2b** | `[Feature/Command]` | 27 | 4배치 | P2a · **D-02 · D-03** (FR-034·035) |
| **P3** | `[Test]` QA-001~014 | 14 | 3배치 | P2 · **AC 확정** |
| **P4a** | `[Infra]` · `[Sec]` | 12 | 2배치 | **D-05** (NF-002) |
| **P4b** | `[Integration]` · `[Design]` | 12 | 2배치 | P1b (계약) |
| **P4c** | 의존성 최종 매핑 · GitHub Project 등재 | — | 1회 | 전 Phase |

### 이 순서의 근거

**P1이 P2보다 앞선 이유** — 방법론 Step 1의 지침 그대로다. 계약과 데이터가 기준점이 되어야
Step 2의 로직 태스크가 그것을 인용할 수 있다. 역순으로 쓰면 계약 확정 시 로직 AC를 전부 고쳐야 한다.

**P2a(Query)가 P2b(Command)보다 앞선 이유** — Query는 기존 데이터를 읽을 뿐이라 계약만 있으면 AC를 완결할 수 있다.
Command는 상태 변경 규칙(예산 차감 동시성, 상태 전이 조건)이 필요하고, 그 규칙 다수가 아직 미정(D-02·D-03)이다.
**Query를 먼저 쓰면 미정 항목 회신을 기다리는 동안 진도가 나간다.**

**P3(Test)를 P2 뒤에 둔 이유** — 방법론 Step 3 Tip이 "AC를 Feature 이슈 DoD로 삽입"이라 규정한다.
삽입될 Feature 이슈가 먼저 존재해야 한다.

**P4를 마지막에 둔 이유이자 예외** — NFR 태스크는 다른 태스크의 성능 예산·보안 규칙을 참조하므로 뒤가 맞다.
**단 `NF-003`(부하 테스트 환경)은 예외로 P1과 함께 앞으로 당길 것을 권고한다.**
성능 문제를 마지막에 발견하면 고칠 시간이 없다. 방법론상 Step 4지만 **실행상으로는 Step 1과 병행**해야 한다.

## 5. 결론

현재 태스크 리스트는 **SRS 커버리지 측면에서는 완결**되어 있다(정방향 13/13, 부속 명세 61/61, 역방향 고아 0).
방법론과의 격차는 **누락이 아니라 절단 기준의 차이**다 — 서비스·엔드포인트 기준으로 자른 것을
계약·데이터 / Query·Command / Test / NFR 축으로 재분류하면 된다.

**실질적으로 새로 만들어야 하는 것은 두 종류다.**

| 신설 | 건수 | 없으면 무엇이 안 되는가 |
| --- | --- | --- |
| `SPEC-000~010` | 11 | 4개 서비스 병렬 개발이 착시가 된다 |
| `MOCK-001~004` | 4 | Ad Serving이 앞 두 서비스를 기다려 크리티컬 패스가 길어진다 |

**그리고 열 3개를 추가해야 방법론이 물리적으로 성립한다** — `Type`, `인수 기준 출처`, `AC 작성 가능`.
특히 마지막 열이 없으면 Step 3의 "AC → DoD 삽입" 흐름에 원본이 없다.

**착수 지점 권고: P0(문서 수정)를 먼저.** M1~M4는 열 추가와 태스크 신설이므로 하루 안에 끝난다.
그것 없이 본문을 쓰면 SPEC·MOCK 부재 상태로 작성되어 전량 재작업이 된다.
