# 검증 · 인수 판정

근거 — 기준 SRS §5.1 · 제약 SRS §5.2·§6.1 · `docs/issues-aiplace/P3a`~`P3c`

**검증 태스크가 17건으로 전체의 20%다.** SRS가 `TC-FUNC-001`~`TC-NF-032` **ID만 부여하고 내용은 비워둔** 자리를 채우는 일이다.

## 1. 최소 시나리오 4종 — 네 번째가 이 제품 고유다

| # | 시나리오 | 출처 |
| --- | --- | --- |
| 1 | **정상** | 요구사항 본문 |
| 2 | **예외** | SRS §4.5.3 비정상 대응 |
| 3 | **경계** | 임계값 **정확히 같을 때** |
| 4 | **불변 규칙** | **§8.3 — 이 제품에만 있다** |

```
Given  근거 4항목 중 확인 주체가 없는 후보가 모집단에 있다
When   Top-3 를 요청한다
Then   그 후보가 응답에 포함되지 않는다
And    근거 표기 누락 이벤트가 1건 발행된다
```

**네 번째가 없으면 인수 기준이 아니다.** 예 — 근거 4항목 누락 시 제외되는가 · 빈 화면이 반환되지 않는가 · 판정형 문구가 0건인가 · 정렬 키에 가격이 섞이지 않았는가.

## 2. 판정 불가를 통과로 세지 않는다

**가장 자주 틀리는 지점이다.**

| 상황 | 처리 |
| --- | --- |
| 기준선 미실측 (`TRK-C` 15건, Phase 0 종료 후) | **판정 불가.** 통과 아님 |
| 측정 조건 미확정 (`REQ-NF-005` 3,000 RPS 적용 시점) | 판정 불가 |
| 법령 확정 대기 (`TEST-014c` 3건) | 판정 불가 |
| Phase 2 미통과 (`REQ-NF-004` 첫 제안 도착) | 판정 불가 |
| 제휴 미도입 (`REQ-NF-023`) | **해당 없음** — 미검증과 구분해 기록 |

**`해당 없음`과 `미검증`은 다르다.** 전자는 적용 대상이 아니고, 후자는 실패다.

```ts
type Verdict = 'PASS' | 'FAIL' | 'UNDECIDABLE' | 'NOT_APPLICABLE'
// UNDECIDABLE 을 PASS 로 접지 않는다. 리포트에 사유를 남긴다
```

## 3. 커버리지 대조표가 산출물이다

각 검증 태스크는 **어느 TC가 어느 스크립트에 대응하는지** 표를 남긴다.
**누락이 곧 미검증 요구사항**이므로, 대조표에 빈칸이 있으면 완료가 아니다.

`TEST-014a`~`d`가 `REQ-NF` 32건을 나눠 갖는다 — **배정 누락·중복 0건**을 확인하고 시작한다.

| 태스크 | 대상 | 건수 | Phase |
| --- | --- | --- | --- |
| `TEST-014a` 성능·가용성 | `001`~`008` `012` `027` | 10 | 1 |
| `TEST-014b` 데이터·결과 품질 | `009` `010` `011` `024` | 4 | 1 |
| `TEST-014c` 보안·개인정보 | `013`~`018` `025` `026` `031` `032` | 10 | **1말** |
| `TEST-014d` 비용·KPI | `019`~`023` `028`~`030` | 8 | 1 |

## 4. 단건 동작과 비율 지표를 구분한다

같은 코드를 다른 축으로 잰다. **합치지 않는다.**

| 축 | 예 | 언제 판정 가능 |
| --- | --- | --- |
| **단건 동작** | 파싱 실패 시 폴백이 도는가 (`TEST-005`) | Phase 1 초반 |
| **집계 비율** | 실패율이 1.5% 이하인가 (`TEST-014b`) | **질의 로그가 쌓인 뒤** |

## 5. 제약 SRS의 검증 방식을 그대로 쓴다

`REQ-IMPL` 34건은 각자 검증 방식을 명시하고 있다. **새로 만들지 말고 그대로 옮긴다.**

| 유형 | 검증 방식 예 |
| --- | --- |
| 정적 검사 | 모듈 import 방향 · 순환 의존 0건 (`REQ-IMPL-002`) · provider 직접 호출 (`011`) |
| 주입 테스트 | AI 실패 주입 → 폴백 경로 (`013`) · 이벤트 적재 실패 (`023`) |
| 감사 | 연결 문자열 (`005`) · 요청 본문 카드 정보 (`028`) · 환경 변수 노출 (`033`) |
| 회귀 | 모델 교체 시 **코드 변경 0건** (`012`) · 테마 변경 (`009`) |
| 차단 테스트 | 타 매장 데이터 접근 (`025`) · 비인가 Cron 호출 (`022`) · MFA 미등록 (`026`) |

## 6. AC가 구현 이슈로 역류한다

검증 태스크를 쓰다 보면 **구현 쪽 DoD에 빠진 항목**이 드러난다. 발견하면 해당 구현 이슈에 반영한다 — 검증 웨이브의 두 번째 목적이다.
