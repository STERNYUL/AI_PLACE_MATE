# 개인정보 취급

근거 — 기준 SRS §4.4·§8.6.4·§8.6.5 · `REQ-NF-013`~`015` `031` `032` · `REQ-IMPL-027`·`029`

**미검증이 곧 출시 불가다.** 다른 영역과 달리 "나중에 고치자"가 성립하지 않는다.

## 수집하지 않는 것이 최선의 통제다

| 요구 | 구조로 강제 |
| --- | --- |
| `REQ-NF-015` 참석자 **취향·비고 미수집** | **스키마에 필드를 두지 않는다.** 필드가 있으면 언젠가 채워진다 |
| `REQ-NF-014` 개인 제약 **단말 저장** | `localStorage`에만. Server Component에서 읽지 않는다 |
| `REQ-NF-032` **옵트인 후 전송** | **서버 경로에 도달할 코드가 없게** 만든다 |

```tsx
'use client'   // ← 이 한 줄이 통제다 (REQ-IMPL-029)
// PreferenceStore 가 Server Component 가 되는 순간 옵트인 통제가 무의미해진다
```

```ts
// ✗ Server Action 시그니처에 들어오면 이미 전송된 것이다
export async function query(input: { dietary: string[] }) { ... }
```

**동의 체크박스로 막지 않는다.** 코드 경로 자체를 없앤다.

## 파기와 목적 제한

| 요구 | 내용 |
| --- | --- |
| `REQ-NF-013` | 출발지 **세션 종료 후 30일 내 파기** — `cron/purge-origins` |
| `REQ-NF-031` | 출발지 **후보 선별 목적 외 사용 금지** — 접근 로그 점검 |

**파기 배치는 여유를 두고 실행한다.** 부분 완료로 남은 건이 밀리는데 **파기 지연이 규제 위반이 되면 안 된다.**

## 감사 — 조회와 같은 문장에서 (`REQ-IMPL-027`)

- 기록을 **별도 호출로 분리하지 않는다.** 분리하면 누락 경로가 생긴다
- 조회를 `lib/db/audit.ts` 래퍼로만 노출하고 **직접 Prisma 호출을 정적 검사로 금지**
- 애플리케이션 역할에 `AuditLog` **UPDATE·DELETE 권한 없음**
- 운영자 세션 수 ↔ 감사 레코드 수 대조 — **불일치 1건도 알림**
- **삭제하지 않는다.** 파티셔닝으로 크기 관리

## 삭제는 논리 삭제다

확인 상태 이력을 보존해야 한다 (§8.3 규칙 12 · §8.6.5).
`deleted_at`으로 표시하고 물리 삭제하지 않는다 — **단, 개인정보 파기는 예외다.** 파기는 실제로 지운다.
